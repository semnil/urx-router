# CLAUDE.md — urx-router

## Overview

Routing planning tool for the YAMAHA URX22 / URX44 / URX44V. Based on the official block diagram,
it visualizes inputs/outputs, mixer buses, and output patches as an SVG node graph, constrained so that
**only connectable routes** can be wired. Plans are saved as JSON and exported as images. Device writes
and Live sync are always enabled in the desktop build (vd protocol, `src/core/control/`).

## Tech stack

- Tauri 2 (desktop shell; Windows 11 / Apple silicon macOS)
- TypeScript + Vite (frontend)
- Rendering is plain SVG. **Zero runtime external dependencies** (no npm packages or CDNs in the runtime)

## Structure

**What each file is for, and why it is shaped the way it is, lives in `docs/{en,ja}/architecture.md` "Source layout".** This is the map; that document is the reasoning, and it is the layer an edit goes to when the behaviour changes.

- `src/main.ts` — app entry. Wires models/core/ui/i18n together

- `src/core/` — logic with no DOM: `plan.ts` plan state + JSON + the `?plan=` deep-link codec / `plan-history.ts` the undo differ, which also arbitrates the device-read merge / `plan-validate.ts` the load-time validation funnel / `routing.ts` connection constraints / `constraints.ts` rate-dependent limits and the insert-FX menu / `levels.ts` the device's level_gain grid / `meters.ts` live meters and the CONSOLE meter-point contract / `eq-response.ts` the measured PEQ response / `storage.ts` save / load / image export / `platform.ts` the Tauri-versus-browser bridge / `settings.ts` user preferences / `env.ts` build-time flags / `scene-scope.ts` the scene boundary in plan terms
  - `src/core/midi/` — external MIDI control (desktop only): `message.ts` decode / encode, `mapping.ts` the free-mapping model, `controls.ts` the control-id catalogue, `engine.ts` incoming application, learn, feedback and gangs

Keep English and Japanese in sync
- `reference/` — primary-source PDFs (block diagram, user guide) under `primary-sources/`, and reverse-engineered vd protocol dumps under `work/` (`vd/vd-protocol.md`/`vd/vd-params.md` etc.; the grounding for `control/`). **Managed in a separate private repository; the entire directory, README included, is excluded from this public repository** (`/reference/` in `.gitignore`). **Treat these private docs as part of this project: edit and keep them in sync exactly like the tracked files (e.g. correct `vd-params.md` when a device fact is confirmed). Only their commit/push timing to the private repo is managed separately — never skip a needed edit because the file lives in the private repo**. That repo carries its own copy of the Markdown table check (same `check-md-tables.mjs`, `PostToolUse` hook and docs workflow), so the table rule below applies there too
- `e2e/race/` — the live-sync race-diagnosis harness: `fake-device.ts` a URX with configurable latency, command barriers, a scriptable notify stream and refusal injection, `analyze.ts` the invariants over one ordered trace, `ui.ts` the shared locators and the value-settle wait, and the tier specs. Its own Playwright **projects** (`race` in Chromium, `race-webkit` for the `@webkit`-tagged cases), both served a trace build on port 4174. The design, the fake device's contract, the tier and case tables, every measured finding and the traps to know before writing a case are in `docs/{en,ja}/live-race-harness.md`
- `src/ui/trace-probe.ts` — read-only probe over the module state the harness cannot otherwise reach: the plan-key write ledger (who wrote which key) and the live snapshot's contents. A build flag (`VITE_TRACE=1`) rather than `import.meta.env.DEV` because the E2E suite serves a production build on purpose. The ledger reuses `plan-history`'s differ rather than a second encoding, so it and the undo entries cannot disagree about what a gesture touched
- `scripts/capture-screenshots.mjs` — documentation screenshot capture (graph + console × EN/JA, dark theme, URX44V) into `docs/assets/`; the console shot widens the viewport to fit `.con-strips`. It also shoots the ducker-bypass warning the development article uses (`screenshot-ducker-warning-*`): the default plan's USB MAIN OUT B wire is deleted, CH 5/6 is rewired to it from its Rec Point tap, and the channel's Ducker is switched on — the article's images are otherwise the only ones with no original under `docs/assets/`, which is how they silently fell three UI generations behind
- `scripts/meter-bench.mjs` + `scripts/meter-bench-run.mjs` — render bench for the CONSOLE. The first is an in-page bench that drives the view's own paint loop from a synthetic meter feed (and, with `churn`, the device-follow strip rebuild / full re-render) and reports painted frames, JS time per frame and per rebuild, DOM mutations, frame gaps and event-loop lag; the second serves a tree, runs it in Playwright **WebKit** and brackets the sample with the browser processes' CPU time. Every run also carries `scrollCheck`, which pins the strip rack's scroll offset across a re-render **in that engine** — the E2E suite is Chromium-only, so it cannot fail on WebKit-specific rendering behavior. Both reach the view through `window.__urxConsole`, whose surface is pinned by `src/ui/meter-bench.contract.test.ts`. Paste `meter-bench.mjs` into the Web Inspector console of a `pnpm tauri dev` window to measure a real device feed instead (`__urxBench.run({ feed: "none", live: false })`)

The word itself is not the target (`the level meters are measured` describes the data); the shapes are, and the set is deliberately narrow because a rule wide enough to catch every phrasing teaches rewording instead. It lexes comments rather than grepping lines, so `Object.entries(measured)` is an identifier and not a finding, a comment inside a template interpolation is still a comment, and a JavaScript file is read ONCE, by the lexical goal. It was the union of three readings for six rounds — the goal's, one forcing division, one forcing a pattern — so that a MISS needed all three to miss. **That is withdrawn.** A forced reading has no grammar, so where it differs from the goal what it produces is a recovery or an invention with nothing to tell the two apart: three rounds each found one valid, Prettier-stable file it refused (`[/\//, "…"]`, `[/[//]/, "…"]`, `[a / "x///y", "…"]`), and each proposed discriminator turned out to have the same shape as the recovery it was meant to keep. What the union was covering was **five determinate defects in the goal**, all now fixed — `export default` and `break` missing from the keywords a pattern may follow, a postfix `!` leaving no value behind, a brace after `=>` taking the body flag a declaration was waiting for, and a modifier-run walk that began one token behind the keyword. The trade is a miss class this reading can still have for a false-positive class it cannot, and a defect here is a grammar bug with one correct answer. **`pnpm format` still takes its JavaScript file list from this scan** (`scripts/format.mjs`), so neither can be narrowed alone; written as globs the two disagreed, and a `.mjs` at the repository root was scanned and formatted by nothing. It also reads **YAML, TOML, shell, Python and HTML**, each with its own reader rather than a shared `#` scan: a YAML block scalar's body and a quoted scalar that spans lines are text, TOML's `"""…"""` spans lines and its `#` needs no space in front of it while YAML's does, a here-document's body is text while the rest of its DECLARATION line is code, and a `$( … )` inside a double quote is code again. One scalar is not data: a workflow's **`run:`** holds shell — block, QUOTED or an alias to either, since GitHub runs the value rather than the way it was written, and a FLOW mapping puts several entries on one line — and its body goes to the shell reader with its offsets carried over. What makes a value that scalar is the PATH to it rather than the NAME of its key: GitHub runs `jobs.<id>.steps[].run` and a composite action's `runs.steps[].run`, and nothing else, so the reader carries the block keys open above each line — with the column each one starts at, since a key is unwound by anything written at its column or to the left of it, and with the keys a flow collection was opened under, since `steps: [{ run: "…" }]` puts a step on the line its own `steps` is on. Taken from the name alone, an `env:` variable, a `with:` input and anything nested under either were lexed against a grammar they are not written in. The VALUE: for a block, dedented and — where the header is `>` rather than `|` — FOLDED, since that is the whole difference between the two; since a here-document's `EOF` never equals an indented delimiter line; escapes decoded and line breaks folded the way YAML folds them for a quoted one — one break becomes a space, n become n-1 newlines, and a `\` in front of the first escapes it, so an escaped break carries a comment past it and a blank line ends one there — with `\n`, `\r\n` and `\r` all breaks, or a CRLF file's escaped break is read as an escaped carriage return and then a fold; and only under `.github/workflows` or `.github/actions`, since nothing else in this tree runs one. **What lexes it is the shell the step CHOSE** — `bash`/`sh`, `pwsh`, `cmd` or `python`, with `powershell` (Windows PowerShell, which GitHub runs on Windows alone) REFUSED by name rather than read, resolved from the step's own `shell:`, then its job's `defaults.run.shell`, then the workflow's, then the runner's own (bash everywhere but Windows) — since a step's `shell:` may be written after its `run:` and a job's `runs-on` after its steps, the values are queued and lexed once the document is read. Read as bash whatever it chose, a `shell: cmd` step's `echo #` was reported as a comment cmd does not have and a `shell: pwsh` step's `<# … #>` was not read at all. PowerShell's block comment does NOT nest — the first `#>` ends it and what follows is code — its `#` begins a comment only where a TOKEN may begin, and its strings are not the shell's: `'…'` doubles the quote, `"…"` escapes with a BACKTICK, a here-string runs to a line beginning `"@`, and the expandable forms are not opaque, since a `$( … )` in either is a statement list. cmd has `rem` opening a line, behind an `@` or not, and a `::` label, and no `#` at all. A shell not in that set is a custom command line, a COMPOSITE action's run step that declares none has no default to fall back on, and a runner named by an expression takes the non-Windows default, since the two defaults agree about `#` and neither is cmd — each of those is left unread rather than lexed against a grammar it was not written in. Shell's own three: a backtick substitution is code even inside a double quote, a case PATTERN's `)` has no opener and closes nothing, and `case` is a keyword only where a command could start — a position WHITESPACE carries rather than ends, and one that a reserved word opening a compound list, a `!`, and `time`'s own options (`time -p case …`) all carry on the same line — `time`'s only, since a `-word` transparent everywhere makes the next word a keyword and the `)` that closed a substitution read as a pattern's, and only until the next boundary, since `time` measures ONE command. The command position, that option state and the open `case` runs all belong to the substitution FRAME they were read in, or an inner `;` leaves the outer position open and the `)` that closes the substitution is read as a pattern's. A `[` or a `{` written against a key opens a flow collection as much as one standing on its own, or that entry reads at flow depth zero and its value runs to the end of the line — and only where a node may BEGIN, since block context lets a plain scalar hold either character (`echo a[0`) and taken as an opener one of those left a collection open for every line after it. A flow collection is ONE node however many lines it is written across, so the scope it opens and the key still waiting inside it are carried across the line break, the lines inside it open no block key and unwind none, and what carries a key to its value there is the ORDER rather than the indentation. Read as though every line began outside one, an action's `with:` input read at the path of a step's `run` and a `run:` whose value sat on the next line read at no path at all. A quoted mapping key is the same key, escapes decoded: `"run": |` is the block GitHub runs, an anchor or a tag may sit between the key and its value, quoted or block — and where the key's line ends after that, the value is the next node indented further, in any of its three spellings, with the anchor in front of the key belonging to it. What such a header's indentation indicator counts from is then the KEY's column, on the line above, and what the block ends at is that column too, since a header written on its own line may sit at its body's own indentation. A PLAIN scalar is that value too — `run: echo ok` is the shell GitHub runs, the same as the other spellings, and handed to no reader at all it was the one this looked straight past; YAML ends a plain scalar at a ` #`, so what survives into the value is a `#` behind a `;`, which is where a shell comment begins, and the scalar runs to the end of the line in block context, to the `,`, `]` or `}` that closes the entry inside a flow collection, and across the lines it continues onto in EITHER — one break folding to a space and a blank line to a newline, with what a flow continuation must be indented past being the block node the flow was opened on rather than the column of a key written inside it. Nothing a line BEGINS with ends a scalar already started: `- b`, `-b` and `?b` are the words they look like, and so is `x:y`, since a mapping key's colon has to be followed by whitespace or by the end of the line and one that is not is part of the key. An ALIAS is that value — `run: *script` is the shell its anchor holds, with the name ended by `,`, `]` or `}` where a flow mapping ends it rather than by the line, and the finding points at the line the text is on, counted ONCE however many aliases read it, and an EXPLICIT entry writes the key on its own line (`? run`) with the `: |` that carries its value on the next — across the blank and comment-only lines that are not nodes, and at the key's own column, where the ordinary spelling takes a deeper one, so a SIBLING sequence entry is not mistaken for a value the key never had. A sequence entry may be written with nothing after its dash, and unwound at the dash's own column an INDENTATIONLESS sequence — whose dash sits at the column of the key that owns it — unwound that key and put its entries at the path of the mapping above. TOML closes a multi-line string on the LAST three quotes of a run, not the first. Python's f-string replacement field is code since PEP 701, comments included, while its format spec is text again — a `#` there is a fill character, and a `!s` conversion ends the expression rather than opening the spec. PEP 750's template strings carry the same fields, so a `t` prefix is read like an `f`. Whether a `/` opens a pattern or divides is carried as a lexical GOAL — the last token plus a stack per bracket kind — because the preceding character cannot decide it (the same state answers the TypeScript type positions, where a generic constraint puts a brace at the signature's own depth — a keyword list rather than a type grammar, so a brace inside a type it does not name can still be read as a block; what settles the known case is that a brace right after `=>` is never a declaration's body). A type ARGUMENT list closes on a value — after anything that ends one, an index and a call included — so `f<string> / 2` divides while `a < b > /re/` compares and then matches; one grammar cannot separate those, and what does in formatted text is the space BEFORE any trivia, since Prettier writes every comparison spaced (`a /* c */ < b`) and every type argument list tight against its name (`f/* c */ <string>`). A DECLARATION's type parameters close on its BODY instead, or `class C<T> {}` leaves an object literal behind and the pattern on the next line is read as a division into it — with the modifier run walked past first, since `abstract` and `declare` are part of it, and the DECORATORS in front of it too. A run is two phases — reading its own expression, then waiting for its target — because `@sealed` ends on a name, `@a.b` on a dotted one and `@dec(…)` on a `)`, and what decides the declaration is the token recorded when the run opened. Its ARGUMENTS are out of that, by a bracket depth that counts type arguments as well — a `{` in one is an object literal, a `class` in one is an expression, and `@dec<string>()` puts a run between the name and the call, and a member's own decorator ends at the member rather than at whatever class expression its initialiser holds. Inside a type there is no comparison for a `<` to be, so a nested generic signature opens whatever sits in front of it, and the `;` that ends an unclosed run is the one at the run's own bracket depth rather than the one separating a type literal's properties: `)` ends a value after a call and starts an expression after `if (…)`, `}` ends one after an object literal and starts one after a block, and `+` is an operator in `a + /re/` and half of a postfix `++` in `x++ / 2`. It reads **Rust too** — `src-tauri/src` is a third of the backlog and was not being opened at all — where block comments NEST, a raw string carries any number of hashes, and a leading `'` is a lifetime far more often than a character literal (consumed as a quote it runs to the next apostrophe and takes every comment between). **The scan set is what git reports** (`ls-files --cached --others --exclude-standard`), not a list of directories: **a source the scan never opens is a source it does not check**, however well it lexes, and a list of roots answers which directories were thought of rather than what the repository carries — the skill's `plan_tool.py` sat outside five named roots, and naming it on the command line printed `0 source file(s)` and exited 0. A file written but not yet added is in scope; what the ignore rules cover never is. Asking git also fails LOUDLY when it cannot answer, rather than walking what it can reach. The two files this check does not read are excluded by their PATH: matched by NAME, a file called the same thing under any other directory was exempt from a check it is source for like any other. **The inventory and the scan set are separate**: `pnpm format` takes the first and this check the second, and folding the self-exclusion into the inventory made the formatter skip this checker and its own pins — narrower than the glob it replaced, and it shipped unformatted edits past a green `format`. `.tsx` is deliberately out of scope: JSX text is neither code nor a comment, a URL in it opens a line comment at the `//`, and this tree carries no JSX to write that state machine against. Importing the module runs none of the command line — every pin imports it, and each import used to scan the tree with vitest's argv. **`scripts/comment-provenance-baseline.json` is a per-file CEILING**, not a target of zero: the idiom predates the rule by a long way, and removing it in one sweep would be a comment-only diff across a third of the tree. A file may carry what it carried and no more, so a NEW one is red while the backlog stays countable; a cleaned file prints its lower count in the ledger's own shape, so lowering the ceiling is a paste. **`--update` only ever LOWERS** — taking the counts as found would let a run add a comment, be refused, update, and come back green with the violation inside; a rule change that legitimately grows the corpus is `--reseed`, a separate decision that shows in the diff as one. **The edit-time hook asks the same ceiling** — refusing on any finding at all would refuse every edit to each of the files the ledger names — and a run given explicit paths compares only those, since a row it never opened is not a row that emptied; a partial `--update` merges rather than rewriting the file from the subset it read

```sh
pnpm reset:storage # clear the dev app's (browser) localStorage = opens the ?reset URL
```

How to reset the dev app's localStorage (theme/model/meter point/consent gate/recent files/inspector open state/user preferences) **and the remembered window geometry** (the state that lives in files rather than in `localStorage` — `.window-state.json` and the `.window-scale.json` beside it, both deleted by the reset; architecture.md "Window geometry" has the mechanism): in the browser, open `http://localhost:5173/?reset` (or `#reset`) (`pnpm reset:storage` opens it; cleared synchronously at startup, then the flag is stripped from the URL); on desktop, launch with `pnpm tauri dev -- -- --reset-storage` (Rust reads `--reset-storage` and the frontend clears + reloads; `reset_storage_requested` command). Both entry points funnel into the reset routine in `src/main.ts`.

**Launch flags run headless against real hardware** — `pnpm tauri dev -- -- --experimental --self-test` (both flags: the self-test's auto-run is nested inside the experimental gate), `-- -- --prepare-modified`, `-- -- --reset-storage`. A packaged build takes them as `open -a 'URX Router' --args --experimental` / `urx-router.exe --experimental`. Only Rust's `eprintln!` reaches stdout; the frontend's `console.*` and the status bar live inside the webview, and Vite's client forwards `console.warn` as `[vite] (client) [console.warn]` when the dev server is attached. **Do not edit sources while a run is writing to real hardware** — an HMR reload is a page load, and each page load starts another destructive sweep over the one already running. The `take_launch_action` latch stops a one-shot flag from re-firing, but the run itself still restarts, and a sweep killed before it reaches its restore leaves the unit perturbed with the original state it captured living only in the dead page's memory: unrecoverable, not merely interrupted. Stop the app before editing.

**Never pipe a run through `tail`** — not a launch, not a test run. A pipe's exit code is `tail`'s, so a failing suite reports success and the failure list falls outside the window that would have shown it; and `tail` buffers, so a long-lived process prints nothing at all until it exits. Redirect to a file and read the whole log.

On this machine (Mac), node/pnpm go through nodenv (`~/.anyenv/envs/nodenv/shims`). The PATH is not loaded in non-interactive shells.

Node >= 21.2 is required (`package.json` `engines`): the `?plan=` deep-link codec needs `CompressionStream("deflate-raw")`. The matching browser floor is Safari 16.4+; `plan.ts` raises a typed `planUrlUnsupported` error on older webviews instead of failing as a malformed link.

If `pnpm tauri dev` keeps showing a stale version or UI, discard the build caches with `pnpm clean` and restart (the version is embedded at build time via `tauri.conf.json`→`../package.json`, so it easily sticks in the Vite cache). The webview's persistent data (the consent gate in `localStorage`, etc.) lives outside the app and is not covered by `pnpm clean`; on macOS delete `~/Library/WebKit/<productName or identifier>/` manually.

E2E runs against a production build served on port 4173 (and the `race` / `race-webkit` projects against a trace build on 4174), and `reuseExistingServer` is on locally: a `pnpm preview` left running (a `build:demo` bundle, say) is reused as-is by `pnpm test:e2e`, silently testing the wrong bundle. Stop it first — and note the same trap catches a **second checkout**: two runs sharing a port means the later one is handed the earlier one's bundle and passes against code that is not the code under test.

Both ports come from the environment — `E2E_PORT` / `E2E_TRACE_PORT`, defaulting to 4173 / 4174 — read in `playwright.config.ts` and in `scripts/e2e-serve.mjs`, which the web server inherits, so the URL polled and the port bound are resolved once from one place. A port pair alone is not isolation: two runs in one checkout still build into the same `dist/` and `dist-trace/`, so the second one's build overwrites the bundle the first is serving. **`pnpm e2e:worktree` is the isolated path** — it derives its port pair from the **process id** (deliberately, rather than scanning for a free pair: a scan is separated from the bind by the `vite build`, and two runs scanning in that window both pick the same pair), puts the run in a throwaway `git worktree`, and carries the working state into it (tracked modifications as a patch, untracked-but-not-ignored files as copies), because a worktree otherwise checks out HEAD and would test the last commit while reporting on the working tree. `--keep` leaves the tree; anything after `--` goes to Playwright.

**Never stop a process by pattern, and never kill a port holder just because it holds the port.** `pkill -f "playwright test"` matches another checkout's run, a wide `pkill -f vite` has SIGTERMed the operator's own `pnpm tauri dev`, and `until ! pgrep -f …` waits for someone else's run to finish. Read `ps` for the cwd and args, prove the process is yours, then act on that **PID** — on a shared machine that is the only safe form, and it is the same rule whether the target is a leftover preview server, a stuck Playwright run, or a dev app.

The version lives in `package.json` alone — `src-tauri/Cargo.toml` stays at `0.0.0` and `tauri.conf.json` reads `"../package.json"`. A version bump touches that one file, **in a pull request that carries nothing else** (`chore(release): X.Y.Z`). **Merging that PR is the release, and nothing else is.** The isolation is therefore not tidiness: it is what makes the released commit the one the checks ran on, and it is why `race.yml`'s trigger carries a version clause at all. That clause no longer decides this PR on its own — a bump edits `package.json`, which is not documentation, so the exclusion answers it first — but it is the written statement that the harness stands in front of the one merge that ships, and it is what survives anyone narrowing the exclusion. Folding a bump into a feature PR — which is how 1.4.1 through 1.5.1 were cut — releases whatever else that PR contained. With two PRs open at once it is worse than untidy: the version number then depends on merge order rather than on the bump, which is how v1.5.0 shipped both branches (the one *without* the bump merged first). Nothing warns you, because neither PR touches `package.json` in a way that conflicts.

CI is 9 workflows: PRs run build + e2e typecheck (`pnpm typecheck:e2e`) + the race harness's skip ledger (`pnpm check:skips`) + unit tests + **the ordinary E2E suite** + **`cargo test`** (`ci.yml`; its expensive jobs skip `**/*.md` / `docs/**`-only changes, except the skill's generated `references/model-*.md`, which `skill-export.test.ts` diffs — that skip is a **job** condition, decided once by the `preflight` job from the API's own file list, and never a trigger filter, for the reason in the next paragraph) and get their formatting verified (`format.yml`: Prettier + cargo fmt applied to a checkout, failing on the resulting diff — it used to push the fixes back to same-repo PRs as a `style:` fixup commit, and the workflow header carries why a required check cannot coexist with that); the document and configuration checks are `docs.yml`, which runs on **every** PR and push (`pnpm check:md` + `pnpm check:assets` + `pnpm check:gates`, seconds, no install — `check-assets-index.mjs` used to run in `ci.yml` as well, which was only needed while `docs.yml` was Markdown-filtered and could not see a moved file the documents still name); the live-sync race harness is its own `race.yml` (three shards + a WebKit job), whose harness jobs run on **every PR except a documentation-only one, and on the version-bump PR** — a `detect` job, which itself runs on every PR, diffs the changed paths against the base and compares the `version` field across the PR, since `paths-ignore:` on the trigger would skip the whole workflow, which reports no check run at all, and could not ask whether the version moved — and on demand via `gh workflow run race.yml --ref <branch>`; three readings — the tiering, the trigger's wall-clock cost per job, and how many of a sampled 80 merges it fires on — live in `docs/{en,ja}/live-race-harness.md`, and `race.yml`, `ci.yml` and `post-merge.yml` point at that document instead of restating them (the copy in `post-merge.yml`'s header had drifted against it); the third-party license gate and the platform Rust cache warming run post-merge (`post-merge.yml`; the warm build keeps the next release off a cold cache — rationale in the job header); license generation itself is the reusable `licenses.yml`, called by both `post-merge.yml` and `release.yml` (once per run, its artifact feeding both platform builds); the desktop installers build for a `vX.Y.Z` tag into a draft Release (`release.yml`) and the browser demo deploys to GitHub Pages when that draft is **published** (`pages.yml`, on `release: published`); `tag-release.yml` is what creates that tag. **The frontend unit job and each of the ordinary E2E tier's three shards upload coverage to Codecov** — under the flags `unit` and `e2e`, four uploads that Codecov merges into one reading; the race jobs upload none — **and Codecov's own behaviour is configured in `.github/codecov.yml`**: the service's defaults fail the `project` status on any decrease at all while the E2E half of the merged figure is not reproducible to the line, so the threshold, the readings behind it and why `patch` stays at its default are in that file and stated nowhere else. All third-party actions are SHA-pinned (`uses: owner/repo@<sha> # vX.Y.Z`); Dependabot's github-actions ecosystem (`.github/dependabot.yml`) bumps the pin and the version comment together. Exception: `dtolnay/rust-toolchain` has no version tags, so it is pinned to a master commit with an explicit `toolchain:` input and updated manually. **The `cargo test` job runs on macOS**, not the cheaper Ubuntu runner: this crate is only ever built on macos-26 and windows-latest, and a Linux build would need libwebkit2gtk from the Ubuntu mirror — the same sequential apt path taken out of every E2E job above, on a platform nothing else here compiles on. Before it existed, **no PR job compiled `src-tauri` at all**, and `cargo check` would not have covered it either: it does not build `#[cfg(test)]`.
**What a merge waits for.** The branch ruleset on `main` requires four status checks — `ci-required`, `docs-required`, `format`, `race-required` — and `.github/required-checks.json` is the only place that list is written down outside GitHub's own settings. One rule shapes all of it: **a workflow skipped by a trigger filter reports no check run at all**, so a required context it carries sits at "Expected" and the pull request can never merge, while **a job skipped by `if:` reports success**. Every pull-request workflow therefore triggers unfiltered and every path-dependent skip is a job condition — the opposite of how `ci.yml`, `docs.yml` and `race.yml` were written before this existed. The quiet third case is why the two gates are `if: always()` jobs that read `needs.*.result` themselves: **a job skipped because something it needed failed also reports success**, so a gate wired with a bare `needs:` would be skipped by its own failed dependency and the ruleset would read a red run as green. A gate also has to wait for *every* job in its workflow, or a new job's failure blocks nothing. `pnpm check:gates` holds all of that from the workflow side, and runs in both `preflight` and `docs.yml` so a change to either one's trigger is still caught by the other. The ruleset itself it can only check with `--ruleset` from an admin's machine: `permissions:` has no administration scope, so **no token available to CI can read a ruleset** — and nothing here writes one either, so the manifest and the live rule are two hand-kept copies with `pnpm check:gates --ruleset` as the only thing that compares them. **Until that command reports the four, this paragraph describes the manifest rather than the repository**, and the check that is missing from the ruleset is one nothing objects to merging over. Two further properties decide what may be added here. Required checks are evaluated **on the head commit**, so **nothing in CI may write to a pull request's branch**: a bot push moves the head past every check run, and a `GITHUB_TOKEN` push triggers no workflow to replace them (the same rule `tag-release.yml` works around below), leaving a pull request that cannot be merged and cannot be made mergeable except by a human push or a close/reopen. That is what ended `format.yml`'s fixup commit, and it is the test any future "CI fixes it for you" idea has to pass. And Codecov's `codecov/project` / `codecov/patch` are deliberately absent from the list: they report only when an upload happens, which is exactly the "sometimes reports" shape the whole arrangement is built to keep out. One thing nothing here can catch, because it is a repository setting rather than a file: **turning on a merge queue breaks all four at once** — a queued pull request runs on the `merge_group` event, which no workflow here triggers on, so every required context goes missing on the branch the queue builds. Adding that trigger is part of enabling the queue, not a follow-up. The ruleset's bypass actor is the repository-admin role, so all of this gates the process rather than the operator.

**Every job carries a `timeout-minutes`, and every step that fetches from a host outside GitHub carries one too.** Not a budget — a hang detector, sized from the job's measured duration with several times the headroom, because a false timeout on the release path costs far more than a slow one. GitHub's default when the field is absent is **six hours**, which is what a stalled release build used to be able to spend. The step-level bound exists for attribution: a job killed by its own budget reports "cancelled" with the reason buried in a log the API will not serve while the run is still going, and finding it means reading several hundred lines. `.github/actions/install-browsers` is the one place that carries the reasoning, the measurements and the message; `pnpm install` sites carry a bare bound and point at it. The measured event behind all of this — a degraded Ubuntu mirror stalling `playwright install --with-deps webkit`, whose system-library half is an order of magnitude more sequential .deb fetches than chromium's, past a whole job — is also why **every E2E job now runs inside the official Playwright image**: pulling the image costs about what the apt path costs on a good day, so it costs nothing in time and takes the Ubuntu mirror out of the picture entirely. **The counts and timings are stated once, dated, in that action's header and nowhere else** — they move with the browser build and with the runner image, and the copies had already drifted against each other while both read as measured. The tag is derived from the lockfile (`.github/actions/playwright-version`) and reaches `container:` as a prior job's output, since `container:` is evaluated before any step of its own job; hand-pinning it would drift at the first Dependabot bump and the symptom is a browser build the installed Playwright does not drive. **What made webkit's install fatal and chromium's survivable is that apt is sequential** — the same request count over a parallel client is a different risk, which is why `pnpm install` and cargo — both of which fetch a comparable number of files, concurrently — were left alone. Count the requests, then ask whether they are issued one at a time.

**How that release actually fires.** `tag-release.yml` watches `ci.yml` finish on main; when that push moved `package.json`'s `version`, it tags the tested commit `vX.Y.Z` and starts the installer build. Two things about it are load-bearing and easy to undo by accident. It triggers on `workflow_run` rather than on the push, because the installers are built from that tag and **a tag a published release points at cannot be moved afterwards** — so it has to name a commit that already has a verdict. And it reaches `release.yml` with `gh workflow run ... --ref <tag>` rather than letting its `push: tags:` trigger fire, because **a tag pushed with the repository's `GITHUB_TOKEN` starts no workflow at all** and `workflow_dispatch` is the documented exception. That is why `release.yml`'s `check-tag` gates on `GITHUB_REF_TYPE` being `tag` instead of on the event name: a dispatch on a tag must mean what a tag push meant, while a dispatch on a branch stays the packaging check that creates nothing. The job is a no-op on any push that did not move the version, refuses to move a tag that already exists, and refuses to push one at all in a shape `check-tag` would decline — the two read the same `scripts/release-tag-shape.sh`, and asking in front of the push is what keeps a bad channel from costing an immovable tag.

**The demo waits for the draft.** The tag only produces a **draft** Release; `pages.yml` runs on `release: published`, so the browser demo goes live with the gesture that ends the draft's review rather than with the tag, and the two stop describing different versions for however long that review takes. **That works only because a person publishes it** — the GITHUB_TOKEN rule above cuts the same way here, so a draft published from a workflow with that token would fire nothing, and the symptom is not a failed run but **no run**. Automating the publish means giving `pages.yml` an explicit dispatch in the same change.

## Conventions

- Code identifiers and comments in English. Comments describe behavior only. Minimize diffs
- **A rule's text lives in exactly one layer.** The global `~/.claude/CLAUDE.md` owns how the operator works across every project; **this file** owns this repository's process rules and its overrides of the global one; `docs/{en,ja}/` own anything that is really a statement about how the software behaves; the private memory owns **the failure that produced a rule and the decisions that were closed** — never the rule text, because memory is recalled as background and is the weakest place to put something someone must obey. Put a new rule in its owning layer and leave a pointer elsewhere; when a copy and the owner disagree, the owner wins and the copy is cut
- **`pnpm format` has no file list of its own.** `scripts/format.mjs` takes one from `check:comments`'s scan set and keeps what Prettier parses — `.ts` / `.mjs` / `.cjs` / `.js` / `.css` / `.html`. The JavaScript half is the load-bearing part: the provenance check's one false positive is unreachable in formatted text, and that argument is only as wide as the formatter's reach, so the two lists are one list. It carried globs until then, and they had already drifted apart. What it formats is the INVENTORY, not the scan set — this checker excludes its own two files from what it reads, and that exclusion has no business deciding what Prettier sees. YAML is deliberately left out although Prettier parses it — the false positive is a JavaScript shape, and reformatting seventeen workflows would be the formatting-only diff the global CLAUDE.md forbids. **Measure before quoting a conformance claim**: away from this tree Prettier defaults to `printWidth` 80 and calls `src/style.css` and `index.html` non-conforming, so a check run outside the repository's own config answers a different question. An UNTRACKED file is out of the derived list until it is added, which is the one thing the globs did differently
- **Required**: run `pnpm format` (+ `cargo fmt` for Rust changes) before committing. `format.yml` verifies both and fails on the diff, and `format` is one of the contexts a merge waits for. It was the other way round until required checks arrived — the workflow applied the formatting to a same-repo PR and pushed a `style:` fixup, and running it locally was a courtesy that saved you a rebase. **A bot push cannot survive a required check** (it moves the head past every check run, and a `GITHUB_TOKEN` push starts nothing to replace them), so the write half was removed rather than kept and worked around; the reasoning is in the workflow header and in "What a merge waits for" above. The upside of the trade is that the fixup commit no longer diverges your branch behind your back
- A note pasted between rows of a Markdown table ends the table: every row after it is absorbed into that paragraph and stops rendering. Keep the note where it belongs and **restate the header + separator row** to resume the table. `scripts/check-md-tables.mjs` catches it (`pnpm check:md`, `docs.yml`, and a `PostToolUse` hook — `.claude/settings.json` is tracked so the hook reaches every clone; `scripts/md-hook.sh` runs `check-assets-index.mjs --hook` behind the same trigger, so an asset row broken by a CLAUDE.md edit — or a file reference broken by a `docs/{en,ja}` edit, which the hook used to skip while checking that same file's tables — is reported at the edit and not in CI). markdownlint cannot see this class of breakage: the swallowed rows are no longer a table to it
- **Every string in `src/i18n/en.ts` carries one of three markers, and `Messages` is derived from them** — `dev()` a control reproduced from one of the unit's own screens, `fixed()` identical for a reason that is not the device, `tr()` this app's own copy. The marker is not decoration: `dev()` / `fixed()` give the value a **literal type**, so `ja.ts` fails to compile if it translates one, and an unmarked string widens to `string` and trips the assertion at the foot of the file — which is what forces a new key to declare its kind rather than default silently into being translated. **What none of it can check is whether the declaration is true**: a device row marked `tr()` and then translated compiles cleanly, so that call is a judgement the author states in the PR and a reviewer confirms by eye. Which rows are the unit's, and how that was established (its Language set to Japanese, seven screens read one at a time), is in architecture.md "Localization" → Terminology; the contributor-facing form is in `CONTRIBUTING{,.ja}.md` "Conventions" and a summary in `README{,.ja}.md`
- Documentation is maintained in Japanese and English (`docs/{ja,en}`); diagrams use Mermaid notation
- **When changing routing rules, keep `docs/{en,ja}/device-model.md` and `src/models/` in sync** (the official block diagram is the primary source). After changing `src/models/`, also regenerate the data bundled with the `urx-routing-planner` skill (`.claude/skills/urx-routing-planner/scripts/models.json` + `.claude/skills/urx-routing-planner/references/model-*.md`) via `UPDATE_SKILL=1 pnpm test skill-export` and commit it (generator: `src/models/skill-export.ts`; drift is caught in CI by `skill-export.test.ts`)
- **The skill's hand-written half has no guard at all and goes stale in silence.** `SKILL.md`, `references/plan-schema.md`, `references/device-apply.md` and `scripts/plan_tool.py` have no test and no lint and sit outside `pnpm format`; the Markdown is table-checked by `pnpm check:md`, and `plan_tool.py`'s comments are read by `pnpm check:comments` — neither of which knows anything about the contract they describe — so the app changes and they keep answering confidently with the old contract. Update them inside the same change as any of these **six**, each of which has actually gone stale before (audited 2026-07-26, PR #215): (1) **the plan document's shape** — a field added to `serialize` / `deserializeDocument`, e.g. the scene-scoped `scope:"scene"` that drops `sampleRate` and the out-of-scene state, which makes a pasted plan read as "no output patch"; (2) **a new `NodeParams` key**, e.g. an output bus master's `pan`; (3) **a claim about a parameter's stability** — an insert-FX / FX selector write is **irreversible**, it refills the engine array with the type's defaults (`control/insert-fx-effect.ts`'s header is canonical); (4) **the load-time gates `plan_tool.py` mirrors** — `deserializeDocument`'s format/version check, the app's model check, and the **silent-drop** rules (unknown kind, invalid params, non-finite leaf, one bad array element dropping the whole collection); a dropped wire is out of scope for the routing check rather than a hard problem; (5) **the write UX** — the Device-menu confirms (firmware mismatch, the rate three-way) and the Preferences device scope, since *Scene only* writes no output patch and a patch-centric plan then never reaches the unit; (6) **"available in a future release" wording**, which becomes a lie at the next ship. **Semantic constraints that never appear in the route table (signal-flow ordering = pre/post-fader, duckers) cannot be generated at all**, so those hand-written feasibility notes are their only carrier — example: channel → USB/SD direct outs tap at the Rec Point = pre-fader/pre-ducker
- **The skill is also published as a marketplace plugin, and both of its manifests are versioned by hand.** `.claude-plugin/marketplace.json` and `.claude/skills/urx-routing-planner/.claude-plugin/plugin.json` each pin `version`, and both sat at the version they were published with through every subsequent change to the skill's content until an audit caught it. **Nothing reads either file** — `skill-export.test.ts` diffs the generated half, `pnpm check:assets` reads the documents and the asset table, and no workflow greps them — so an installed copy is never told an update exists. Bump both in the same change that alters `SKILL.md`, `references/` or `scripts/`
- Keep the theme palettes in sync between the CSS variables in `src/style.css` and `PALETTES` in `src/ui/graph.ts` — architecture.md "Display themes" enumerates what has to correspond. **The wire half is the one pair with a test** (`pnpm test palette.contract`): six connection kinds share three colour families, and the mapping lives in `WIRE_GROUP` in `src/ui/graph.ts`, so adding a kind does not compile until it is placed. The **rail** and **background** pairs still have nothing checking them, and the background pair has no on-screen tell at all
- **The design system — every token, component recipe, canvas constant and copy rule, rendered as live specimens in the app's own CSS — is a Claude artifact, not a repository document** (link in the operator's private memory, since this repository is public and the artifact is not). It is a *copy*: `src/style.css` and `src/ui/graph.ts` stay the source of truth, so a token or recipe change has to reach the artifact in the same change or it goes stale in silence. Read it before adding a surface, and before inventing a button / chip / fader / modal that an existing recipe already covers
- Do not write machine-specific values, real device UDIDs, or real control-protocol values in code/documentation (placeholders + files outside git). Values the application needs to work correctly (device parameters, routing rules, the level_gain grid, addresses/encodings of confirmed broker params, etc.) are exempt from this rule and may be written in `docs/` and `src/`
- Device writes and Live sync (`src/core/control/`) are always enabled in the desktop build (consent to the risk of destructive writes is covered by the first-launch gate in `src/ui/consent.ts` and the installer license). Only the self-test round-trip diagnostics require an `--experimental` launch. **Write only confirmed parameters — confirmed means verified on the unit itself**, by writing a value and reading the result back from the hardware, not inferred from a static descriptor and not read off a broker dump. A descriptor lies: the parameters the unit's own UI drives are frequently different ones, and some emit no notify at all when the front panel moves them (D.Gain, the FX / insert-FX engine arrays), so a dump can look complete and still be describing something the app must not write. Never add a speculative address to `params.ts`
- **A claim that acquires a "provided that" is a new verification item, from the moment the clause appears.** The rule above fires before an implementation and cannot catch this one, because the second item never arrives as an open question — it arrives as a subordinate clause inside the answer to the first ("the URX22 D.Gain map holds, provided the ids follow stereo-pair position"), and a clause gets settled by judgement without anyone noticing that a decision was taken. Two moves are open: measure it, or record it with what would settle it. Both already have a shape here — `UNVERIFIED_MAPPINGS` in `src/core/control/translate.ts` registers each guess beside the addresses that decide it, which is what lets the self-test return a verdict per guess (`unverified[]`: confirmed / refuted / could-not-test) instead of one pass; the private `reference/work/device-tests/PLAN.md` keeps the prose form, one row per open item — the question, why the answer is needed, and the observation that would answer it. **Deciding it quietly is the third move, and the only one that leaves nothing behind**: an assumption nobody wrote down reads exactly like an assumption nobody made, and the same file records what that costs — a settlement declared from memory rather than from the list, with unmeasured items still in it. That is why the ledger is a field in the report and not a habit; the pull request template asks for each assumption with what would settle it, or an explicit "none", so leaving one out has to be written as a false statement instead of passing as a silence
- **When adding features or changing the UI, add E2E coverage to `e2e/*.spec.ts`.** Writing the test is the obligation; **running it locally is not** — the PR's own CI runs the ordinary tier (`ci.yml`, `pnpm test:e2e:app`) and a failure is reported on the pull request, which is where it gets read. Run whatever you find useful before pushing, at your own judgement. **The race harness runs on the pull request too** — on every one whose diff is not documentation alone (`race.yml`'s `detect`), so a live-sync break surfaces at the merge that caused it. It is an EXCLUSION rather than a watch list because three attempts at a list each left a real dependency out, and each of those was a pull request that could break the harness while `race-required` stayed green; the sequence, and the recorded accident that made `src/**` a whole directory in the first place, are in `docs/{en,ja}/live-race-harness.md`. `detect` applies the same documentation rule, in the same order and with the same `model-*.md` exception, as `ci.yml`'s `preflight`. **A comment-only diff is not excluded**; the exclusion was measured before being dropped, and that reading — 3 of the 42 `src/**`-touching merges in an 80-merge sample — is in `docs/{en,ja}/live-race-harness.md`. `pnpm test:e2e:race` and `gh workflow run race.yml --ref <branch>` are still how to pull a verdict forward or re-run one. **`race-required` being green still does not say the harness ran** — a job skipped by `if:` reports success, and a required context must be `success` to merge, so "did not run" has no colour of its own to be shown in; what distinguishes them is `detect`'s log, which prints its reason on both sides. What the gate DOES now catch on every pull request is the harness disappearing — `pnpm check:skips` fails if a spec file collects fewer cases than the floor in `e2e/race/skip-ledger.json`, so a deleted or uncollectable case is a red check rather than a smaller green run
- **A case that fails only sometimes has a private ledger**, `reference/work/e2e-flakes.md` — one section per case, open and closed alike, each carrying what was ruled out and how, and what observation would settle it. **Read it before re-deriving.** A `boundingBox()` that answers null has been the open one for a while, and its refuted hypotheses are written down precisely so the next session does not kill them again — including one that is refuted *for that case* and is the plain answer for a different case with the same symptom. The file also carries **how to reproduce a load-dependent failure**: CPU-throttle the renderer over CDP rather than loading the machine (deterministic, no orphan processes, invisible to anyone else on it), with the conversion to a CI runner and the measured thresholds. Both of the ways a load experiment was botched here are in it too, and both look like findings until you notice you caused them
- **An item only the Windows checkout can settle goes to `reference/work/windows-verify/`, and leaves this side's task list.** One section per item carrying five fields — the claim, what is still unverified, how to measure it, what would settle it, and the result — written so the session in the other checkout can act on it without asking. **Append results rather than replacing them** while an item is open: "measured and inconclusive" and "never measured" are indistinguishable afterwards otherwise, which is the same discipline as the flake ledger. **Once an item settles, fold its durable conclusions into `docs/{en,ja}/` and delete the section** — but only in that order, and **only once the section's own result field holds the readings**. Settling and folding in one session is the case that skips it, and it has happened: a run deleted its sections with their results still reading "not measured", so the history now says the opposite of what took place, and the folded text plus the screenshots that directory keeps are the only copy of those readings. **No settlement record goes into the ledger itself** — the document folded into is that record, and the ledger's own "この台帳の使い方" owns that rule; this is a pointer to it, not a second copy. Deleting without folding is what turns the distinction above back into a guess; the raw readings then live only in that file's git history, which is deliberate (they are OS- and machine-shaped evidence, not statements about this software, and do not belong in the public documents). The ledger exists at all because the two checkouts no longer share anything else — the memory that used to carry this is per-machine and the Windows side's copy is gone
- **Every dialog, window, menu and popover shows everything its messages say it does, and that stays at 100%.** `e2e/inventory.spec.ts` derives the expected set from the message catalog and drives each surface through its states, so **adding a message obliges some surface to display it** — there is no way to add one and have nothing check it. Four escapes exist and each has to be *written down* in that file: another surface shows it (`elsewhere`, naming that surface); the app never shows it here and the run asserts it stays absent (`neverShown`); the app deliberately shows it only in a tooltip or other label attribute (`viaAttribute` — a hover-revealed explanation is **not** a display, which is why the default is text-only); or it is composed into a larger run (`composed`). **`OUT_OF_SCOPE` is the one that must not quietly grow** — it is the countable statement of what a green run does not prove, so a namespace lands there only with a reason, never to make a failure go away. The guard answers **presence, not layout**: a collapsed or clipped element whose text still renders passes, and that question belongs to `ui-capture`
- `*.audit.test.ts` (`src/core`, `src/core/control`, `src/core/midi`, `src/models`) pin current behavior found during robustness audits (`AUDIT:` comments). When intentionally changing that behavior, rewrite the matching audit test as a set — do not delete it or leave it failing — so the pin tracks the fix
- **On the device link, a failed operation aborts the whole operation**; everything outside that link — MIDI feedback, port restore, file IO — keeps the softer rule of salvaging what can be salvaged, but never in silence. The call sites, the read paths that draw the line differently, and the **four permanent exceptions** are in architecture.md "Aborting on failure". Read that exception list before proposing one: all four are closed decisions
- Where a setting change makes the **device itself** switch what a value reflects, let it: subscribe or read, and do not model the switch in the app. Implement follow only where the device does not — and decide which of the two cases applies by **measuring** the change's effect on the *other* params and readouts, especially those downstream of the one being operated, before writing either. The two cases, why they must not be conflated, and the worked examples are in architecture.md "What the app models, and what it leaves to the unit"

- **Once a pull request merges, delete the local branch and any worktree that carried it.** GitHub deletes the remote branch itself; the local half is what gets left behind, and the worktree is the half that costs something — `reuseExistingServer` plus the E2E ports mean a forgotten checkout can hand a later run the bundle it built, so the run passes against code that is not the code under test. Remove it as `git worktree remove <path>` followed by `git branch -d <branch>`; deleting the directory instead leaves the worktree registered until someone remembers `git worktree prune`. **Two must be left alone**: a branch whose worktree still holds uncommitted work (`git status` before every removal — a merged branch does not mean a finished tree), and a **locked** worktree, whose lock means another session is inside it. `git branch --merged origin/main` also lists a branch that merely points at an ancestor and has no commits of its own — that is an unstarted branch, not a finished one

**Where the line is.** Observing the protocol from outside — sending a request and recording what comes back — is the permitted route, and it is what all of `src/core/control/` stands on. **Reading a distributed binary is not.** Do not analyze the bundled firmware image or an application binary, and do not propose it, even when a missing enum label, string table or value catalogue makes it the obvious next step; fill those from device observation instead (write, then confirm on the LCD; notify reverse-mapping; snapshot diff) and from the primary sources above. Data already obtained the other way stays where it is, but **its provenance is written in no document, public or private** — which means it has to be kept in a form justifiable from hardware evidence alone, and re-verified that way.
