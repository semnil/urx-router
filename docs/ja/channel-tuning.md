# チャンネル調整画面 (設計仕様)

> English: [../en/channel-tuning.md](../en/channel-tuning.md)

**状態: GATE / COMP / EQ / DUCKER 実装済み (DUCKER は 2026-08-08)。** 1 つの処理のパラメーターを、
その効果を映すメーターの隣に置くノード単位の画面の仕様。insert FX のダイナミクス系にもゲインリダクション
メーターがある ([対象範囲](#対象範囲)) ため、それが続くときも同じ画面形式になる。実装は
`src/ui/dyn-screen.ts` (共通ホスト) / `src/ui/dyn-gate.ts`・`src/ui/dyn-comp.ts`・`src/ui/dyn-eq.ts`・
`src/ui/dyn-ducker.ts` (処理ごとの差分) / `src/ui/dyn-chan.ts` (チャンネルストリップ 2 種が共有する束縛) /
`src/ui/dyn-plot.ts` (dB×dB の伝達プロット) / `src/core/eq-response.ts` (実測フィルターモデル) /
`src/core/meters.ts` (GR テーブルとデコード) / `src/style.css` (`.gt-*`)、カバレッジは
`e2e/dyntuning.spec.ts` と `e2e/eqoneknob.spec.ts`。

**ホストは 1 つで、どの処理を出すかは open のたびに選ぶ。**どれを開いても相手を置き換える。
インスタンスを 2 つ持つと同じ DOM を奪い合ううえ、ブローカーのメータースロットが 1 つしかない以上、
同時に開いても両方は流せない。

**ホストはどの処理を表示しているか知らない。** `DynProcessor` がそのノードに実際に何があるか
(フィールドとメーターレーン) を解決し、プラン内の自分の持ち分を読み書きし、ホストが提供する部品から
表示カラムを組む。この分担のおかげで「GR メーターを持たず、タップがステレオで、値が配列にあり、
セグメントバーが表示モードではなくバンドを選ぶ処理」をホストの特殊ケース無しに載せられた。

## 背景

これまで GATE の 5 パラメーターはインスペクタのスライダーだけで、効果を見る手段が無かった。
ゲインリダクションメーターは URX44V で同定済みだが、メーターモデルからは意図的に外していた —
`tapsFor` は CONSOLE のメーターポイントセレクタの契約でもあり、そこに載せるとリダクションが
ストリップのメーターとして選択可能になり、信号用の 3 色帯を持つ dBFS ラダーで描かれてしまう。

専用画面を作るに足る実機事実が 2 つある (以下は GATE の記述。COMP についての同じ 2 点は
[COMP](#comp) 節)。

1. **GATE の threshold の dB は PRE GATE メーターの dBFS と直接比較できる。** 実測: CH1 の
   ノイズフロア -54 dBFS が threshold -52 dB を下回り、ゲートは閉じたままで COMP に何も届かなかった。
   threshold とメーターは同一座標にある。
2. 関心のある 3 点がすべてメーターされている — PRE GATE (106) 入力 / GATE GR (107) /
   PRE COMP (108) 出力。いずれも同じ mono CH 軸。

1 がこの画面唯一のジェスチャーを正当化する: **threshold は入力メーター上のフェーダーキャップ**として
掴む。キャップの上で押せばその位置のまま掴み、スロットの上で押せばキャップがポインタへジャンプする
(押下点がキャップなら `e.target === cap` でキャップ側のリスナへ譲る)。**CONSOLE のフェーダーと同じ
押下の文法**で、根拠と実測は architecture.md「メインフェーダーの押下」が両方まとめて持つ。

## メーターに写るもの / 写らないもの

URX44V・System firmware 1.3.1.0・2026-07-29 実測。測定の全容は非公開のリファレンスノートにあり、
ここには設計を規定する部分だけを載せる。

| 事実 | 画面への帰結 |
| --- | --- |
| 通知周期は 100.0 ms 丁度。値が動かなくても毎ティック送られる | 10 Hz より速く描いても新しい情報は無い。フレーム間の補間も行わないので大半のフレームは何も運ばず、何も書かない — レーンの書込は量子化して不変ならスキップ、読み値のテキストは CONSOLE と同じく約 6 Hz に間引く |
| 1 フレームは**瞬時値**であって窓内の極値ではない | 100 ms 未満の事象は確率 (1 − 幅 / 100 ms) で見落とす |
| **レベル**メーター (106 / 108) は release 約 30 dB/s のピーク検波器 | 実機側で過渡を保持する。アプリ側の release は二重掛けになるので足さない。このレーンのピーク線は装飾 |
| **GR** メーター (107) は弾道特性を一切持たない — 適用されたゲインをそのまま出す | ピーク保持は、捕まえたゲート動作を読める唯一の手段。捕まらなかったものは復元できない |
| GR のアイドル値は **2 つ**あり、その使い分けは恣意的ではない: `0` は**処理ブロックが係合していない** (ゲート OFF / COMP OFF)、OVER センチネル `32767` は**係合していてリダクションが無い** | 両方を「リダクション無し」としてデコードし、どちらもクリップ扱いにしない。3 状態を切り分けられるのは、報告内容を変えずに係合だけを切れる COMP だけなので、そこで実測した |
| GR メーターは**リダクション量のみ**を運ぶ。COMP の makeup gain を 0 → +18 → 0 dB と振ると、下流のレベルタップはきっちり 18 dB 動くのに GR は -3.0 dB のまま動かず、OVER フレームも 0 だった | makeup をいくつにしてもレーンは読める。「makeup の分だけ圧縮が見えない」という但し書きは不要。逆 (正味ゲイン説) だとレーンが実用にならないので測った |

最後の 2 行の非対称は実使用でも見える — 入力の過渡が IN / OUT のレーンには出るのに対応する GR が
出ないことがある。GR のサンプルがそれを逃したためで、不具合ではなく実機の性質。

## レイアウト

Preferences / 本体設定と同じモーダルの枠 (`.consent-box` + `.prefs-box`・2 列)。
左列が表示、右列がコントロールと読み値。

**ただし枠の幅だけは共有していない。**`#dyn-screen-box` は `#console-host` と同じ規則に同居していて
(レーンの寸法トークンを共有するため)、そこから受け取る `flex: 1` が `.prefs-box` の
`width: min(920px, 100%)` に勝つ。結果、この画面だけが**ビューポート幅いっぱい** (窓 1500px で 1452px)
に広がり、地も `--panel` ではなく盤面の `--graph-bg` になる。同居から実際に必要なのは `--groove` だけで、
`--strip-w` / `--head-h` は継承されるが読まれない。

```text
┌ [CH 1] Gate ─────────────────────────────────────────────────┐
│ DISPLAY            [LADDER][CURVE] │ PARAMETERS               │
│ ┌────────────────────────────────┐ │ Threshold  ──●──  -50.0 dB
│ │   0 ─┐  ┌──┐ ┌──┐ ┌──┐         │ │ Range      ─●───  -56.0 dB
│ │ -10 ─┤  │  │ │▨▨│ │  │         │ │ Attack     ──●──   20.2 ms
│ │ -50 ─┤  │▬▬│ │▨▨│ │  │ ← キャップ│ Hold       ●────   15.3 ms
│ │ -72 ─┘  └──┘ └──┘ └──┘         │ │ Decay      ─●───  150.2 ms
```

### 表示モード

1 つのコントロール群に対する 2 モード。切替タブは**切り替える対象の直上**、セクションヘッダに置く。
両者は**排他であって重ね合わせではない** — それぞれが列全体を占めるので、相手のために縮む必要が無い。

- **LADDER** — 3 タップを -72..0 dB の 1 本の目盛列で並べる。dB に対して線形で、これは threshold の
  定義域そのものなので、キャップの位置と値が比例する。CONSOLE の目盛 (detent index 等間隔) を
  流用しないのはこのため。
- **CURVE** — 入出力の静特性。threshold がニー、range がその下の落差。**出力軸は入力軸と別**で、
  入力が -72..0 なのに対し出力は GR フロア (-128 dB) まで伸ばす。閉じた側の棚は threshold + range に
  位置し、range 定義域の大半でそれが -72 dB を下回る (工場値なら -50 + -56 = -106 dB) ため、床を
  共有していたときは -22 dB より深い range がすべて同じ線に張り付き、range が見えなかった。現在は
  -∞ のときだけ軸の床に達し、落差には range の値をラベルとして出す。

表示下の説明文は CURVE のときだけ出す。メーター上のフェーダーキャップは自明だが、曲線のニーを
ドラッグするのは自明ではない。

### GR レーン

**レベルレーンと同じ dB/px** で描き、目盛列 1 本が 3 本すべてに効くようにする — GR バーが -56 の
目盛に届いていれば 56 dB のリダクション。ローズ + 斜線ハッチで、信号用の緑/黄/赤は使わない。
リダクションはレベルではないため。不採用の 2 案は下記。

### 読み値

レーン 1 本につき 1 セルで、ライブ値と保持ピークを出す — GATE / COMP は 3 つ、DUCKER は 4 つ。
**1 フレームも受信していないタップは `—`** を出し、床値は出さない。GR の `0.0` は「処理が素通し
している」と偽ることになり、レベルの床値は測っていない無音を主張することになる。

3 列のグリッドに 4 枚だと 3 + 1 の折り返しになるので、レーンが 4 本の画面では 2 列へ切り替える
(`.gt-readouts.two`)。**幅は縮まない** — グリッドは親の列いっぱいに広がる — 不揃いな折り返しが
消えるだけである。

## COMP

1 段下流の同じ 3 タップ構成 — PRE COMP (108) 入力 / COMP GR (110) / PRE EQ (111) 出力 — で、
モードも同じ 2 つ。COMP で変わるのは以下。

**曲線は読むもので、ドラッグするものではない。** 実機の COMP 画面 (ユーザーガイド p.104) は伝達曲線に
T (threshold) / R (ratio) / G (gain) を置いて直接ドラッグさせる。同じものを作ってから**外した** —
1 枚のプロットに 3 つのグリップがあると、押下がどの値を指したのか決められず、外れた押下は下の
threshold ドラッグに落ちるため、**gain のグリップを押すと threshold が動いた**。編集経路は横の
スライダーで、曲線は「その設定が信号に何をしているか」に答える役。GATE の曲線は押下で threshold を
置く操作を残す — 編集できる値が 1 つなので誤読しようがない。

**リダクションには専用スケールを与える。** GATE のリダクションは目盛列いっぱいに動く (range が
-∞ まで届く) ので共有の目盛で読める。COMP は 54 dB の目盛のうち数 dB しか使わない — -8 dB でも
レーンの 15% で、見えるが読めない。そこで COMP のレーンは **0〜-24 dB の目盛を横に印字**し、
レベル 2 本から間隔を空けて置く。下記で GATE について不採用にした「共有目盛の下に**無印**の
第 2 スケールを置く」案とは別物。

**デバイスが駆動している間、その値はデバイスのもの。** 1-knob ON では threshold / ratio / gain を、
Auto Makeup ON では gain を実機が算出する。再計算はアドレス単位で announce される (実測) ので、
該当行は隠さず・こちらで再計算もせず、**タグ付き・減光・読取専用**のまま更新を映し続ける。

**1-knob 自身の 2 行は差し替えず、ロックする。** Auto Makeup は 1-knob ON 中は操作できず (UG)、
1-Knob Level は OFF 中は何も効かない — 常にどちらか一方だけが有効になる。EQ 画面が 1-knob の行を
そう扱うのと同じく、両方とも常に出したまま、該当しない側をロックする。**ロックは行の組み立て側で
判定せず、他のロックと同じく `rowStates` で宣言する**。差し替えるとパネルが動く: トグル行とスライダー行は
高さが違うため。さらに Auto Makeup が消えると 1-knob 行自身が 1 行分せり上がり、今クリックした
ポインタの下から外れる。どちらも `e2e/dyntuning.spec.ts` が固定している。

**ニーは描き、その幅は逆向きに 2 度実測した。** Soft / Medium / Hard の幅は非公開なので、描かなければ
セレクタが画面上で何も変えず、描けば根拠のない曲率を主張することになる。1 度目は**信号を固定して
threshold を上へ歩かせ、リダクションが消える点** (ニーの下端) を測り、対称モデルで倍にした:
0 / 16 / 40 dB。

2 度目は **threshold を固定して信号を 1 dB 刻みで通し** (曲線が読まれる向き)、幅の候補ごとに
当てはめた。検出器とメーターのオフセットはリグの性質でセレクタの性質ではないので、3 設定で共有した。
**Medium と Hard は変わらず、Soft だけが変わった** — 残差の最小は 51 dB で、倍化が出した 40 dB は
62% 悪い。定数は実測側を採る (残差では 50 / 52 / 54 dB を区別できないので、丸めた中央を採る)。

倍化が Medium で当たり Soft で外れたのは、**ニーが対称ではない**ため: 下端の到達 20 dB に対し
全幅 51 dB なら、threshold より上に約 31 dB ある。対称モデルに当てはめられるのは最良の対称近似だけで、
定数が持つのはそれである。したがって**非対称そのものと、端の間の曲率 (標準的な二次補間) は仮定のまま**で、
仮定であることを明記して使う。

**出力軸は 0 dBFS より上へ伸びる。** makeup gain が +18 dB まであるので、入力が -54〜0 なのに対し
出力は -54〜+18。GATE が逆向き (GR フロアまで) に伸ばすのと理由は同じで、パラメーターの効果を
軸内に収めるため。

**SSMCS では画面ごと存在しない。** モーフィングチャンネルストリップが COMP を置き換え、
`channelDynamics().comp` が null になり、起動元も両方描かれない。

## EQ

4-band PEQ。同じホストの上で 3 点だけ配置が違う — いずれも EQ にあってダイナミクス 2 種には無い理由による。

**表示モードの選択が無い。** ゲートは「メーター上のしきい値」と「伝達カーブ」のどちらかで読むもので、
両者は代替関係にある。EQ の周波数特性とレベルは代替ではない: カーブはスペクトルに何をしているかを、
メーターはその段が飽和していないかを答え、互いの代わりにならない。よって両方を同時に出し
(プロットが幅を取り、レーンラックはその横の別枠)、**タブの位置のセグメントバーはバンドを選ぶ**。
開くたび LOW に戻る — プロセッサーの読み方ではなくパラメーターへのカーソルだからで、
表示モードがプロセッサー単位で永続するのとは意図的に別扱いにしている。

**プロットの軸は周波数 × ゲイン**なので、ライブの点も押下による設定も無い。各バンドには頭文字を入れた
**マーカー**を置く — バンドがどこにあるかは知る必要があるため。グリップではなくマーカーなのは、1 枚の
プロットに 4 つのグリップでは押下がどの値を指したか決められないから (COMP 画面が 3 つで実証した)。
編集経路はスライダーのままである。**スケール外は枠外** — [スケール外は枠外](#スケール外は枠外) を参照
(この画面の全プロットに適用する規則)。HPF はコーナーから 1 オクターブで -18 dB の下限を超え、
マーカーも同じ扱い。各マーカーは自分のバンドの
周波数と、そこでの**合成**特性の位置に置く。こうすると常にカーブ上に乗る: pass 型には置くべきゲインが
無く、重なった 2 バンドはそのままでは読んでいる線から外れた位置にマーカーを置いてしまう。

**4 種類のノードに存在する** — mono CH / stereo CH / MIX / STEREO マスター。EQ が各チェーンの
別の位置に入るため、タップがここで変わる:

| ノード | 入力側 | 出力側 |
| --- | --- | --- |
| mono CH | PRE EQ (111) | PRE INS FX (112) |
| stereo CH | INPUT (101) = その pre-EQ 点 | PRE FADER (114) |
| MIX / STEREO マスター | PRE EQ (サム) | PRE FADER (post-EQ) |

stereo ノードのタップは L と R を持ち、ラックは 1 レーン内の**2 本のバー**として 1 つのキャプションの
下に描く — CONSOLE と同じ扱いで、理由も同じ: 半幅 2 本は「1 点をステレオで測っている」と読めるが、
2 レーンでは「信号経路上の 2 点」と読めてしまう。

**mono CH の HPF は意図的に描かない。** HPF は COMP より上流にあり、COMP のゲインは周波数成分で
変わるため、この段のカーブに素直に足せる量ではない。

### 周波数特性モデル

URX44V で実測: オシレーターを MIX 1 に入れ、EQ を挟む 2 メーターの差を読む。同じ手法を STEREO
マスターブロックで、さらにホストの USB 出力を信号源として stereo CH でも繰り返した。19 データセット・
108 点・最大偏差 **1.3 dB** — 1 dB 量子化のピークメーター 2 つの差を取る本手法の分解能そのもの。
フィルターは RBJ cookbook のバイクアッドだが、実測でしか出てこない補正が 3 つあり、いずれも
補正前は目に見えて誤ったカーブを描いていた:

| 形 | 補正 |
| --- | --- |
| peaking | **実機の Q はバイクアッドの Q の 2 倍**。「Q 1.00」+12 dB のベルは 1k/700/500/300 Hz で +12/+10/+7/+3 dB = バイクアッド Q 0.5 相当。数値をそのまま入れると全てのベルが実機の半分の幅になる |
| HPF / LPF | 2 次バターワース固定: 公称周波数でちょうど -3.0 dB、以降 12 dB/oct。**バンドの Q スロットは無視される** — Q 0.71 と Q 4.00 が完全一致し、コーナーに共振も無い。Q を効かせると存在しない +12 dB のピークを描く |
| shelving | S = 1 の形だが、**公称周波数はプラトーから 3 dB 下の点**で中点ではない: 1 kHz の +18 dB シェルフはその点で +15 dB、+18 dB に達するのは 4 kHz。よって設計周波数を解く。しかも二分探索の向きがゲインの符号で反転し、ブースト用の向きをカットに流用すると 4.2 dB ずれる |

モデルの妥当範囲を決める実測がさらに 2 件: **バンドは dB で加算される** (LOW シェルフ +12 と
HIGH-MID peaking -9 の同時測定が、個別測定の和とメーターの ±2 dB 以内で一致)、**レートによる差は
高域ベルで最大 2 dB** (44.1 … 176.4 kHz)。よって描画はプランのレートに関わらず 48 kHz 固定とし、
そう明記する。モデルは `src/core/eq-response.ts`、上の表はすべて `src/core/eq-response.test.ts` の
テストで、許容差 2.0 dB — 実測の分解能を残しつつ、3 つの補正のどれを外しても落ちる幅。

### パネルの高さは変わらない

Parameters セクションは**どれを選んでも Band / Type / Q / Freq / Gain の 5 行**で、4 バンド・
3 つの型すべてで同一。変わるのは「そのうちどれをデバイスが読むか」で、読まれない行は消えるのではなく
ロックして理由を表示する:

| ロックする行 | タグ | 理由 |
| --- | --- | --- |
| shelf / pass での Q | この型では無効 | Q を読むのは peaking のみ。pass については実測 — Q 0.71 と Q 4.00 が完全一致し、コーナーに共振も無い |
| pass での Gain | この型では無効 | pass 型に適用するゲインが無い |
| LOW MID / HIGH MID の Type | このバンドは固定 | mid 2 バンドは peaking 固定でデバイスが書込を拒否する (実測 response_code 400) ため、その 1 値だけを出す |

行が消えるとパネルの高さがその分変わり、下の行すべて (Close ボタンも) がポインタの下で動く。
4 バンド × 3 型すべてでモーダル高さが 1 値であることを実測し、`e2e/dyntuning.spec.ts` で固定した。

**1-knob ON 中はバンドのブロックごと消える**が、これも高さは変えない。そのとき編集中のバンドは
存在しない (4 バンドをデバイスが 1 つのレベルから計算する) ので、バンド選択を出すのは効果の無い選択肢を
提示することになる: 行は**その場に予約したまま非表示** (`visibility: hidden` = タブ順からも外れる。
コントロール自体も disabled)、バンドバーは見出しの横で不活性、Parameters 見出しからバンド名が外れ、
プロットのマーカーも「選択中」を描かない。予約領域には**その値の持ち主を示す 1 行**を置く — 見出しの下が
5 行分の空白では描画不具合に見えるうえ、行を隠すと「この数値はデバイスのもの」と分かる唯一の場所が
消えるため。消さずに予約するのが高さを保つ手段で、行はタグも (見えないまま) 保持する — タグピルは
行を高くするので、落とすと 5 行で 3px 縮み、見出しのピルでさらに 3px 縮む (実測)。

### 1-knob とデバイスの持ち分

1-knob はバンドのパラメーターの上に独立したセクションとして置く。下の行が誰のものかを決めるのが
1-knob だからだ。Type と Level は 1-knob OFF でも**ロックして出す** — 隠すとトグルごとに
セクションが 2 行縮み、その下の全てが動く。実機はその行をバンドの Type セレクタに差し替えるが、
この画面は Parameters に専用の Type 行を持つので差し替える相手が無い。ロックの根拠は実機の 2 点:
1-knob OFF 中に書いた TYPE は無効で、しかも OFF→ON 遷移が TYPE を Intensity・LEVEL を 50 に戻す —
編集可能にすると実機が捨てる値を提示することになる。実機は行を隠して到達不能にし、この画面は
ロックして到達不能にしたうえで値を見せる。

1-knob ON 中、4 バンドの行はすべてデバイスのものになる (1 つのレベルから再計算する)。読み取り専用で
見せるのではなく**画面から外す** (上記) — 誰も操作できない数値の並びはノイズであり、そもそも選択中の
バンドが無い。残るのは特性カーブで、デバイスの計算はそこで読める: ライブ同期中は後述の refetch が
実機値に追従させ、同期していないときはプランが最後に持っていたカーブである。

1-knob の Type は**どのインスタンスでも 3 択** (Intensity / Vocal / Loudness・実測)。カタログは
以前 2 つのサブセットを持っていたが、両方とも誤りだった (レベルの初期化を拒否と誤読した経緯は
param のノート側に記録)。

### 96 kHz 超

176.4 / 192 kHz では stereo CH の EQ はアプリがロックしているだけではない: 500 Hz を -13 dB
落とす 1 kHz HPF が両レートで素通りすることを実測した (param は保持され読み戻せる)。行は
device-driven ではなくレート固有の文言でロックし、特性は「効いているように見える」まま残さず沈めて描く。

## DUCKER

**開いたノード自身を調整しない唯一の画面。** GATE / COMP / EQ はチャンネルの中にあるが、ducker は
ステレオチャンネルにぶら下がる独立ノードで、そのしきい値が見ているのは**別の場所から来る信号**である。
以下の違いはすべてそこから出る。

- **開く対象は ducker ノード**。そのノードのインスペクタ節か、CONSOLE では親ストリップの開くチップから。
  チップが親にあるのは、吊り下げノードが自分のストリップを持たないため。渡す id は ducker のもの。
- **タイトルは母体チャンネルを名乗る**。ducker ノードのラベルは `Ducker` で、DUCKER という見出しの隣では
  何も名指さないので、この記述子だけ `nodeLabel` フックに `CH 5/6` を返す。
- **表示バーは無い。** Envelope とレーンを同時に出すので (EQ のプロットとレーンと同じ) 選ぶものが無く、
  `DynProcessor.bar` を置かない。ボタンの無いセグメントの上に見出しを載せると、存在しない選択を名乗る。
- **MIDI の id を返さない。** コントロールカタログは ducker の `duckerOn` しか持たないので、
  4 本のスライダーに id を返すと存在しないコントロールへラーンを構えることになる。

### 3 スロットに 4 レーン

| レーン | アドレス | 備考 |
| --- | --- | --- |
| Key | キーソース自身のタップ — チャンネルなら **Rec Point に追従**し (下記)、バスなら POST | **ソースの幅によらず 1 本。**しきい値キャップを持つ |
| Pre Ducker | `116 : 2p, 2p+1` | 母体チャンネルの post-fader。ステレオなので 2 本 |
| Post | `120 : 2p, 2p+1` | 母体の出力。**リダクションはこのスロットに描く** |
| Ducker GR | `119 : p` | 専用の列を持たない (`DynLane.sameSlot`)。読み値タイルは自前 |

**キーレーンがどのタップを読むか。** ブロックダイアグラムで決まる: `Rec Point` セレクタの出力そのものが
`CH OUT` と印字された信号で、`DUCKER 1-4 SOURCE` はその `CH 1-4 OUT` / `CH 5/6-11/12 OUT` を入力に取る。
したがってチャンネルのキーは**そのチャンネルの現在の Rec Point** で読まれる — モノなら PRE GATE /
PRE COMP / PRE EQ / PRE INS FX / PRE FADER、ステレオなら PRE EQ か PRE FADER で、ステレオの PRE EQ は
INPUT メーターに当たる (ステレオストリップは EQ が鎖の先頭にあるため)。いずれもソース自身のフェーダーと
ダッカーより手前なので、ソースのフェーダーを動かしてもトリガーは動かない。バスのキーはバス自身の OUT
(出力インサート FX の後)。2026-08-13 まではチャンネルソースを一律 PRE FADER で読んでいたため、
Rec Point を他へ変えたソースでは、検出器が聞いていない信号を — 間の段が加えた分だけずれた状態で —
表示していた。

**キーレーンが 1 本である理由。** URX44V 実測: 実機はステレオキーの両側を検出前に**加算する** —
相関のあるペアは片側単体より **6.02 dB** 上に来る (パワー和の 3 dB でも、大きい側採用の 0 dB でもない)。
キャップは自分と同じ座標の定規にしか乗れず、加算した表示に対してはしきい値の発動点が **-3.0 ±0.5 dB**
の定数に収まる一方、`max(L,R)` に対しては 7 dB ばらつく。よってレーンは検出器が読む値へ畳み
(`duckerKeyDb`)、キャップはそのまま乗る。-3.0 dB は**サイン波の peak→RMS** で、メーターがピーク読み・
検出器が RMS 読みであることの現れである。

**キャップは較正済みのマーカーではなく目安である。** -3.0 がサイン波の値であって定数ではないためで、
片側にトーン・もう片側にプリアンプノイズを入れて測ると、発動点は加算表示より **8.5 dB** 下だった
(3.5 ではない) — ノイズ的なキーの peak→RMS は 3 dB ではなく 10 dB 前後だからである。
つまりプログラム素材では、キャップが示すより**低いバー読みで発動する**。補正は当てない: アプリは
キーのクレストファクタを測っていないし、-3.0 は選べる 2 つの定数のうち良い方 (無補正だとトーン側が
3 dB ずれる) というだけである。

**リダクションを POST に重ねる理由。** リダクションは 0 から下へ、レベルは床から上へ伸びるので、
衝突条件は `レベル + |リダクション| > 0 dBFS`。入力側のレーンではこれが常態で、工場出荷のレンジ
-56 dB ではブロックが定規の 93% を覆いバーの頂点が埋もれる。出力レーンは
`出力 = 入力 - |リダクション|` なので衝突は入力が 0 dBFS に達したときだけで、
**両者の隙間がその信号のヘッドルームそのもの**になる。

代償は、重ねたリダクションが専用目盛りを持てないこと。共有定規に乗るが、その定規はしきい値の定義域
(0..-60 dB) のままなので、**60 dB より深いリダクションは頭打ち**になる。レンジは -70 dB まで届くので
到達しうる。他のレーンとキャップを、実際に使う定義域に載せ続けることとの交換である。

### Envelope

x は対数の時間で、両方の設定を 1 本で張る (attack は 0.092 ms から、decay は 5 s まで)。y はゲインで、
上が 0 dB、下はレンジの下限 -70 dB。3 本の直線 — `attack` でレンジまで下り、保持し、`decay` で戻る。

**直線で、ライブ要素を持たない。** release は指数的な近づき方をするが、末端が GR メーターの 1 dB 量子に
支配されるため単一の時定数を当てはめていない。主張は**到達時間**だけで、2 点間の直線はそれを述べる。
リダクションが専用列を持っていた頃はここにライブの破線を引いていたが、数ピクセル右の POST バーに
ブロックとして出るようになった時点で、破線は同じ量の 2 つ目の表示になった — しかも時間軸はライブの
読みに位置を与えないので弱い方だった。COMP が点を残すのは、あちらのプロットが入力→出力を写していて
ライブのレベルに実位置があるため。

## スケール外は枠外

すべてのプロットはカーブを**真値**で描き、**ホストがプロット領域でクリップする**。軸にクランプすると
下端 (上端) に横棒を引くことになり、そのプロセッサーが持たない特性を描いてしまう:

| プロット | クランプが起こしていたこと |
| --- | --- |
| EQ | HPF はコーナーから 1 オクターブで -18 dB の下限を超えるため、カーブが枠の下端に沿って伸びていた |
| GATE | 閉じたシェルフは threshold + range にあり、**range が有限のまま -144 dB まで届く** (threshold -72 … -56 × 最深 range)。-128 の軸にクランプすると **range = -∞ と同じ絵**になる — 閉じていないゲートが閉じているように見える |
| マーカー | 床に張り付けると、その周波数で特性が到達しないレベルを指し示すことになる |
| COMP | 何も起きていなかった — -54 … +18 の軸が応答全体を含む (makeup は加算のみ・膝の補正は減算のみ)。推測ではなく `src/ui/dyn-plot.test.ts` が両端で検査する |

この分離は各 descriptor が覚える約束ではなく**構造**である: `drawAxes` はクリップ無しで呼ばれ
(目盛りラベルは `geo.pad` が確保する余白に描く)、`drawCurve` はクリップ内で呼ばれる。新しい
プロセッサーのプロットは存在するだけでこの規則を継承する。

意図的な例外は 2 つ。いずれも該当箇所に明記する:

- **値の注記はクランプしてよい**。注記は値そのものではなく値を説明するものだから — GATE の range
  ラベルは、指し示すシェルフが枠外へ出ても枠の下端で読めるまま残る。注記へ引く引出線はカーブの一部
  なのでクランプしない
- **GATE の range = -∞ は軸の床に固定する**。そこでは床が -∞ の表現である (GR メーター自身の床であり、
  ラベルも "-∞" と出す)。これはクランプではなく表現で、有限値側が枠外へ抜けるようになった今、
  有限値と -∞ を区別可能にしているのはこの固定である

## 対象範囲

GATE / COMP は MONO IN の機能なので、その画面は CH1-4 (URX22 は CH1-2) にのみ存在する。EQ は
4-band PEQ があるところすべて — SSMCS 以外の全 mono CH・全 stereo CH・各 MIX Bus・STEREO マスター。
ノードは**開いた場所で固定**され、画面内に切替は無い。

購読アドレス集合はそれに**追随して固定されるわけではない**。DUCKER の KEY レーンはソース自身の
Rec Point で読む (上記) ため、画面を開いたまま Rec Point が変わると — グラフのインスペクタからでも、
アンドゥでも、実機の前面パネルからでも — 画面は開いたノードのままアドレスだけが移る。したがって画面は
rebind のたびにアドレス集合を比較し、違えば購読し直す。これが無いと KEY のバーは画面を閉じて開き直すまで
`—` のままになる。

残る確定済み GR メーターは DUCKER (119) と insert FX (132 入力・133 出力)。**軸が GATE / COMP の
mono CH index とは違う** — DUCKER はステレオペア、出力 insert FX はエフェクトのバンド — ので、
追加するときは `grAddr` の軸を継承せず、それぞれの実測軸を持ち込む必要がある。

### この画面は最前面ではない

プラン読み込み (ドロップ / 開く / 最近使用) は調整画面を開いたまま起こりうるので、`loadPlan` が画面を
refresh する: 画面はクロージャ経由でプランを読むので値自体は既に新しく、足りなかったのは再描画の指示
だけだった。refresh は束縛も再解決するので、新しいプランにそのノードや処理が無い画面は、無くなった対象へ
書き込む前に自ら閉じる。

各スクリムは同一 z-index を共有していたため**ドキュメント順が優劣を決めており**、**読み込みレポートが
調整画面の背面**に回っていた — そのドロップについてのレポートが読めない状態である。**ドロップ告知**も
背面だったが、こちらは別の理由で知っておく価値がある: `z-index: 120` を書いた規則が `.consent-scrim` の
`100` より**前**にあり、同一詳細度では後の規則が勝つため、告知は**一度も 120 になっていなかった** —
「モーダルより前面に出る」というコメントは書かれた時点から誤りだった。両方を `style.css` の 1 つの
明示的な順序表にまとめ、`.consent-scrim` より後に置いてカスケードが黙って打ち消せないようにした
(メニュー 40 / コントロール付随ポップオーバー 60 / ツールモーダル 100 / ドロップ告知 120 /
決定ゲート 130)。consent・読み込みレポート・レート選択はいずれも「何が開いていても答えられなければ
ならない問い」なので最前面に置く。

### ジェスチャの途中でウィンドウを奪われたとき

この画面が持つ 3 つのドラッグ — スレッショルドのキャップ、プロット、値の行 — は、ウィンドウがフォーカスを
失った時点で終了する。どのエンジンも終わらせてくれないためで、ボタンを押したまま OS の前面を奪われると
`blur` は発火し、**`pointercancel` は発火せず**、ポインタキャプチャも保持される (2026-08-14 に Chromium と
実機の WKWebView で実測)。これが無かった間は、アプリ切替を跨いで押し続けた操作が、別アプリが前面のまま
プランと実機へ書き込み続けていた。`history.ts` も同じ `blur` で押下を終端するので、残りの移動は**新しい
Undo エントリ**に落ちていた。

キャップとプロットはビュー自身のジェスチャなので、ビューが持っているものを落とせば終わる。**値の行は
ネイティブの `<input type="range">` で、ドラッグを所有しているのはエンジン**であり、3 点で別の問題になる
(いずれも実測):

| 処置 | 結果 |
| --- | --- |
| リスナを外す | 効果なし。駆動しているのはエンジンで、アプリは `input` を写しているだけ |
| `pointer-events: none` | 効果なし。両エンジンで書き続けた |
| DOM から外して戻す | ドラッグは終わるが、**フォーカスが戻ると再開する** — 実機で押したまま戻ると行が再開した |
| `disabled` | 終わり、かつその間は再取得されない |

したがって、ウィンドウを失った行は `disabled` にし、**押下が終わるか、ウィンドウが戻るまで**その状態で
保つ — `pointerup` / `pointercancel` / ボタン無しを報告する `pointermove` (ウィンドウが聞き逃した離しの
受け皿) / アプリのフォーカス復帰。blur で 1 度切るだけでは足りなかった: **detach の処置**では、押したまま
フォーカスが戻った時点で行が再開し、それがその処置を差し戻した理由である。`disabled` は再開しない
(両エンジンで実測、実機でも手作業で確認) ので復帰を解除条件にでき、しかもこれは**必ず届く唯一の信号**
である — ウィンドウの外で失われた離しは数えられず、タッチの識別番号は再利用されないため、これが無いと
行が不活性のまま解除されずに残りうる。`disabled` はフォーカスを落とすので、
戻すときに復元する。画面上の代償は無い — このスライダーは `appearance: none` でトラックもつまみも自前
描画のため、エンジン側に減光する対象が無く、enabled と disabled で撮った行は両エンジンともバイト一致する。

**これは調整画面の規則ではなくアプリ全体の規則**で、本体は `ui/dom.ts` の `holdInertOnBlur`。`wheelStep`
と同じ理由で、**すべての `<input type="range">`** がここを通る — 調整画面の値行、inspector の 2 つの
スライダー生成器、共有の `sliderRow`、本体設定の Brightness。この画面が足すのは、保留した refresh が
どこで着地するかである。blur はこの画面自身のジェスチャを終わらせるが `grabbed` は解除しない — 押下は
まだ続いており、その下での再構築は押したままのポインタに生きたコントロールを渡す (hold が防いでいる状態
そのもの)。したがって保留は blur を越えて続き、refresh は**最初に届いた解放**で走る — この画面自身の
`pointerup` / `pointercancel` か、アプリ全体で最後の hold の解除 (ウィンドウの復帰もこれを生むので、
押したまま戻ると再構築はそこで起きる)。先に走った側が `grabbed` を解除し、残りは解除済みを見て何もしない。
hold 側はジェスチャ開始時の行ではなく**今画面にある行**を引く — 再構築が既に置き換えている可能性があるため。作り直された行は再構築が与えた `disabled` を保つ (COMP の 1-Knob が
入ると threshold / ratio / gain / knee はデバイス駆動になりロックされる) し、フォーカスも戻さない —
このアプリのどの再構築もフォーカスを復元しないため。

inspector も同じ信号で保留する。IME の変換中と `<select>` のピッカー展開中を待つ既存のゲートに相乗り
させている。名指しする価値があるのは、hold だけが自前の終了イベントを持たないためである — 変換は終わり、
ピッカーは閉じるが、hold が終わるのはパネルが観測しないポインタの解放なので、ゲートは hold の管理側を
直接購読する。

## メーター購読の所有権

ブローカーのメーター購読スロットは**プロセス全体で 1 つ** — `vd_meters_subscribe` は既存の登録を
置き換え、`vd_meters_unsubscribe` はアドレスを取らない。置き換えは無音で、CONSOLE は自己回復
しないため、断りなく奪うと CONSOLE のバーが床で凍りついたまま残る (無音と区別が付かない)。

これを塞ぐ機構が 2 つある。

- **購読自体への世代スタンプ** (`subscribeMeters`)。呼び出し側が持つ解除ハンドルは購読単位に見えて
  実はそうではないので、古いハンドルが**今の所有者**をキャンセルしうる (CONSOLE の登録が飛行中に
  画面がスロットを取った場合、画面が自分の購読往復より速く閉じた場合の 2 経路)。解除は自分の世代が
  現行のときだけ効き、古い登録から遅れて届いたフレームは新しい所有者の store に書かず捨てる。
- **明示的な貸し借り** (`Console.releaseMeters()` / `regainMeters()`・`metersLent` でガード)。画面は
  購読前にスロットを取り、閉じるときに返す。貸出中は CONSOLE の `render()` が再購読しない — render は
  「CONSOLE が見られているか」と無関係な理由 (デバイス追従のリコンサイル等) でも起きるため。
  `regainMeters` は CONSOLE がライブかつ表示中でなければ no-op で、GRAPH のインスペクタから開いた
  場合は CONSOLE が非表示のことがあり、その場合は次の `show()` が走らせる `render()` が張り直す。

ライブ状態は `setLiveUi` から両サーフェスへ届く。セッションの出入りが必ず通る funnel で、
「CONSOLE が購読し、その後に画面が奪い返す」という**順序が効く**ため、各呼び出し側ではなくここに 1 度だけ書く。

GR のピーク畳み込みは `MeterStore` からではなく**購読コールバック側**で行う。store はアドレス単位で
last-write-win なので、1 バッチに同一アドレスの複数フレームが入ると最後の 1 つしか残らない。

## 起動元

| 場所 | コントロール |
| --- | --- |
| GRAPH インスペクタの GATE / COMP / EQ セクション | ON/OFF トグルの下の全幅ボタン。ラベルは中央、末端にカレット |
| CONSOLE のストリップ | そのストリップが持つ処理チップそれぞれの横の細いチップ。字は `▸` |

**どちらも右を指し、言っていることも同じだが、描き方は意図的に違う** — それぞれが乗っている面の
一族に属させている。インスペクタ側は 2 行上のセクション見出しの開閉矢印と同じ作り (グリフではなく
隣接 2 辺のボーダー) で、その矢印と並べて測ると 180 画素に対して 174 画素 = 同じ重さの同じ記号に
読める。CONSOLE 側がグリフなのは、隣がグリフだから。**両者を互いに合わせると、合わせた先の面が
壊れる。**

**3 セクションとも ON トグル + 起動ボタンだけに縮めた。**インスペクタにスライダーの写しを残すのは
単なる重複ではない — `dynFieldSlider` は render 時の params スナップショットを読み、値変更で
再レンダしないので、画面側で値を動かした後にそのスライダーをドラッグすると古い値が書き戻る。

CONSOLE 側を既存チップのジェスチャーにせず独立チップにしたのは、`wireActivate` が click と
Space/Enter を `detail` ガード無しで束ねているため、ダブルクリックが処理を 2 回トグルして 2 回
書き込むから。加えてダブルクリックはこのビューのフェーダー / ノブで工場出荷値リセットに使われている。
各ペアが 2 列グリッドの 1 行を埋める — ヘッド高さが一律なのは SENDS ラック / フェーダー / メーターを
揃えるためで、その整列は保たれる。

EQ の起動チップは mono CH で処理チップを 4 行目に入れるため、ヘッドがその分を負担する必要がある:
旧 252px で実測したヘッド内寸は 254px (height が content-box なので padding 対と下ボーダーが加算される)、
チップ 1 行は 24px で、Hi-Z チップを持つ CH3 / CH4 の余白は 0.9px しか無かった。**手計測に頼るのは
やめた** — どのストリップのヘッドも自分の内容を溢れさせないことを E2E が assert する
(`e2e/console.spec.ts`)。`--head-h` は 276px とし、チップを持たないストリップも含めて全ストリップの
フェーダー領域が 24px 縮む。起動チップは、レートで EQ が強制 OFF のとき (隣のトグルも読み取り専用)
と SSMCS モードのとき (EQ チップはモーフィングストリップのもので、開く 4-band PEQ が無い) には出さない。

## MIDI 割り当て

この画面の全パラメータは外部 MIDI コントローラーから操作できる。カタログもラーンのジェスチャも CONSOLE
ストリップと同一である (`ui/midi-learn.ts`。カタログは `core/midi/controls.ts`、周辺設計は architecture.md)。

- **対象は行のコントロールセル。** ラーン中は破線リング、アーム中は実線のパルス、割当済みは琥珀のドット —
  コンソールと同じ 3 状態なので、ストリップのコントロールと画面のコントロールが同じに読める。押下は
  **capture フェーズ**で取るため、アームするクリックでスライダーがドラッグを始めない。ホイールも同じ理由で
  ゲートする。
- **ロックされている行は提供しない。** 理由は行が既に印字しているものと同じ — レートによりステレオ CH の EQ
  が無効、1-knob が値を実機に渡している、フィルタタイプがその値を読まない。列挙セレクタ (COMP の knee、EQ の
  フィルタタイプと 1-knob タイプ) も対象外で、カタログは連続値とトグルのみを持つ。
- **バンドはそのバンドに束縛される。** id のスコープは `@eq.low` … `@eq.high` であり、「バーが選んでいるバンド」
  ではない。マッピングはこの画面を閉じていても効かねばならず、バーは開くたび LOW に戻るからである。値キーに
  対する id を答えるのは `DynProcessor.controlId` — ホストはどのプロセッサを表示しているか知らないままで、
  コントロールを持たないキーには `null` が返る。
- **グリッドはフィールド表のもの。** MIDI 値もドラッグしたスライダーも先に「位置」を解決する
  (`control/translate.ts` の `dynToPos` / `dynFromPos`) ので、同じグリッドの別の値に落ちることはない。
- **ラーン中でも画面は開く。** `▸` オープナー自身は割当対象ではないため、アームのガードを素通りする。

## デバイスが無いとき

どのビルドでも、どの状態でも開く。パラメーターはプランの値なのでデバイス無し (ブラウザビルド含む) でも
完全に編集でき、メーターは床、読み値は `—`。ロックも非表示も行わない — ここには**編集**にデスクトップ
シェルを要するものが無く、**観測**にだけ要るため。

## 実装メモ

`DynScreen` が「どの処理を開いているかに依存しないもの」をすべて持つ — モーダル・レーンラック・
メーターフィードとピーク・スロットの貸借・キャンバス のライフサイクル・バー選択の永続化。残りは
`DynProcessor` が渡す: そのノードが何を持つか (`bind`)・プラン内の自分の持ち分 (`read` / `patch`)・
バー・行とその状態・プロット。DUCKER や insert FX を足すのは descriptor 1 枚を書くことで、画面を
もう 1 つ作ることではない。

置き場所はその分担から決まる:

| モジュール | 持つもの |
| --- | --- |
| `src/ui/dyn-screen.ts` | ホスト: モーダル・レーン・メーターフィード・キャンバス・`DynField[]` からの行 |
| `src/ui/dyn-chan.ts` | GATE / COMP が「MONO IN のチャンネルストリップ処理」として共有するもの — 束縛・サブオブジェクトのプラン I/O・表示バー |
| `src/ui/dyn-plot.ts` | その 2 つが描く dB×dB 伝達プロット: `transferPlot()` が軸 3 定数とヒントから 5 つのフックを返す |
| `src/ui/dyn-{gate,comp,eq}.ts` | descriptor — 差分だけ |
| `src/core/control/translate.ts` | 全フィールドテーブル (EQ の `eqBandFields` を含む)。実測の fine グリッドやレンジが UI ファイルではなく他と並ぶ |
| `src/core/eq-response.ts` | 実測フィルターモデル。デバイスのスイープに対してテスト済み |

EQ の予約領域の 1 行は、ホストのフックではなく descriptor が自分の `rows.tail` に入れる DOM。
絶対配置 (高さ 0 コスト) + `pointer-events: none` — 背後の Close ボタンへの押下を飲み込むラベルは、
ラベルが無いより悪い。

画面は独自の部品ではなく共有レシピで組む。行と見出しは `settingsRow` / `settingsSection`、モードタブは
`.udk-banks`、-∞ の読み値は `setLevelText`、スライダーは `wheelStep`、実機の fine グリッドを持つ唯一の
値には `fineTag` / `optInFine`、メーターの shade / peak は CONSOLE の登録済み `--lvl` / `--pk` ルール。
GR レーンが足すのは反転 (上から下がり、覆いではなくバーそのもの) とハッチだけ。`formatDyn`・range の
-∞ ノッチ (`dynValueText`)・どのフィールドが fine グリッドを持つかは、いずれもそれらを定義する
フィールドテーブルの隣 = `translate.ts` に置く。画面とインスペクタで値の表記や刻みが食い違わない
ようにするため。

表示モードは**処理ごとに**保存する (`urx-dyn-display`・処理をキーにしたレコード)。GATE と COMP は
読み方が違い、この選択は「処理の読み方」であって機種ごとの写像ではないので、メーターポイントと違い
機種スコープにはしない。

曲線は**静的レイヤーのキャッシュ + ライブの点**に分けて描く。点以外はパラメーター / サイズ /
テーマにしか依存しないため。キャンバス のサイズは open と refresh で、テーマトークンは render で読む —
どちらも強制読み取りで、そのフレーム自身の DOM 書込直後のフレームループに置くと同期レイアウトを誘発する。
**他の行の持ち分を変える行 (1-knob / Auto Makeup) はコントロール列を組み直す**が、スライダーは組み直さない
— ドラッグ中に組み直すとポインタキャプチャが外れる。

## 不採用案 (新しい根拠なしに蒸し返さない)

| 不採用 | 理由 |
| --- | --- |
| 曲線の出力軸に入力軸の -72 dB 床を共有 | 工場 threshold では range 定義域の 70% で棚が目盛外。range を -30 → -56 dB に動かしても描画は 0% しか動かない |
| 出力軸を対数圧縮 | dB は既に対数単位で、さらに圧縮すると range が居る深い側がちょうど潰れる。同じ -30 → -56 の移動で実測 8.5% (軸を伸ばすだけの案は 20%) |
| 縦軸を出力でなくゲイン (出力 − 入力) に | 実測 4 案で最も読みやすく (35.6%)、軸がメーター 107 の報告値と一致する。ただし伝達曲線ではなくゲイン曲線になり、1:1 の領域が 0 dB の水平線に潰れてプラグインの慣用句から外れる |
| 出力軸を棚に合わせて自動伸縮 | 棚は常に見えるが、range をドラッグすると線ではなく目盛の数字が動くので、何が変わったのか読めない |
| GR を `monoTaps` の 8 番目として追加 | `tapsFor` は CONSOLE のメーターポイントセレクタの契約。GR が信号用 3 色帯の dBFS ラダーで選択可能になる。固定テストも 2 本壊れる |
| GR を 0〜-30 dB 固定フルスケールに | 工場値 range (-56 dB) で振り切れる。ゲートが仕事をしている間だけ情報を失う |
| GR を range 追従フルスケールに | 振り切れは直るが、共有の目盛列の下で GR だけ別スケールになる。隣の目盛で読めそうに見えて読めない |
| GR に `readingTap` / `decodeMeterDb` を流用 | `readingTap` は OVER センチネルで `over` を立てる。GR では「ON かつ開」を意味するので、素通し中のゲートがクリップ点灯する |
| OUT を IN + GR で導出 | 3 タップは実機が独立に計測する。1 フレーム内で最大の入力と最深のリダクションは同時刻ではなく、足すと出力が数十 dB 低く出た |
| インスペクタにも 5 スライダーを残す | `dynFieldSlider` は render 時の params スナップショットを読み、値変更で再レンダしない。画面側で threshold を動かした後、古い位置のスライダーをドラッグすると古い値が書き戻る |
| 履歴スクロール / レベル分布の表示 | 試作して不採用。ゲートの性質上どちらも読み取りづらい。両案が扱えていた問い (フレーズ間でゲートが落ちるか、ノイズフロアとソースの分離量) が対象外であることを記録として残す |
| 画面内の CH セレクタ | 切替のたびにアドレス集合を再登録することになる。そもそも CH 単位のコントロールから CH 単位で開く |
| CONSOLE の GATE チップへのジェスチャー (ダブルクリック / 右クリック) | ダブルクリックはこのビューの工場出荷値リセットで、`wireActivate` に `detail` ガードが無い。右クリックはアプリ全体で未使用だが macOS の Ctrl+click でネイティブメニューと衝突する |
| レベルレーンにアプリ側 release を足す | 実機のメーターが既に約 30 dB/s で減衰する。二重掛けになる |
| COMP GR を正味ゲイン (リダクション + makeup) と読む | makeup +18 dB の CH でアイドル OVER が出たことからこちらが有力に見えたが、そう読むと makeup を少し上げただけでレーンが役に立たなくなる。実測で否定 — makeup は下流タップを動かし GR は動かさない |
| COMP の GR レーンをレベルと同じ dB/px に | GATE のリダクションは目盛いっぱいに動くが、COMP は数 dB。動かないレーンに見える |
| COMP の曲線からニーを省く | セレクタが画面上で何も変えなくなる (GATE の出力軸で 1 度払った失敗と同型)。幅を測るほうが、フィードバックの無いコントロールを出荷するより安かった |
| COMP 用に画面インスタンスをもう 1 つ持つ | 同じモーダルホストと同じ 1 つのメータースロットを奪い合う。処理は open のたびに選ぶ方式にした |
| 実機同様に COMP 曲線上へ T / R / G のグリップを置く | 作ってから外した。グリップを外した押下が下の threshold ドラッグに落ちるため **gain のグリップを押すと threshold が動く**。加えて描画は枠内にクランプ、当たり判定はクランプ前の座標で、軸の端では両者が約 13px ずれていた。2 つの欠陥の下にあるのは「1 枚のプロットの 3 グリップでは押下がどの値を指したか決められない」こと |
| DUCKER のリダクションを専用列にする | 列と専用目盛りのぶんの幅を食う。プロットに回せば、窓 1440px でレーン 333 → 235px、Envelope 312 → 410px |
| DUCKER のリダクションを KEY / PRE DUCKER に重ねる | 実測で否定。リダクションは 0 から下、レベルは床から上なので衝突条件は `レベル + \|リダクション\| > 0 dBFS`。入力側のレーンではこれが常態で、工場出荷のレンジではブロックが定規の 93% を覆いバーの頂点が読めない |
| Envelope にライブ表示を載せる | リダクションが数ピクセル右の POST バーにブロックとして出るようになった時点で、同じ量の 2 つ目の表示になった。時間軸はライブの読みに位置を与えないので、上下に動くだけだった |
| DUCKER に Ladder / Envelope のトグルを置く | EQ と同じく両方を同時に出すので選ぶものが無い。見出しが存在しない選択を名乗ることになる |
| 重ねたリダクションのために DUCKER の定規を -70 dB へ広げる | レンジの深い端を買う代わりに全レーンの分解能を薄める。しかも下 10 dB は KEY にとって死んだ領域 (しきい値がそこへ行けない) |
| 注記が切れるので文言を短くする | 器の側が欠陥だった。1 行確保のとき、出荷済みの COMP と EQ の注記は窓幅 約 1150px 以下 (日本語は約 1300px 以下) で既に折り返していた。短くしても次に切れる幅が動くだけ |

## 承知の上のトレードオフ / 注意点

- **ピーク保持時間 (1.2 秒) は純粋に UI 側の裁量**。実機に前例が無い — レベルメーターはハードウェアで
  保持し、GR は一切保持しない。
- **ピーク線の意味がレーンごとに違う** — GR では本質的、レベルレーンでは装飾。差異の明示より
  見た目の一貫性を採った。
- **100 ms 未満のゲート動作は GR に映らず**、どんな UI でも復元できない。この画面はそれを主張しない。
  定常状態のレベル関係を読み、それに対して threshold を置くための画面であって、attack / hold / decay を
  追い込むための画面ではない。
- **微調整モードは COMP Gain だけ。** 実機のパネルノブ押し込み微調整は GATE の全パラメーターで
  **無効**、COMP でも **Gain (makeup) のみ有効 (0.1 dB)** と検証済み。したがって FINE 表示が出るのは
  その 1 行だけで、これはクラス規則ではなく個別実測の結果。

## 編集 → デバイスのデータ経路

インスペクタと同一。`onUpdateNodeParams` がパッチを `plan.nodeParams[id]` の該当する持ち分にマージし
`markChanged()` を呼ぶ。これがプランの dirty フラグ・ライブ同期のスケジュール・MIDI フィードバックを
まとめて担う。BAL モードで STEREO リンクされたペアでは、他のノードパラメーターと同様にグループも
相方へミラーされる。値がどこにあるかは descriptor の担当: GATE / COMP は 1 つのサブオブジェクト、
EQ は `eqBands[i]` と `eqOneKnob` に分かれ、パッチをキーで振り分ける。

**1-knob の書き込みは読み込みとして返ってくる。** `ParamSpec.sideEffect` は 2 つの修復を区別する。
デバイスが動かした値の**所有者が違う**ためだ:

| フラグ | デバイスが動かしたもの | 修復 |
| --- | --- | --- |
| `"converge"` | プランが**著作**する値 (COMP/EQ type 変更で CH ストリップのトグルがクリアされる) | 押し戻す = 書込スコープに対する converge ラウンド |
| `"refetch"` | プランが**鏡映し**ているだけの値 (EQ 1-knob が 4 バンドを再計算する) | 所有ノードを読み直し、スナップショットをそこから採り直す |

EQ 1-knob の 3 param は refetch 側。converge すると操作者の古い手動カーブをデバイス自身の計算結果に
上書きしてしまい、しかも再計算は誰も通知しない: notify 登録はアドレス列挙で、1-knob ON 中は
バンドのアドレスがその集合から外れる (プランが emit をやめる) から。そこで `live.ts` は
device-follow の scoped 経路と同じ device→plan の逆変換を呼び、その後スナップショットを採り直す —
これが無いと、読み込んだ値がすべて次の diff で「未送信の編集」として書き戻される。実機側で同じノブを
回した場合は既にこの経路を通っていた。これは**自分の書き込みに対する同じ修復**である。また refetch は
1 ノード 1 回の読みで converge ラウンドではないので、フラッシュ窓が収束の完了まで塞がれることはない —
1-knob レベルのドラッグがポインタ停止まで待たされていた原因がこれだった。

ただし**無料ではなく**、その費用は測れる。実機は書込を ACK した時点ではまだその値に答えず
(`docs/ja/architecture.md`「書込は ACK された時点ではまだ読めない」)、refetch はまさにその同じ ms に発行
される。そのため読み出しはフラッシュの内側で書込を待ち合わせ、1-knob レベルのドラッグの 1 サイクルは
「書込 + 待ち + 読み」になる (通常のパラメーターは「書込」のみ)。レースハーネスで同一ジェスチャを比較すると
**フラッシュ窓 1 回あたり 423/428/432 ms、待ちが無かった時点では 322/334 ms** だった (`t2c-shape-change`。
このケースのドラッグを 10 ステップから 16 ステップへ伸ばしたのはこのためで、短いドラッグには窓が複数
入らなくなった)。同ケースの対照アーム — `sideEffect` を持たない LOW band gain のドラッグ — は 205/200 ms で
変化がない。**実機に再計算させるドラッグだけが払う。**

**そこからの推定ではなく、実機で測った** (2026-08-02・URX44V System V1.3.1.0・修正に診断計装を載せた使い捨て
