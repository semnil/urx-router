# チャンネル調整画面 (設計仕様)

> English: [../en/channel-tuning.md](../en/channel-tuning.md)

**状態: GATE / COMP / EQ / DUCKER と SSMCS バンク実装済み。** 1 つの処理のパラメーターを、
その効果を映すメーターの隣に置くノード単位の画面の仕様。insert FX のダイナミクス系にもゲインリダクション
メーターがある ([対象範囲](#対象範囲))。実装は
`src/ui/dyn-screen.ts` (共通ホスト) / `src/ui/dyn-gate.ts`・`src/ui/dyn-comp.ts`・`src/ui/dyn-eq.ts`・
`src/ui/dyn-ducker.ts`・`src/ui/dyn-ssmcs.ts` (処理ごとの差分) / `src/ui/dyn-registry.ts` (どれが存在するか) /
`src/ui/dyn-chan.ts` (チャンネルストリップ 2 種が共有する束縛) /
`src/ui/dyn-plot.ts` (dB×dB の伝達プロット) / `src/ui/dyn-freq-plot.ts` (EQ 2 種が共有する周波数プロット) /
`src/core/eq-response.ts` (実測フィルターモデル) /
`src/core/meters.ts` (GR テーブルとデコード) / `src/style.css` (`.gt-*`)、カバレッジは
`e2e/dyntuning.spec.ts`・`e2e/ssmcs.spec.ts`・`e2e/eqoneknob.spec.ts`。

**ホストは 1 つで、どの処理を出すかは open のたびに選ぶ。**どれを開いても相手を置き換える。
インスタンスを 2 つ持つと同じ DOM を奪い合ううえ、セッションが持つメーター購読が 1 つしかない以上、
同時に開いても両方は流せない。

**ホストはどの処理を表示しているか知らない。** `DynProcessor` がそのノードに実際に何があるか
(フィールドとメーターレーン) を解決し、プラン内の自分の持ち分を読み書きし、ホストが提供する部品から
表示カラムを組む。この分担のおかげで「GR メーターを持たず、タップがステレオで、値が配列にあり、
バンドは自分のプロット上のマーカーを押して選ぶ処理」をホストの特殊ケース無しに載せられた。

## 背景

これまで GATE の 5 パラメーターはインスペクタのスライダーだけで、効果を見る手段が無かった。
ゲインリダクションメーターは URX44V で同定済みだが、メーターモデルからは意図的に外していた —
`tapsFor` は CONSOLE のメーターポイントセレクタの契約でもあり、そこに載せるとリダクションが
ストリップのメーターとして選択可能になり、信号用の 3 色帯を持つ dBFS ラダーで描かれてしまう。

専用画面を作るに足る実機事実が 2 つある (以下は GATE の記述。COMP についての同じ 2 点は
[COMP](#comp) 節)。

1. **GATE の threshold の dB は PRE GATE メーターの dBFS と直接比較できる。** 実測: CH1 の
   ノイズフロア -54 dBFS が threshold -52 dB を下回り、ゲートは閉じたままで COMP に何も届かなかった。
   threshold とメーターは同一座標にある。
2. 関心のある 3 点がすべてメーターされている — PRE GATE (106) 入力 / GATE GR (107) /
   PRE COMP (108) 出力。いずれも同じ mono CH 軸。

1 がこの画面唯一のジェスチャーを正当化する: **threshold は入力メーター上のフェーダーキャップ**として
掴む。キャップの上で押せばその位置のまま掴み、スロットの上で押せばキャップがポインタへジャンプする
(押下点がキャップなら `e.target === cap` でキャップ側のリスナへ譲る)。**CONSOLE のフェーダーと同じ
押下の文法**で、根拠と実測は architecture.md「メインフェーダーの押下」が両方まとめて持つ。

## メーターに写るもの / 写らないもの

URX44V・System firmware 1.3.1.0・2026-07-29 実測。測定の全容は非公開のリファレンスノートにあり、
ここには設計を規定する部分だけを載せる。

| 事実 | 画面への帰結 |
| --- | --- |
| 通知周期は 100.0 ms 丁度。値が動かなくても毎ティック送られる | 10 Hz より速く描いても新しい情報は無い。フレーム間の補間も行わないので大半のフレームは何も運ばず、何も書かない — レーンの書込は量子化して不変ならスキップ、読み値のテキストは CONSOLE と同じく約 6 Hz に間引く |
| 1 フレームは**瞬時値**であって窓内の極値ではない | 100 ms 未満の事象は確率 (1 − 幅 / 100 ms) で見落とす |
| **レベル**メーター (106 / 108) は release 約 30 dB/s のピーク検波器 | 実機側で過渡を保持する。アプリ側の release は二重掛けになるので足さない。このレーンのピーク線は装飾 |
| **GR** メーター (107) は弾道特性を一切持たない — 適用されたゲインをそのまま出す | ピーク保持は、捕まえたゲート動作を読める唯一の手段。捕まらなかったものは復元できない |
| GR のアイドル値は **2 つ**あり、その使い分けは恣意的ではない: `0` は**処理ブロックが係合していない** (ゲート OFF / COMP OFF)、OVER センチネル `32767` は**係合していてリダクションが無い** | 両方を「リダクション無し」としてデコードし、どちらもクリップ扱いにしない。3 状態を切り分けられるのは、報告内容を変えずに係合だけを切れる COMP だけなので、そこで実測した |
| GR メーターは**リダクション量のみ**を運ぶ。COMP の makeup gain を 0 → +18 → 0 dB と振ると、下流のレベルタップはきっちり 18 dB 動くのに GR は -3.0 dB のまま動かず、OVER フレームも 0 だった | makeup をいくつにしてもレーンは読める。「makeup の分だけ圧縮が見えない」という但し書きは不要。逆 (正味ゲイン説) だとレーンが実用にならないので測った |

最後の 2 行の非対称は実使用でも見える — 入力の過渡が IN / OUT のレーンには出るのに対応する GR が
出ないことがある。GR のサンプルがそれを逃したためで、不具合ではなく実機の性質。

## レイアウト

Preferences / 本体設定と同じモーダルの枠 (`.consent-box` + `.prefs-box`・2 列)。
左列が表示、右列がコントロールと読み値。

**ただし枠の幅だけは共有していない。**`#dyn-screen-box` は `#console-host` と同じ規則に同居していて
(レーンの寸法トークンを共有するため)、そこから受け取る `flex: 1` が `.prefs-box` の
`width: min(920px, 100%)` に勝つ。結果、この画面だけが**ビューポート幅いっぱい** (窓 1500px で 1452px)
に広がり、地も `--panel` ではなく盤面の `--graph-bg` になる。同居から実際に必要なのは `--groove` だけで、
`--strip-w` / `--head-h` は継承されるが読まれない。

```text
┌ [CH 1] Gate ─────────────────────────────────────────────────┐
│ ┌────────────────────────┐ ┌──────┐│ PARAMETERS               │
│ │  transfer curve        │ │0 ┌──┐││ Threshold  ──●──  -50.0 dB
│ │                     ／ │ │  │  │││ Range      ─●───  -56.0 dB
│ │                   ／   │ │-50──││← キャップ   ──●──   20.2 ms
│ │  _______________／     │ │  │▬▬│││ Hold       ●────   15.3 ms
│ │                        │ │  │▨▨│││ Decay      ─●───  150.2 ms
│ │                        │ │-72└──┘│                          │
│ └────────────────────────┘ │IN  OUT││ METER                   │
│  曲線のニーがしきい値                │ [PRE GATE][PRE COMP][GATE GR]
│                                    │                   [Close]│
└──────────────────────────────────────────────────────────────┘
```

**コントロール列は半分ではなく 400px で止める。**`.prefs-grid` は器を真ん中で割るが、調整画面の
コントロールはそれを必要としない — パラメータ行は固定幅のスライダーとラベルで、読み値タイルは
与えられた列いっぱいに広がるだけ。列を `max-content` にして測ると、実際に要求される最大は **392px**
(EN の 4-band EQ と SSMCS EQ 面。ロックされた Q 行のタグピルが決めている)、他は 297〜350px で、
英日とも同じ。規則は `#dyn-screen-box` にスコープしてあるので、環境設定と本体設定は半分のまま。
表示列へ戻るのは 149px で、4-band EQ のプロットは 369 → 518px、SSMCS MAIN 面のキャンバスは
547 → 696px になる。

どの画面も図とラックを横に並べてこの幅を使うようになったので、「広げても黒が広がるだけ」の画面はもう無い。
幅が厳しいのは SSMCS バンクの 960px 最小ウィンドウだけで、それは[レーンの定規](#レーンの定規とそこに無いもの)にある。

**最終列は 4px の余白を持つ。フォーカスリングの場所。**`.prefs-grid` は `overflow-y: auto` を持つので
横軸も `auto` に計算され、横スクロールしなくても横方向にクリップする。右列のコントロールはコンテンツ端に
ぴったり接していたため、リングが箱の外に出て 1 つも描かれなかった。4px は最も広いリングの量 — select の
アウトラインが 2px + offset 2px で 4px、白リング系のハローも 4px、通常ボタンは 3px。**グリッドではなく列に
置く**: グリッドに置くと図の列からも同じだけ削られ、960px でそこは 4px 減るだけで折り返しに変わる。

### 表示

**図とレーンラックは常に両方出る。**かつては LADDER / CURVE のバーで選ぶ排他の 2 モードで、そのバーは
単一プロセッサの画面から全て消えた。消せた理由はリダクションが出力列へ移ったこと — 3 列だったラックが
2 列になり、図の横に入るようになった。選ばせるものが無くなった、つまり EQ と DUCKER が最初から取っていた
配置になった。

**図**は入出力の静特性。threshold がニー、range がその下の落差。**出力軸は入力軸と別**で、入力が -72..0 な
のに対し出力は GR フロア (-128 dB) まで伸ばす。閉じた側の棚は threshold + range に位置し、range 定義域の
大半でそれが -72 dB を下回る (工場値なら -50 + -56 = -106 dB) ため、床を共有していたときは -22 dB より深い
range がすべて同じ線に張り付き、range が見えなかった。現在は -∞ のときだけ軸の床に達し、落差には range の
値をラベルとして出す。

**ラック**はタップをプロセッサ自身の定義域で 1 本の目盛列に並べる (GATE なら -72..0 dB)。dB に対して線形で、
これは threshold の定義域そのものなのでキャップの位置と値が比例する。CONSOLE の目盛 (detent index 等間隔) を
流用しないのはこのため。

**どの表示も同じ高さから始まる。**バーを持たない画面はその行を予約する — 同じビルダーを通すので、確保される
量は実際に描かれるバーの高さそのものになる。予約が無いと、それらの画面だけ黒い表示部がバー 1 行分上に来た。

表示下の説明文は常に出す (図が常にあるため)。枠は中身によらず固定高 — **全画面 3 行** — なので
長い文は折り返されずに**切られる**。文字列は出荷前に 960px ウィンドウで実測する。ただし
**折り返しを決めるのはフォントで、それは走らせる機のものであってこの機のものではない** — 判定は CI 側の
`pnpm test:e2e:app dyntuning` が持つ。

**バーが残るのは 1 箇所だけ** — SSMCS バンクで、そこでは表示モードではなくフェイスを選ぶ。

### レーンのキャプション

**バー下のキャプションは位置 (`Input` / `Output`) を名乗り、その下の読み値タイルがタップを名乗る。**
以前は両方がタップ名で、どちらもプロセッサのどちら端かを言っていなかった。実機のダイナミクス画面も同じ対を
メーターしており、ユーザーガイドはこの項目を `Input/output meter` /「入出力メーター」、半分ずつを名指しする
ときは `Input meter` /「インプットメーター」・`Output meter` /「アウトプットメーター」と書く (D0)。全言語で
英字のまま — キャプション行は狭く、ここを訳すと幅を食うため。

**SSMCS バンクだけは例外で、タップ名を出す。**位置ラベルが成立するのは 1 画面 = 1 プロセッサで「入力」が
一意に決まるからで、あのバンクは 1 つのタイトルの裏に複数のエフェクトが並び、面ごとに 1 本のストリップの
重なり合う点をメーターする。PRE EQ は COMP 面ではコンプの出力、EQ 面では EQ の入力、サイドチェイン面では
そのどちらでもない — その面の出力はディテクター入力で、そもそもメーターに出ていない。

レーン自身の名前は読み値タイルが出すので失われるものは無く、余裕のある面へ移っただけ。以前バーの下に
並んでいたメーター ID (`108`, `111` 等) は画面から外した — あれはプロトコルのアドレスであって信号ではない。

### GR レーン

ローズ + 斜線ハッチで、信号用の緑/黄/赤は使わない。リダクションはレベルではないため。もうどの画面でも
専用の列は持たない — 規則とその算術は[リダクションの描き方](#リダクションの描き方--全画面で-1-つの規則)。
不採用の 2 案は下記。

### METER

レーン 1 本につき 1 セルで、ライブ値と保持ピークを出す。**1 フレームも受信していないタップは `—`**
を出し、床値は出さない。GR の `0.0` は「処理が素通ししている」と偽ることになり、レベルの床値は
測っていない無音を主張することになる。

**見出しはユーザーガイドがこの項目を呼ぶ語で、訳す。** ガイドは両言語で名指ししており —
「チャンネルメーター」/ "Channel meter"、「ステレオメーター」/ "stereo meter"、
「LEVELメーター」/ "LEVEL meter" (D0) — 英語では `METER`、日本語では「メーター」。実機に METER と
出る画面は存在しないため字面を合わせる相手が無く、ガイドの修飾語は落とす — タイルが持つ全タップを
1 語で覆えるのに対し、LEVEL / チャンネルは面ごとに選び直す必要が出て、どの面でも幅を食う。

**CONSOLE のライブセルだけは日本語モードでも `METER` のままで、これが例外。** あのキャプションが
乗るストリップはラベルが全て英語で (区切りラベルは縦書きで組むため全角字が列幅を変える)、その中で
1 語だけ和文になると誤りに見える。CONSOLE 側の 2 つのキャプションは `fixed()`、この見出しは `tr()`
で、こちらは全体が日本語のモーダルの中にある。

タイルは画面が指定しない限り 3 列。3 列に 4 枚だと 3 + 1 の不揃いな折り返しになり、しかも 4 枚に
必要な幅より広いので、レーンが 4 本の画面は 2 列 (2 × 2 のブロック) か 4 列 (1 段) を要求する。
バンクの中では見た目の問題ではなく効いてくる — SSMCS のサイドチェイン面が 4 列を取るのは、タイルが 2 段に
なると 64px 増え、3 面を揃えている高さを超えるため。**指定しても幅は縮まない** — グリッドは親の
列いっぱいに広がる — 決まるのは折り返しである。

## COMP

1 段下流の同じ 3 タップ構成 — PRE COMP (108) 入力 / COMP GR (110) / PRE EQ (111) 出力 — で、
表示も同じ。COMP で変わるのは以下。

**曲線は読むもので、ドラッグするものではない。** 実機の COMP 画面 (ユーザーガイド p.104) は伝達曲線に
T (threshold) / R (ratio) / G (gain) を置いて直接ドラッグさせる。同じものを作ってから**外した** —
1 枚のプロットに 3 つのグリップがあると、押下がどの値を指したのか決められず、外れた押下は下の
threshold ドラッグに落ちるため、**gain のグリップを押すと threshold が動いた**。編集経路は横の
スライダーで、曲線は「その設定が信号に何をしているか」に答える役。GATE の曲線は押下で threshold を
置く操作を残す — 編集できる値が 1 つなので誤読しようがない。

**リダクションには専用スケールを与える。** GATE のリダクションは目盛列いっぱいに動く (range が
-∞ まで届く) ので共有の目盛で読める。COMP は 54 dB の目盛のうち数 dB しか使わない — -8 dB でも
レーンの 15% で、見えるが読めない。そこで COMP のレーンは **0〜-24 dB の目盛を横に印字**し、
レベル 2 本から間隔を空けて置く。下記で GATE について不採用にした「共有目盛の下に**無印**の
第 2 スケールを置く」案とは別物。

**デバイスが駆動している間、その値はデバイスのもの。** 1-knob ON では threshold / ratio / gain / knee が
実機のものになる (前 3 つは 1 つのレベルから算出し、knee はノブが入った時点で実機が決める)。
Auto Makeup ON では gain を実機が算出する。再計算はアドレス単位で announce される (実測) ので、
該当行は隠さず・こちらで再計算もせず、**タグ付き・減光・読取専用**のまま更新を映し続ける。

**1-knob 自身の 2 行は差し替えず、ロックする。** Auto Makeup は 1-knob ON 中は操作できず (UG)、
1-Knob Level は OFF 中は何も効かない — 常にどちらか一方だけが有効になる。EQ 画面が 1-knob の行を
そう扱うのと同じく、両方とも常に出したまま、該当しない側をロックする。**ロックは行の組み立て側で
判定せず、他のロックと同じく `rowStates` で宣言する**。差し替えるとパネルが動く: トグル行とスライダー行は
高さが違うため。さらに Auto Makeup が消えると 1-knob 行自身が 1 行分せり上がり、今クリックした
ポインタの下から外れる。どちらも `e2e/dyntuning.spec.ts` が固定している。

**ニーは描き、その幅は逆向きに 2 度実測した。** Soft / Medium / Hard の幅は非公開なので、描かなければ
セレクタが画面上で何も変えず、描けば根拠のない曲率を主張することになる。1 度目は**信号を固定して
threshold を上へ歩かせ、リダクションが消える点** (ニーの下端) を測り、対称モデルで倍にした:
0 / 16 / 40 dB。

2 度目は **threshold を固定して信号を 1 dB 刻みで通し** (曲線が読まれる向き)、幅の候補ごとに
当てはめた。検出器とメーターのオフセットはリグの性質でセレクタの性質ではないので、3 設定で共有した。
**Medium と Hard は変わらず、Soft だけが変わった** — 残差の最小は 51 dB で、倍化が出した 40 dB は
62% 悪い。定数は実測側を採る (残差では 50 / 52 / 54 dB を区別できないので、丸めた中央を採る)。

倍化が Medium で当たり Soft で外れたのは、**ニーが対称ではない**ため: 下端の到達 20 dB に対し
全幅 51 dB なら、threshold より上に約 31 dB ある。対称モデルに当てはめられるのは最良の対称近似だけで、
定数が持つのはそれである。したがって**非対称そのものと、端の間の曲率 (標準的な二次補間) は仮定のまま**で、
仮定であることを明記して使う。

**出力軸は 0 dBFS より上へ伸びる。** makeup gain が +18 dB まであるので、入力が -54〜0 なのに対し
出力は -54〜+18。GATE が逆向き (GR フロアまで) に伸ばすのと理由は同じで、パラメーターの効果を
軸内に収めるため。

**SSMCS では画面ごと存在しない。** モーフィングチャンネルストリップが COMP を置き換え、
`channelDynamics().comp` が null になり、起動元も両方描かれない。

## EQ

4-band PEQ。同じホストの上で 3 点だけ配置が違う — いずれも EQ にあってダイナミクス 2 種には無い理由による。

**周波数特性とレベルを同時に出す** — プロットが幅を取り、レーンラックはその横の別枠。カーブはスペクトルに
何をしているかを、メーターはその段が飽和していないかを答え、互いの代わりにならない。この画面が最初に
この配置を取り、今はこれが唯一の配置になった。

**バンドはプロット上のマーカーを押して選ぶ。**バンドバーは無い。1 マーカー = 1 バンドなので押下が一意に
決まる — 4 つ並んだボタンが離れた場所でやっていたことで、しかも次に編集するバンドは操作者が既に見ている
場所にある。選択は開くたび LOW に戻る — プロセッサーの読み方ではなくパラメーターへのカーソルだから。

当たり判定と描画は同じ関数を通す。マーカーはバンド周波数と、その下の合成カーブの**両方**で動くので、
同じ数値から別々に書いた当たり判定はどちらかが動いた瞬間にずれる。判定域はピル + 全周 7px — ピルは
高さ 13〜15px しかなくポインタ target には足りず、プロット上に他の押下対象が無い。

**プロットはフォーカス停止点で、矢印キーでバンドが動く。**マーカーはセグメントバーを置き換えたもので、
セグメントバーはキーボードで操作できる。canvas は停止点 1 つなので、左右で 1 つずつ・Home / End で両端へ。
選択すると列が再構築されるため、フォーカスはバーと同じ経路で新しい canvas へ戻す。1-knob が ON のときは
選べるものが無いので、canvas はタブ順から抜ける — 何もしない停止点として残らないように。

**プロットの軸は周波数 × ゲイン**なので、ライブの点は無い。各バンドには頭文字を入れた
**マーカー**を置く。グリップではなくマーカーなのは、グリップならドラッグがバンドのどの値を動かしたかを
言えねばならず、1 枚のプロットに 4 つでは決められないから (COMP 画面が 3 つで実証した)。編集経路は
スライダーのままで、マーカーがするのは選択だけ。**スケール外は枠外** — [スケール外は枠外](#スケール外は枠外) を参照
(この画面の全プロットに適用する規則)。HPF はコーナーから 1 オクターブで -18 dB の下限を超え、
マーカーも同じ扱い。各マーカーは自分のバンドの
周波数と、そこでの**合成**特性の位置に置く。こうすると常にカーブ上に乗る: pass 型には置くべきゲインが
無く、重なった 2 バンドはそのままでは読んでいる線から外れた位置にマーカーを置いてしまう。

**4 種類のノードに存在する** — mono CH / stereo CH / MIX / STEREO マスター。EQ が各チェーンの
別の位置に入るため、タップがここで変わる:

| ノード | 入力側 | 出力側 |
| --- | --- | --- |
| mono CH | PRE EQ (111) | PRE INS FX (112) |
| stereo CH | INPUT (101) = その pre-EQ 点 | PRE FADER (114) |
| MIX / STEREO マスター | PRE EQ (サム) | PRE FADER (post-EQ) |

stereo ノードのタップは L と R を持ち、ラックは 1 レーン内の**2 本のバー**として 1 つのキャプションの
下に描く — CONSOLE と同じ扱いで、理由も同じ: 半幅 2 本は「1 点をステレオで測っている」と読めるが、
2 レーンでは「信号経路上の 2 点」と読めてしまう。

**mono CH の HPF は意図的に描かない。** HPF は COMP より上流にあり、COMP のゲインは周波数成分で
変わるため、この段のカーブに素直に足せる量ではない。

### 周波数特性モデル

URX44V で実測: オシレーターを MIX 1 に入れ、EQ を挟む 2 メーターの差を読む。同じ手法を STEREO
マスターブロックで、さらにホストの USB 出力を信号源として stereo CH でも繰り返した。19 データセット・
108 点・最大偏差 **1.3 dB** — 1 dB 量子化のピークメーター 2 つの差を取る本手法の分解能そのもの。
フィルターは RBJ cookbook のバイクアッドだが、実測でしか出てこない補正が 3 つあり、いずれも
補正前は目に見えて誤ったカーブを描いていた:

| 形 | 補正 |
| --- | --- |
| peaking | **実機の Q はバイクアッドの Q の 2 倍**。「Q 1.00」+12 dB のベルは 1k/700/500/300 Hz で +12/+10/+7/+3 dB = バイクアッド Q 0.5 相当。数値をそのまま入れると全てのベルが実機の半分の幅になる |
| HPF / LPF | 2 次バターワース固定: 公称周波数でちょうど -3.0 dB、以降 12 dB/oct。**バンドの Q スロットは無視される** — Q 0.71 と Q 4.00 が完全一致し、コーナーに共振も無い。Q を効かせると存在しない +12 dB のピークを描く |
| shelving | S = 1 の形だが、**公称周波数はプラトーから 3 dB 下の点**で中点ではない: 1 kHz の +18 dB シェルフはその点で +15 dB、+18 dB に達するのは 4 kHz。よって設計周波数を解く。しかも二分探索の向きがゲインの符号で反転し、ブースト用の向きをカットに流用すると 4.2 dB ずれる |

モデルの妥当範囲を決める実測がさらに 2 件: **バンドは dB で加算される** (LOW シェルフ +12 と
HIGH-MID peaking -9 の同時測定が、個別測定の和とメーターの ±2 dB 以内で一致)、**レートによる差は
高域ベルで最大 2 dB** (44.1 … 176.4 kHz)。よって描画はプランのレートに関わらず 48 kHz 固定とし、
そう明記する。モデルは `src/core/eq-response.ts`、上の表はすべて `src/core/eq-response.test.ts` の
テストで、許容差 2.0 dB — 実測の分解能を残しつつ、3 つの補正のどれを外しても落ちる幅。

### パネルの高さは変わらない

Parameters セクションは**どれを選んでも Band / Type / Q / Freq / Gain の 5 行**で、4 バンド・
3 つの型すべてで同一。変わるのは「そのうちどれをデバイスが読むか」で、読まれない行は消えるのではなく
ロックして理由を表示する:

| ロックする行 | タグ | 理由 |
| --- | --- | --- |
| shelf / pass での Q | この型では無効 | Q を読むのは peaking のみ。pass については実測 — Q 0.71 と Q 4.00 が完全一致し、コーナーに共振も無い |
| pass での Gain | この型では無効 | pass 型に適用するゲインが無い |
| LOW MID / HIGH MID の Type | このバンドは固定 | mid 2 バンドは peaking 固定でデバイスが書込を拒否する (実測 response_code 400) ため、その 1 値だけを出す |

行が消えるとパネルの高さがその分変わり、下の行すべて (Close ボタンも) がポインタの下で動く。
4 バンド × 3 型すべてでモーダル高さが 1 値であることを実測し、`e2e/dyntuning.spec.ts` で固定した。

**1-knob ON 中はバンドのブロックごと消える**が、これも高さは変えない。そのとき編集中のバンドは
存在しない (4 バンドをデバイスが 1 つのレベルから計算する) ので、バンド選択を出すのは効果の無い選択肢を
提示することになる: 行は**その場に予約したまま非表示** (`visibility: hidden` = タブ順からも外れる。
コントロール自体も disabled)、プロットはバンドの押下を受け付けなくなり (タブ順からも外れ)、
Parameters 見出しからバンド名が外れ、プロットのマーカーも「選択中」を描かない。予約領域には**その値の持ち主を示す 1 行**を置く — 見出しの下が
5 行分の空白では描画不具合に見えるうえ、行を隠すと「この数値はデバイスのもの」と分かる唯一の場所が
消えるため。消さずに予約するのが高さを保つ手段で、行はタグも (見えないまま) 保持する — タグピルは
行を高くするので、落とすと 5 行で 3px 縮み、見出しのピルでさらに 3px 縮む (実測)。

### 1-knob とデバイスの持ち分

1-knob はバンドのパラメーターの上に独立したセクションとして置く。下の行が誰のものかを決めるのが
1-knob だからだ。Type と Level は 1-knob OFF でも**ロックして出す** — 隠すとトグルごとに
セクションが 2 行縮み、その下の全てが動く。実機はその行をバンドの Type セレクタに差し替えるが、
この画面は Parameters に専用の Type 行を持つので差し替える相手が無い。ロックの根拠は実機の 2 点:
1-knob OFF 中に書いた TYPE は無効で、しかも OFF→ON 遷移が TYPE を Intensity・LEVEL を 50 に戻す —
編集可能にすると実機が捨てる値を提示することになる。実機は行を隠して到達不能にし、この画面は
ロックして到達不能にしたうえで値を見せる。

1-knob ON 中、4 バンドの行はすべてデバイスのものになる (1 つのレベルから再計算する)。読み取り専用で
見せるのではなく**画面から外す** (上記) — 誰も操作できない数値の並びはノイズであり、そもそも選択中の
バンドが無い。残るのは特性カーブで、デバイスの計算はそこで読める: ライブ同期中は後述の refetch が
実機値に追従させ、同期していないときはプランが最後に持っていたカーブである。

1-knob の Type は**どのインスタンスでも 3 択** (Intensity / Vocal / Loudness・実測)。カタログは
以前 2 つのサブセットを持っていたが、両方とも誤りだった (レベルの初期化を拒否と誤読した経緯は
param のノート側に記録)。

### 96 kHz 超

176.4 / 192 kHz では stereo CH の EQ はアプリがロックしているだけではない: 500 Hz を -13 dB
落とす 1 kHz HPF が両レートで素通りすることを実測した (param は保持され読み戻せる)。行は
device-driven ではなくレート固有の文言でロックし、特性は「効いているように見える」まま残さず沈めて描く。

## DUCKER

**開いたノード自身を調整しない唯一の画面。** GATE / COMP / EQ はチャンネルの中にあるが、ducker は
ステレオチャンネルにぶら下がる独立ノードで、そのしきい値が見ているのは**別の場所から来る信号**である。
以下の違いはすべてそこから出る。

- **開く対象は ducker ノード**。そのノードのインスペクタ節か、CONSOLE では親ストリップの開くチップから。
  チップが親にあるのは、吊り下げノードが自分のストリップを持たないため。渡す id は ducker のもの。
- **タイトルは母体チャンネルを名乗る**。ducker ノードのラベルは `Ducker` で、DUCKER という見出しの隣では
  何も名指さないので、この記述子だけ `nodeLabel` フックに `CH 5/6` を返す。
- **表示バーは無い。** Envelope とレーンを同時に出すので (EQ のプロットとレーンと同じ) 選ぶものが無く、
  `DynProcessor.bar` を置かない。ボタンの無いセグメントの上に見出しを載せると、存在しない選択を名乗る。
- **MIDI の id を返さない。** コントロールカタログは ducker の `duckerOn` しか持たないので、
  4 本のスライダーに id を返すと存在しないコントロールへラーンを構えることになる。

### 3 スロットに 4 レーン

| レーン | アドレス | 備考 |
| --- | --- | --- |
| Key | キーソース自身のタップ — チャンネルなら **Rec Point に追従**し (下記)、バスなら POST | **ソースの幅によらず 1 本。**しきい値キャップを持つ |
| Pre Ducker | `116 : 2p, 2p+1` | 母体チャンネルの post-fader。ステレオなので 2 本 |
| Post | `120 : 2p, 2p+1` | 母体の出力。**リダクションはこのスロットに描く** |
| Ducker GR | `119 : p` | 専用の列を持たない (`DynLane.sameSlot`)。読み値タイルは自前 |

**キーレーンがどのタップを読むか。** ブロックダイアグラムで決まる: `Rec Point` セレクタの出力そのものが
`CH OUT` と印字された信号で、`DUCKER 1-4 SOURCE` はその `CH 1-4 OUT` / `CH 5/6-11/12 OUT` を入力に取る。
したがってチャンネルのキーは**そのチャンネルの現在の Rec Point** で読まれる — モノなら PRE GATE /
PRE COMP / PRE EQ / PRE INS FX / PRE FADER、ステレオなら PRE EQ か PRE FADER で、ステレオの PRE EQ は
INPUT メーターに当たる (ステレオストリップは EQ が鎖の先頭にあるため)。いずれもソース自身のフェーダーと
ダッカーより手前なので、ソースのフェーダーを動かしてもトリガーは動かない。バスのキーはバス自身の OUT
(出力インサート FX の後)。2026-08-13 まではチャンネルソースを一律 PRE FADER で読んでいたため、
Rec Point を他へ変えたソースでは、検出器が聞いていない信号を — 間の段が加えた分だけずれた状態で —
表示していた。

**キーレーンが 1 本である理由。** URX44V 実測: 実機はステレオキーの両側を検出前に**加算する** —
相関のあるペアは片側単体より **6.02 dB** 上に来る (パワー和の 3 dB でも、大きい側採用の 0 dB でもない)。
キャップは自分と同じ座標の定規にしか乗れず、加算した表示に対してはしきい値の発動点が **-3.0 ±0.5 dB**
の定数に収まる一方、`max(L,R)` に対しては 7 dB ばらつく。よってレーンは検出器が読む値へ畳み
(`duckerKeyDb`)、キャップはそのまま乗る。-3.0 dB は**サイン波の peak→RMS** で、メーターがピーク読み・
検出器が RMS 読みであることの現れである。

**キャップは較正済みのマーカーではなく目安である。** -3.0 がサイン波の値であって定数ではないためで、
片側にトーン・もう片側にプリアンプノイズを入れて測ると、発動点は加算表示より **8.5 dB** 下だった
(3.5 ではない) — ノイズ的なキーの peak→RMS は 3 dB ではなく 10 dB 前後だからである。
つまりプログラム素材では、キャップが示すより**低いバー読みで発動する**。補正は当てない: アプリは
キーのクレストファクタを測っていないし、-3.0 は選べる 2 つの定数のうち良い方 (無補正だとトーン側が
3 dB ずれる) というだけである。

**リダクションを POST に重ねる理由。** リダクションは 0 から下へ、レベルは床から上へ伸びるので、
衝突条件は `レベル + |リダクション| > 0 dBFS`。入力側のレーンではこれが常態で、工場出荷のレンジ
-56 dB ではブロックが定規の 93% を覆いバーの頂点が埋もれる。出力レーンは
`出力 = 入力 - |リダクション|` なので衝突は入力が 0 dBFS に達したときだけで、
**両者の隙間がその信号のヘッドルームそのもの**になる。

代償は、重ねたリダクションが専用目盛りを持てないこと。共有定規に乗るが、その定規はしきい値の定義域
(0..-60 dB) のままなので、**60 dB より深いリダクションは頭打ち**になる。レンジは -70 dB まで届くので
到達しうる。他のレーンとキャップを、実際に使う定義域に載せ続けることとの交換である。

### Envelope

x は対数の時間で、両方の設定を 1 本で張る (attack は 0.092 ms から、decay は 5 s まで)。y はゲインで、
上が 0 dB、下はレンジの下限 -70 dB。3 本の直線 — `attack` でレンジまで下り、保持し、`decay` で戻る。

**直線で、ライブ要素を持たない。** release は指数的な近づき方をするが、末端が GR メーターの 1 dB 量子に
支配されるため単一の時定数を当てはめていない。主張は**到達時間**だけで、2 点間の直線はそれを述べる。
リダクションが専用列を持っていた頃はここにライブの破線を引いていたが、数ピクセル右の POST バーに
ブロックとして出るようになった時点で、破線は同じ量の 2 つ目の表示になった — しかも時間軸はライブの
読みに位置を与えないので弱い方だった。COMP が点を残すのは、あちらのプロットが入力→出力を写していて
ライブのレベルに実位置があるため。

## SSMCS

Sweet Spot Morphing Channel Strip は、MONO IN チャンネルの COMP/EQ タイプ切替でコンプと 4-band PEQ
の代わりに入るバンク。1 画面に収まらない量を持つ 1 つの処理なので、3 画面ではなく**1 画面 3 面**を取る:

| セグメント | 表示 | 行 | レーン |
| --- | --- | --- | --- |
| MAIN | コンプの伝達曲線と EQ の特性を 1 枚のキャンバスに左右で | Sweet Spot Data / Comp Drive / Morphing / Out Gain | 無し (タップは読み値タイルで出る) |
| COMP | 伝達曲線とその横のラック | Attack / Release / Ratio / Knee | PRE COMP / PRE EQ |
| Side Chain | フィルターの応答とその横のラック | Side Chain / Q / Freq / Gain | PRE COMP / SIDE CHAIN / PRE EQ |
| EQ | 特性とその横のラック | Band / Q / Freq / Gain | PRE EQ / PRE INS FX |

**4 つとも 1 本のバーで選び、それは表示列自身のバー。**3 面に対してセグメントが 4 つあるのは、COMP 面の
2 つのプロットが別の問いに答えるもので、別々に名指しする価値があるため。題の行のフェイスバー + その下の
表示バー、という 2 本立てを置き換えた — セグメント行が 2 本あると、探しているものがどちらにあるかを
操作者が知っている必要があり、しかも題の行の方が見つけにくかった。バーの項目は行き先のフェイスと着地する
セグメントを持つので、2 項目が同じフェイスを指せる。どれが押されているかはホスト自身の問いである —
フェイスとその中の選択の両方を知っているのはホストだけであり、選択が別物であるフェイス (EQ 面の選択は
バンド) はフェイスだけで一致させる。

**EQ 面は BAND 行を持たない。**レスポンス上のマーカーがバンド選択そのもので、出荷済み EQ 画面と同じ扱い。
4 つの面が持つバーはバンクの 1 本だけである。

題は 4 つとも `[CH 1] SSMCS` で固定する。面ごとに題を付けると `[CH 1] Comp` と `[CH 1] EQ` — 出荷済み
COMP / EQ 画面の題と完全に一致 — になり、チャンネルの 2 つのバンクのどちらを見ているかが題から読めなくなる。

**COMP 面の各セグメントは、隣のプロットに効果が出るスライダーだけを持つ** — CURVE にはコンプの、
SIDE CHAIN にはフィルターの。描かれていない曲線のスライダーは、操作者に見える変化を何も起こさない。
2 群とも 4 行で、これがこの面を兄弟と同じ高さに保っている量でもある。

**面を変えても画面は閉じない。**3 面は 1 チャンネルに対する一続きの作業 — Morphing を回す → リダクション
を見る → Mid を触る → Comp Drive に戻る — で、その都度閉じて開き直すとモーダルの再構築とメーター
スロットの返却・再取得が挟まる。

**各面は同じ高さで、表示パネルの上端も揃える。**面を移るバーは表示の上にあるので、モーダルが伸縮すると
今押したコントロール自体が動き、パネルの開始 y が違うとプロットが読んでいる目の下で跳ねる。どちらも自動
では揃わない — 行数は 4 / 4 / 4 / 4 になったが読み値タイルの枚数が違い、表示の中身も面ごとに違う。
グリッドには最も高い面に、より幅の広いフォントスタック向けの余裕を足した `min-height` を置く。

**読み値タイルの列数はここでは見た目でなく効いてくる。**3 列に 4 枚だと 3 + 1 の不揃いな折り返しになり、
4 枚に必要な幅より広い。そこで 4 枚を持つ面は 2 列 (2 × 2) か 4 列 (1 段) を要求する。サイドチェイン面は
4 列 — タイルが 2 段になると 64px 増え、この予約が吸える量を超える。

**予約は窓が足りなければ譲り、その下でグリッドがスクロールする。**`.consent-box` は自分をビューポートへ
クランプし溢れを隠す。Close を載せた操作行はその最後の子なので、箱が守れない下限を置くと Close が見えなく
なる — 最小窓 960×640 (`tauri.conf.json`) で実測、MAIN / COMP / EQ × 日英の 6 読みすべてで箱の下端から
68px 外。そこで下限は `min(520px, calc(100vh - 211px))` とした (211px はグリッドの外側でモーダルが使う
分と、箱がビューポートから空ける 48px の和)。下限を下回る側では、行き場の無い行を切る代わりにグリッドが
スクロールを取る。**譲っても高さの一致は残る** — 640px では 3 面ともクランプ後の 592px で、差はスクロール
が吸う。

ここからさらに 2 つ派生する。ヒント行は**全画面 3 行**。元は 2 行で、バンクだけが 3 行だった — MAIN の文は
Comp Drive・Sweet Spot Data・Morphing を名指す必要があり、日本語では最小窓 960px で 3 行目に入って
無言で切られていたため。3 行が既定になったのは COMP の説明文が CI イメージ上で同じことをしたから:
macOS では 2 行が両言語・全画面で 960px を通っていたのに、CI では日本語 COMP が 13px 切られた。
3 行の代償は実測でほぼ無い — 960×640 では言語×画面の 6 組すべてで盤の高さが動かず、1280×800 で
伸びるのは GATE だけ (610 → 634px)。そしてどの面も 960px までプロットをレーンの横に保つ (出荷済み 4-band 画面はそこで折り返す) — バンクの
中ではその折り返しが 1 面だけ 291px 変わることになるため。バンクは折り返さない: 行を `flex-wrap: nowrap`
とし、ラックが自分の幅 (固定幅スロットの固定本数) を保ち、プロットが残りを取る。先に試したのは実測値の
下限で、いま置き換えたのがそれである — レーンを 1 本足すたびに**どの面が持つ最も広いラック**に対して
測り直す必要があり、EQ 面の 2 列が最も広かった頃に測った下限に対してサイドチェイン面が折り返した。
現行規則での実測 (960px): サイドチェイン面はプロット 199px・ラック 223px、COMP 264 / 158、EQ 252 / 170、
960 / 1000 / 1280 / 1600px のいずれでも折り返し無し・横方向のはみ出し無し。
最小窓でプロットが細くなるのは受け入れた対価 — 伝達曲線は情報量が少なく、幅を削る代償が最も小さい。
以前の実測は
ビューポート高 731px 以上で **683px・パネル上端 141px**、最小の 640px で **592px・同じ 141px**、
幅 960 / 1000 / 1100 / 1280 / 1440px × 日英で一致し、いずれも Close は箱の内側。押さえているのは
`e2e/ssmcs.spec.ts` (既定ビューポートと 960×640 の 2 本) で、jsdom はレイアウトしないので他に置き場所が
無い。

ホストの「行は消えない」不変条件が禁じているのは**編集**が版面をポインタの下で動かすことで、面を
切り替えるセグメントはグリッドより上にあるため、押した先の要素が入れ替わることはない。

**アドレス集合は同一ではなく包含関係。**MAIN の 4 タップは他 2 面の和なので、面を変えると購読は縮むか
元へ広がるかのどちらかで、DUCKER の動く KEY タップに要る比較 (下記「対象範囲」) がそのまま担う。

**内部段は既存のタップに対応する。**URX44V 実測: 108 がコンプ入口、110 がそのリダクション、111 が
コンプと EQ の間、112 が EQ の後。**このモードでも 111 は生きたタップ**で、SSMCS の Mid を +18 dB に
すると 112 だけが 7 dB 動き、108 と 111 は動かない。MAIN が 3 本ではなく 4 本のレーンを持つのはこのため
— 伝達曲線のライブドットはコンプ自身の出力を指す必要があり、112 を使うと EQ の効きがコンプの曲線に乗る。

### レーンの定規と、そこに無いもの

床 -60 dB・6 dB 刻み = 4-band EQ 画面と同じ。この段はプログラムレベルを運ぶため。GATE / COMP が
-72 / -54 を使うのはそれぞれのしきい値の定義域だからで、**このバンクは dBFS の値を 1 つも露出しない**
ので、キャップが乗る値が無くラックはジェスチャーを持たない。折れ点は実機が表示しない内部値が駆動する。

リダクションのレーンは COMP 画面のもの: アドレス 110、自前の 0〜-24 dB 目盛、COMP 面のみ。MAIN では
同じリダクションが、ライブドットの下で伝達曲線と単位線の差として図に出て、値は読み値タイルが持つ。

**SSMCS の COMP 面の Side Chain セグメントは 3 本目のレーンを持つ: サイドチェイン自身。** 読むのはアドレス `109` =
サイドチェインフィルタの出力で、このコンプの検出器が聴いているものであり、実機の COMP 画面で
「サイドチェインが ON のときだけ動く」唯一の量。入力とリダクションの間に立つ — 因果の順序が
それだから: レベルが届き、検出器がそれの自分用の版を聴き、リダクションが続き、レベルが出ていく。

**音声が通る段ではない**ので、この並びを直列の鎖として読んではいけない。実測 (URX44V・2026-08-15):
コンプを膝の下に固定したままフィルタを 36 dB 振ると、`109` は `108` に対して ±18 dB 丸ごと動く一方、
`111` − `108` は全域で 5.0 dB のまま動かない。フィルタはコンプ入力からの**分岐**で、`108` は
PRE COMP でありフィルタの入力でもある — 別々の 2 点ではなく 1 つのタップ — であり、`109` は音声では
なくキー信号。

したがって `109` は console が提供するメーターポイント**ではない**。チャンネルが SSMCS で、strip の
コンプとサイドチェインが両方 ON のときにしか floor から上がらないので、console のタップにすると
ほぼ全チャンネルで真っ黒な列になる。`meters.ts` は `monoTaps` から外し、`sidechainTap` として渡す。
CURVE と SIDE CHAIN は 3 本のまま — プロットと画面を分け合うため。

### リダクションの描き方 — 全画面で 1 つの規則

**レベルの列に合流したリダクションは相対値** — そのプロセッサが足すゲインぶん短く描かれるので
**量そのものではなく目安**であり、読み値タイルの数値とは意図的に別になる。合流形は共有定規に乗るので、
自前の目盛は持てない (2 本の定規が並ぶと 1 本に読める)。読み値タイルの数値はリダクション量そのもの。

理由は視認性で、承知の上での取引。合流すると 2 つは 1 本の目盛の両端から伸びるので、重なった区間は
**どちらも読めない**。重なり量は dBFS で `入力 + ゲイン` でありリダクション量には依存しないので、
ゲインを引くと `入力` が残る — 実信号なら 0 以下。したがって**決して重ならず**、隙間は入力の
ヘッドルームぶんになる。

**全画面が合流形式**で、これは DUCKER が元から採っていた形。GATE のリダクションは PRE COMP に、
COMP と SSMCS strip のものは PRE EQ に乗る。引くゲインはそのプロセッサ自身のもの (出荷済みコンプの
メイクアップ、strip の `min(24, |折れ点| × makeup/200)`) で、**GATE は何も引かない** — ゲートには
メイクアップが無く重なりようがないため。自前の列の分岐は `bindChannelStrip` から**削除した** —
その分岐が唯一の担い手だったレーンごとの目盛ごと。どの画面からも到達しない描画経路は、走らせて
確かめることができず読んで正しさを保つしかない 2 つ目の配置になる。

引く代わりに「差し引かれた元のレベルにブロックを固定する」形も作ったが取り下げた — 正確ではあるが、
バーと接するので 2 つが 1 本の列に見え、長さを読むのに動く辺が 2 本になる。

**引く量は `min(24, |折れ点| × makeup/200)` — プランから決まる定数で、スライダーを動かしたときにしか
変わらない。** 最初は同じ量を `108` − `111` の実測差として毎フレーム計算していたが、操作者が実機で
「リダクションが減るときにバーが突然伸びる」を観測 (2026-08-16)。2 つは別のメーターアドレスで
フレームの到着時刻が違うため差が別々の瞬間のものになり、しかも各々にメーター側のリリースがあるので、
リダクションが戻る局面では `111` が先に上がって差が逆向きに広がる。Out Gain は引かない — `117` は
EQ の後に効き `108`/`111` のどちらも動かさないと実測済みのため。

### 2 つの曲線

どちらも実測モデルから描き、確度の違いを線種では表さない — どちらも実測で、片方だけを破線にすると
絵が「こちらの方が確からしくない」と言ってしまう。仮定のまま残しているのは膝の中の曲率で、これは
出荷済み COMP の曲線が置いているのと同じもの。

- **コンプ。**しきい値は Comp Drive が駆動する内部値で、drive はゲインも足す — つまり
  このつまみ 1 つが折れ点を動かし**かつ**出力を上げるので、OUT レーンが動くのが操作者に見える。
  **Comp Drive は raw 31 で接する 2 領域を持つ。**31 以上ではしきい値パラメータが折れ点を持ち
  drive がそれをずらす (どちらも 0.2 dB / raw)。31 未満では折れ点は drive のもので、drive 0 の
  0 dBFS から raw 31 でしきい値が要求する値まで走るため、しきい値はそこでは 0.2 dB / raw のうち
  `drive / 31` しか持たない。URX44V (System 1.3.1.0) でコンプ出力そのものをホスト側で録音して実測:
  折れ点は raw 31 未満で 1 ステップあたり 0.8468 dB 落ち (31 以上は 0.2004)、しきい値は drive
  25 / 27 / 30 で 0.1616 / 0.1745 / 0.1938 dB / raw 動かす (drive 60 では 0.2004)、2 領域は
  drive 30.998 で接する。**境界はこの 1 つの drive で、2 パラメータにまたがる曲線ではない** —
  しきい値を raw 30 に保持して drive を掃引すると折れはまったく現れず、drive 31 から傾き
  0.2006 dB/step の 1 本の直線として始まる (RMS 0.0022 dB・22 点)。低い drive の見え方もこれで決まる:
  折れ点が実信号より上に来るので、コンプは「弱い」ではなく「切れている」ように読め、
  **描かれる**リダクションもそれに従う。**drive 0 はそれでもランプの下端ではなく独立した挙動**で、
  ランプなら折れ点は 0 dBFS に残り、Soft の膝はそこから −19.9 dBFS のトーンに 0.2 dB 描くところ、
  実機はどの膝でも 0 dB を返す (同じトーンが drive 10 では既に 1.9 dB 減る)。折れ点と膝を合わせた
  形も実機と突き合わせた: Soft / Medium / Hard × drive 10 / 20 / 24 / 28 の 12 通りで、
  描く減衰と実測は最大 0.107 dB で一致する。膝は**非対称**で、しきい値より上へ大きく開く。**膝のモデルは 2 つのバンクで 1 本** (`dyn-plot.ts` の `kneeResponse`) で、
  上下のリーチをペアで受け取る。バンクごとに別なのは**データのほう**で、
  `dyn-comp.ts` の `KNEE_WIDTH_DB` は対称な幅 1 値として当てはめた測定値なので、
  そのバンクは `up = down = 幅/2` を渡す。対称なペアでは 3 次補間は 2 次補間と同一の多項式になる
  (両端と両傾きの 4 条件を同じく満たすため) ので、共有しても出荷曲線は動かない。フルスケールのリダクション注記は漸近線ではなく描いた曲線から読み、ゲイン項を
  戻した値を印字するので、0 dBFS でまだ膝の中にある設定でもそこで実際に起きている量が出る。
- **makeup は曲線全体に掛かる 1 つのゲイン**で、出荷済み COMP 画面が自分の makeup を当てているのと
  同じ扱い。実測したのは**圧縮中**の挙動 — raw 5 点・線形・±6 dB・GR メーターは不動。同じ走行の
  しきい値より下の読みはしきい値 1 設定での陰性結果 1 点で、「makeup が切れている」と「ブロックが
  係合していない」を分離しない。両方を 1 本の曲線に載せることはできない: 片方の脚だけにゲインがあると
  膝の中に何を描いても角が段差になり、Hard は幅 0 dB なので均す余地が無い。圧縮側の脚だけに載せた版は
  Hard に**段差**、Medium にプラトーを超える**山**を出した — 320px キャンバス (4.44 px/dB) で隣接
  サンプル間 22.97px / 1.30px、掃引 2100 通り中 515 通りが折り返し、そのすべてが makeup ≠ 0 dB を
  必要とした。コンプの伝達曲線はどちらもしない。実機がどちらの脚に載せているかが未決で、決着させる
  観測は入力を角の上下にまたがせて `111 − 108` を両側で読むこと。
- **膝の形**は、実測した両端を通り各脚自身の傾き (下は 1、上は 1/ratio) を持つ 3 次補間で、2 つの傾きは
  使う前に 3 次の単調域へ制限する。2 次では原理的に届かない — 端点が 2 つの傾きで決まって
  しまうので、非対称な膝では漸近線から `(1 − 1/ratio)(up − down)/2` ずれ、工場値で 0.45 dB、上端の
  縦の段差として描かれていた。制限は、制限なしの 3 次が行き過ぎるのを止めるもの — プラトーを超えて
  上がってから戻る形で、入力の増加を出力の減少として描くことになる。両方の傾きを `3/hypot` 倍するもので、
  すでに単調域の内側にある組では 1 になるため、制限が要らない膝は両脚と厳密に接続したままになる。
  **実測した辺では一度も発動しない** — ratio 全域での最悪値が 2.18 で上限 3 に届かず、Hard は幅 0 なので
  分岐自体が走らない。それでも残すのは、辺が実測値でありまた動きうるため。
- **EQ。**3 バンド固定 (LOW シェルフ / MID ピーキング / HIGH シェルフ)。シェルフの規約は 4-band の
  モデルと同じ — 公称周波数はプラトーから 3 dB 下 — だが、peaking の Q は**別**で、4-band の
  「実機 Q はバイクアッドの 2 倍」はここでは反証された。MID は下のサイドチェインフィルタと同じ
  ゲイン依存の法則を取る (同一のフィルタだと実測されている)。4-band 側の定数は `eq-response.ts` に
  隣り合わせて置いてあり、片方をもう一方のブロックへ持ち込めないようにしてある。バンドを OFF にすると合成から
  抜けるがマーカーは残り、自分の周波数で合成後の曲線の上に座る — 「選択されたまま、効いていない」の
  2 状態が 1 枚で読める。
- **Out Gain は**コンプ**の曲線のベースラインに描く。実機が適用するのは EQ の後**。適用位置は実測した:
  `117` を +18 と -18 dB の間で振るとタップ `112` が 1:1 で動き、`108` と `111` は動かなかった
  (URX44V・2026-08-15)。つまり strip は `108 → コンプ → 111 → 3-band EQ → Out Gain → 112`。それでも
  もう一方のプロットに描くのは軸の都合で、EQ 側のゲイン軸は**バンドのゲイン範囲そのもの**なので、
  最大 18 dB のオフセットは応答を枠外へ押し出し、操作者が見に来た形ごと持って行く。伝達プロットの出力軸は
  ドライブとメイクアップが足されるぶん元から +18 まであり、strip の出力ゲインはそこでベースラインの
  持ち上がりとして読める。これ以前は**どちらの曲線にも入っておらず**、±18 dB のスライダーが画面上の
  何も動かしていなかった。
  **ライブドットも同じだけ持ち上げる**: 伝達プロットのドットは (`108`, `111`) の対で、`111` は
  Out Gain より上流。素のまま描くとどの入力レベルでもちょうど Out Gain のぶん曲線の下に座り、
  操作者から報告された。プロットの `outOffsetDb` がプランの Out Gain を出力読み値に足してから描く。
  MAIN 面の左半分は同じ曲線を描くので同じ持ち上げを、同じ 1 つの関数を通して取る — 2 つのドットが
  別の高さに座ることがないように。代案は曲線側から Out Gain を外すことだったが、そうすると
  どこにも描かれなくなる (EQ のプロットが運べない理由は 1 つ上)。

### 2 本目の曲線: サイドチェイン

バンクのバーには出荷済みの COMP 画面に対応物の無いセグメントがある。このコンプにはあちらに無い入力 —
**検出器**の手前のフィルター — があるからで、その応答を下の 3 行から描く。コンプ自身のスライダーは
もう一方のセグメントにある: 描かれている曲線を動かさないスライダーは、操作者に見える変化を何も
起こさないため。

**strip の MID バンドと同じベルで、1 つの法則が両方を描く**。フィルターだけを共有し他を共有しない 2 つの器で URX44V 上で
測定した — ratio ∞ + knee Hard にしたコンプ自身のリダクション (GR = 検出レベル − しきい値で、
しきい値は 0.2 dB/step の定規) と、フィルター出力を運ぶメーター `109`。両者は 488 組の読みで
中央値 0.00 dB で一致し、音声経路で読んだ MID バンドと検出器経路で読んだサイドチェインは
61 点中 60 点で完全一致した。ピークゲインと中心周波数は設定値そのもの、0 dB は完全なバイパス。

**実機が表示する Q はバイクアッドの Q ではなく、係数も定数ではない** — ゲインが大きいほどベルは
狭くなる: `Q(biquad) = 0.238 × Q(表示) × A^0.39`、`A = 10^(|gain|/40)`。18 / 12 / 6 / 3 dB で
0.3585 / 0.3085 / 0.2750 / 0.2615 を実測、ゲインの符号に対称で、16:1 のレンジの Q にも中心周波数にも
依存しない。定数比で代用すると RMS 0.160 dB、この法則なら 0.064 dB = ゲインごとに個別に当てはめた
残差と同じ。

MID バンドはこの法則が届くまで**定数比 0.82** で描いていた。その数値は「ピークから 3 dB 下の 2 点」の
幅を読んだ掃引から来ており、バイクアッドの Q は**半ゲイン点**の幅で定義される — 18 dB のベルでは
両者が 2.78 倍違うので、すべての MID ベルを約 2.3 倍狭く描いていた。61 点掃引に対して定数は
3 状態通しで RMS 2.2 dB (最悪 5.6 dB、常に狭い側)、この法則は 0.47 dB (最悪 1.0)。
`pnpm test eq-response` がその実測値に対して 1 点ずつ当て、定数に戻すと 3 状態すべてが落ちる。

**軸はフィルター自身の符号に対して反転してあり、それが要点**。このセグメントが描くのはフィルターが
適用するゲインではなく、それが生む**リダクション量**である。検出器側で帯域を持ち上げるとコンプは
そこをより強く聞いて深くかかるので、ブーストは**下**へ描く。逆向きに描くと、曲線は上がるのに
それが生むものは下がり、数ピクセル右のリダクションレーンと反対を向いた。モデルはフィルターの
真の符号を保ち、反転するのは描画だけ。

**アプリで面を塗る唯一の曲線**。他はどれも曲線が音声で、線そのものが操作者に聞こえる結果を語る。
ここでは線は音声ではなく、面が読み取りの対象 — コンプが強く反応するようにされた帯域、あるいは
反応しなくされた帯域。ヒント文が同じことを 1 度だけ言葉で言う。

**ラックは隣に立ち、各セグメントは自分のプロットが答えないレーンを落とす**。伝達曲線はコンプ自身の対なので
サイドチェインのタップが落ちて 2 列になる。Side Chain は 3 本とも残す — フィルターがしたことは「入力と
ディテクターが聞いているものの差」なので、入力を落とすとその面が自分の問いに答えられなくなり、しかも
フィルター自身の出力はそもそもメーターに出ていないので減らして対にする先が無い。COMP GR はどちらでも
それが差し引かれた PRE EQ の列に重なる。**タップはセグメントごとに違う**ので、セグメントの移動は
ラックの組み替えであると同時に購読の変更でもある — Side Chain は `109` を 1 本足す。

**マーカーは曲線が言えないことを運ぶ**。フラットは 2 通りで来る — フィルターを外した状態と、
フィルターが効いていて 0 dB の状態 — どちらも曲線では区別できない。`on` は前者でマーカーを暗くする
(OFF にした EQ バンドと同じ扱い)。ピルは枠内に収める: ホストはプロットを軸でクリップし、その上端が
ゲインレンジの最大値そのものなので、フルブーストのフィルターはマーカーの上半分を失っていた —
3 バンドの EQ では気付かれない程度に稀で、1 バンドのサイドチェインでは普通の設定。

### 行が決してしないこと

Morphing 中でも行はロックしない。Morphing と Sweet Spot プリセットは**再計算**であって継続する駆動では
ない: 書いた瞬間にデバイスがコンプ / サイドチェイン / EQ / Out Gain を書き換え、その次の瞬間から値は
操作者のものに戻る (実機の LCD も直後の編集を受ける)。これが EQ の 1-knob — ON の間じゅう行を視界から
予約退避する — との違いで、修復はロックではなく読み直し (`ParamSpec.sideEffect: "refetch"` と、その隣の
`drives`) である。

EQ 面は Type 行を持たない。3 バンドとも固定なので、どのバンドでも同じ 1 値のロック行が常設になるだけ —
4-band 画面が Type 行を残す理由 (4 バンド中 2 つが型を持ち、落とすとバンドによって高さが変わる) は
ここには無い。シェルフ 2 帯の Q 行がロック + タグで残るのは、まさにその理由による。

## INS FX

**インサートエフェクトすべてを 1 つの画面で扱い、family はプランから解決する。**ノードが何を保持しているかは
別の面が変更するセレクタの値であり、デバイス追従は開いている画面の下でそれを変えうる — そのため
`insert-fx-screen.ts` は family ごとに存在するのではなく、呼び出しごとにプランを読む。レジストリの項目は 1 つ、
モーダルも 1 つで、追従は画面を閉じて開き直すのではなく再束縛する。タイトルはエフェクト自身の名前を持つ
(`INS FX — Compander-H`)。持たなければ見出しは中身ではなくスロットを名指すことになる。

- **Effect Type の行は意図的に持たない。**セレクタを書くと実機は束縛されたエンジン配列をそのタイプの既定値で
  埋め直し、これは可逆ではない — 元のタイプを選び直しても、そのタイプの既定値で埋まるだけで、そこにあった値は
  戻らない。これをスライダーの隣に置けば、スライダーと同じ重さに見える。選択はインスペクタの Insert FX 行に残り、
  この画面は選択済みのものを調整する。
- **プロットを持たない。**ギターアンプの周波数応答もピッチトラッカーもパラメータから導出できず、実機もどちらも
  計測していないため、表示列はレーンのラックだけである。`plotGeo` / `drawAxes` / `drawCurve` がまとめて省略可能
  なのはこのためである。
- **field はパラメータではなくエンジンスロットを名前に持つ。**インサート FX の値は family とスロットをキーに
  `insertFxParams` へ入るので、field のキーは `ifx6` であり、スロット 6 が画面上の family で何を指すかは
  カタログだけが知っている — `fieldLabel` と `fieldText` にコンテキストを渡すのはそのためである。範囲・既定値・
  enum・表示形式はすべて `core/control/insert-fx-effect.ts` から来る。ここで書き直すものは 1 つも無い。
- **コンパンダーの行は応答を形づくるもので束ねる** — Threshold・Ratio・Width、次にメイクアップ、最後に Attack と
  Release — であって、カタログが emit 経路のために持つ実機の読み出し順ではない。
- **MIDI id を持たない。**コントロールカタログにこれらの値の id が無いため、画面は何も mark しない — DUCKER と
  同じ位置であり、理由も同じである。

### 2 つのリダクションメーターは軸が違う

1 つの表にしていない理由がこの違いである:

| エフェクトの位置 | 入力レーン | 出力レーン | リダクション |
| --- | --- | --- | --- |
| MONO IN チャンネル | PRE INS FX (`112:ch`) | PRE FADER (`113:ch`) | `132:ch` — x は mono CH |
| 出力バス | PRE INS FX (post-fader) | POST (post-insert) | `133:band` — x はエフェクトの**バンド** |

`133` はノードを一切取らない: 出力インサートエフェクトは実機全体で 1 つしか動かない (`out-dyn` の 1-of スロット)
ため、どのバスが持っているかはアドレスに入らない。単バンドのエフェクトはバンド 0 を読む。

リダクションはどの画面でもそうであるように OUTPUT の列へ併合し、オフセットは取らない: 規則は「そのプロセッサが
加えるゲインを差し引く」であり、これらは何も加えないからである — コンパンダーのメイクアップは 0 dB までで、
それ以下は減衰のみなので、レベルのバーと同じ定規の上端から下がるリダクションは出会えない。

### この画面が表示する family

ギターアンプ 4 種と 2 つのコンパンダーである。Pitch Fix とマルチバンドコンプレッサはインスペクタ側のエディタに
残り、`bind` も拒否するので、どこで編集するかについて 2 つの面が食い違うことはない。Pitch Fix は Key・Scale・
12 音マスクをフラットなカタログの外に、かつ独自の規則の下に持つ — 音を編集すると Scale は Custom になり、
パターンをこのアプリが生成できるプリセットは 2 つだけである — ため、フラットな行だけで組んだ画面は、エフェクトが
何へ補正するかを決める半分を欠く。マルチバンドコンプレッサはそもそもフラットなカタログに無い。

## スケール外は枠外

すべてのプロットはカーブを**真値**で描き、**ホストがプロット領域でクリップする**。軸にクランプすると
下端 (上端) に横棒を引くことになり、そのプロセッサーが持たない特性を描いてしまう:

| プロット | クランプが起こしていたこと |
| --- | --- |
| EQ | HPF はコーナーから 1 オクターブで -18 dB の下限を超えるため、カーブが枠の下端に沿って伸びていた |
| GATE | 閉じたシェルフは threshold + range にあり、**range が有限のまま -144 dB まで届く** (threshold -72 … -56 × 最深 range)。-128 の軸にクランプすると **range = -∞ と同じ絵**になる — 閉じていないゲートが閉じているように見える |
| マーカー | 床に張り付けると、その周波数で特性が到達しないレベルを指し示すことになる |
| COMP | 何も起きていなかった — -54 … +18 の軸が応答全体を含む (makeup は加算のみ・膝の補正は減算のみ)。推測ではなく `src/ui/dyn-plot.test.ts` が両端で検査する |

この分離は各 descriptor が覚える約束ではなく**構造**である: `drawAxes` はクリップ無しで呼ばれ
(目盛りラベルは `geo.pad` が確保する余白に描く)、`drawCurve` はクリップ内で呼ばれる。新しい
プロセッサーのプロットは存在するだけでこの規則を継承する。

意図的な例外は 2 つ。いずれも該当箇所に明記する:

- **値の注記はクランプしてよい**。注記は値そのものではなく値を説明するものだから — GATE の range
  ラベルは、指し示すシェルフが枠外へ出ても枠の下端で読めるまま残る。注記へ引く引出線はカーブの一部
  なのでクランプしない
- **GATE の range = -∞ は軸の床に固定する**。そこでは床が -∞ の表現である (GR メーター自身の床であり、
  ラベルも "-∞" と出す)。これはクランプではなく表現で、有限値側が枠外へ抜けるようになった今、
  有限値と -∞ を区別可能にしているのはこの固定である

## 対象範囲

GATE は MONO IN の機能なので、その画面は CH1-4 (URX22 は CH1-2) にのみ存在する。COMP は同じ
チャンネルの **COMP->EQ モード**、SSMCS の 3 面は同じチャンネルのもう一方のモード — 2 つのバンクは
排他なので、チャンネルはどちらか一方だけを提供し両方は出さない。EQ は 4-band PEQ があるところすべて
— SSMCS 以外の全 mono CH・全 stereo CH・各 MIX Bus・STEREO マスター。ノードは**開いた場所で固定**され、
画面内にノードの切替は無い。

**処理**の方は 1 つのバンクに限り固定でない。SSMCS の 3 面は題の行から互いに行き来する (上記) ので、
これは 1 つの開いた画面の中での処理切替である — ノードの切替にはならない。そもそも画面はチャンネル
単位のコントロールから開くため。

購読アドレス集合はそれに**追随して固定されるわけではない**。DUCKER の KEY レーンはソース自身の
Rec Point で読む (上記) ため、画面を開いたまま Rec Point が変わると — グラフのインスペクタからでも、
アンドゥでも、実機の前面パネルからでも — 画面は開いたノードのままアドレスだけが移る。したがって画面は
rebind のたびにアドレス集合を比較し、違えば購読し直す。これが無いと KEY のバーは画面を閉じて開き直すまで
`—` のままになる。

残る確定済み GR メーターは DUCKER (119) と insert FX (132 入力・133 出力)。**軸が GATE / COMP の
mono CH index とは違う** — DUCKER はステレオペア、出力 insert FX はエフェクトのバンド — ので、
追加するときは `grAddr` の軸を継承せず、それぞれの実測軸を持ち込む必要がある。

### この画面は最前面ではない

プラン読み込み (ドロップ / 開く / 最近使用) は調整画面を開いたまま起こりうるので、`loadPlan` が画面を
refresh する: 画面はクロージャ経由でプランを読むので値自体は既に新しく、足りなかったのは再描画の指示
だけだった。refresh は束縛も再解決するので、新しいプランにそのノードや処理が無い画面は、無くなった対象へ
書き込む前に自ら閉じる。

各スクリムは同一 z-index を共有していたため**ドキュメント順が優劣を決めており**、**読み込みレポートが
調整画面の背面**に回っていた — そのドロップについてのレポートが読めない状態である。**ドロップ告知**も
背面だったが、こちらは別の理由で知っておく価値がある: `z-index: 120` を書いた規則が `.consent-scrim` の
`100` より**前**にあり、同一詳細度では後の規則が勝つため、告知は**一度も 120 になっていなかった** —
「モーダルより前面に出る」というコメントは書かれた時点から誤りだった。両方を `style.css` の 1 つの
明示的な順序表にまとめ、`.consent-scrim` より後に置いてカスケードが黙って打ち消せないようにした
(メニュー 40 / コントロール付随ポップオーバー 60 / ツールモーダル 100 / ドロップ告知 120 /
決定ゲート 130)。consent・読み込みレポート・レート選択はいずれも「何が開いていても答えられなければ
ならない問い」なので最前面に置く。

### ジェスチャの途中でウィンドウを奪われたとき

この画面が持つ 3 つのドラッグ — スレッショルドのキャップ、プロット、値の行 — は、ウィンドウがフォーカスを
失った時点で終了する。どのエンジンも終わらせてくれないためで、ボタンを押したまま OS の前面を奪われると
`blur` は発火し、**`pointercancel` は発火せず**、ポインタキャプチャも保持される (2026-08-14 に Chromium と
実機の WKWebView で実測)。これが無かった間は、アプリ切替を跨いで押し続けた操作が、別アプリが前面のまま
プランと実機へ書き込み続けていた。`history.ts` も同じ `blur` で押下を終端するので、残りの移動は**新しい
Undo エントリ**に落ちていた。

キャップとプロットはビュー自身のジェスチャなので、ビューが持っているものを落とせば終わる。**値の行は
ネイティブの `<input type="range">` で、ドラッグを所有しているのはエンジン**であり、3 点で別の問題になる
(いずれも実測):

| 処置 | 結果 |
| --- | --- |
| リスナを外す | 効果なし。駆動しているのはエンジンで、アプリは `input` を写しているだけ |
| `pointer-events: none` | 効果なし。両エンジンで書き続けた |
| DOM から外して戻す | ドラッグは終わるが、**フォーカスが戻ると再開する** — 実機で押したまま戻ると行が再開した |
| `disabled` | 終わり、かつその間は再取得されない |

したがって、ウィンドウを失った行は `disabled` にし、**押下が終わるか、ウィンドウが戻るまで**その状態で
保つ — `pointerup` / `pointercancel` / ボタン無しを報告する `pointermove` (ウィンドウが聞き逃した離しの
受け皿) / アプリのフォーカス復帰。blur で 1 度切るだけでは足りなかった: **detach の処置**では、押したまま
フォーカスが戻った時点で行が再開し、それがその処置を差し戻した理由である。`disabled` は再開しない
(両エンジンで実測、実機でも手作業で確認) ので復帰を解除条件にでき、しかもこれは**必ず届く唯一の信号**
である — ウィンドウの外で失われた離しは数えられず、タッチの識別番号は再利用されないため、これが無いと
行が不活性のまま解除されずに残りうる。`disabled` はフォーカスを落とすので、
戻すときに復元する。画面上の代償は無い — このスライダーは `appearance: none` でトラックもつまみも自前
描画のため、エンジン側に減光する対象が無く、enabled と disabled で撮った行は両エンジンともバイト一致する。

**これは調整画面の規則ではなくアプリ全体の規則**で、本体は `ui/dom.ts` の `holdInertOnBlur`。`wheelStep`
と同じ理由で、**すべての `<input type="range">`** がここを通る — 調整画面の値行、inspector の 2 つの
スライダー生成器、共有の `sliderRow`、本体設定の Brightness。この画面が足すのは、保留した refresh が
どこで着地するかである。blur はこの画面自身のジェスチャを終わらせるが `grabbed` は解除しない — 押下は
まだ続いており、その下での再構築は押したままのポインタに生きたコントロールを渡す (hold が防いでいる状態
そのもの)。したがって保留は blur を越えて続き、refresh は**最初に届いた解放**で走る — この画面自身の
`pointerup` / `pointercancel` か、アプリ全体で最後の hold の解除 (ウィンドウの復帰もこれを生むので、
押したまま戻ると再構築はそこで起きる)。先に走った側が `grabbed` を解除し、残りは解除済みを見て何もしない。
hold 側はジェスチャ開始時の行ではなく**今画面にある行**を引く — 再構築が既に置き換えている可能性があるため。作り直された行は再構築が与えた `disabled` を保つ (COMP の 1-Knob が
入ると threshold / ratio / gain / knee はデバイス駆動になりロックされる) し、フォーカスも戻さない —
このアプリのどの再構築もフォーカスを復元しないため。

inspector も同じ信号で保留する。IME の変換中と `<select>` のピッカー展開中を待つ既存のゲートに相乗り
させている。名指しする価値があるのは、hold だけが自前の終了イベントを持たないためである — 変換は終わり、
ピッカーは閉じるが、hold が終わるのはパネルが観測しないポインタの解放なので、ゲートは hold の管理側を
直接購読する。

## メーター購読の所有権

**このアプリはセッションごとにメーター購読を 1 つだけ持つ。これは実機の制限ではなくアプリ自身の
持ち方である。**ワイヤに購読という単位は無く、`reg_meter` がアドレス 1 本ごとに `regist` /
`unregist` フレームを送る。1 つしか無いのはワーカー自身の集合のほうで、`src-tauri/src/vd.rs` の
`Cmd::MetersSubscribe` が `subs.meter_addrs` を 1 本ずつ解除してから新しいアドレスを登録する。
だから `vd_meters_subscribe` は追加ではなく置き換えになり、`vd_meters_unsubscribe` がアドレスを
取らないのは落とす集合が 1 つしか無いためである。同じ箇所に記録されている実機由来の制約は別物で、
`/vd/meters` へのバルク POST は禁止 (Device Center が落ちるのを観測済み)。

置き換えは無音で、CONSOLE は自己回復しないため、断りなく奪うと CONSOLE のバーが床で凍りついた
まま残る (無音と区別が付かない)。

これを塞ぐ機構が 2 つある。

- **購読自体への世代スタンプ** (`subscribeMeters`)。呼び出し側が持つ解除ハンドルは購読単位に見えて
  実はそうではないので、古いハンドルが**今の所有者**をキャンセルしうる (CONSOLE の登録が飛行中に
  画面がスロットを取った場合、画面が自分の購読往復より速く閉じた場合の 2 経路)。解除は自分の世代が
  現行のときだけ効き、古い登録から遅れて届いたフレームは新しい所有者の store に書かず捨てる。
- **明示的な貸し借り** (`Console.releaseMeters()` / `regainMeters()`・`metersLent` でガード)。画面は
  購読前にスロットを取り、閉じるときに返す。貸出中は CONSOLE の `render()` が再購読しない — render は
  「CONSOLE が見られているか」と無関係な理由 (デバイス追従のリコンサイル等) でも起きるため。
  `regainMeters` は CONSOLE がライブかつ表示中でなければ no-op で、GRAPH のインスペクタから開いた
  場合は CONSOLE が非表示のことがあり、その場合は次の `show()` が走らせる `render()` が張り直す。

ライブ状態は `setLiveUi` から両サーフェスへ届く。セッションの出入りが必ず通る funnel で、
「CONSOLE が購読し、その後に画面が奪い返す」という**順序が効く**ため、各呼び出し側ではなくここに 1 度だけ書く。

GR のピーク畳み込みは `MeterStore` からではなく**購読コールバック側**で行う。store はアドレス単位で
last-write-win なので、1 バッチに同一アドレスの複数フレームが入ると最後の 1 つしか残らない。

## 起動元

| 場所 | コントロール |
| --- | --- |
| GRAPH インスペクタの GATE / SSMCS / COMP / EQ セクション | ON/OFF トグルの下の全幅ボタン。ラベルは中央、末端にカレット |
| CONSOLE のストリップ | そのストリップが持つ処理チップそれぞれの横の細いチップ。字は `▸` |
| GRAPH インスペクタの Insert FX | 同じ全幅ボタン。Insert FX セレクタと ON トグルの下に置き、この画面が調整するエフェクトが選択されているときだけ出す (未選択なら開く先が無い) |

SSMCS モードでもインスペクタは 4 セクションを保ち、起動ボタンをそれぞれ引き渡す: SSMCS
セクションは MAIN 面、COMP / EQ セクションは同じバンクの COMP / EQ 面を開く。ラベルは出荷済み画面の
もの (「Comp screen」「EQ screen」) をそのまま共用し、専用の文言は持たせない — 起動元は同じセクション
で、チャンネルは 2 つのバンクを同時に持たないので、そのラベルはそのチャンネル上でちょうど 1 つのものを
指す。

**CONSOLE 側はチップを引き渡さない。**ストリップが持つ起動チップはバンク全体で 1 つ、SSMCS チップの
横だけで、COMP / EQ のチップはストリップを持たないチャンネルと同じ見え方になる。バンクの残り 2 面へは
画面内の面セグメントから行く — 画面を開いている読み手が探すのはそこで、ストリップに 2 つ目・3 つ目の
入口を置くと 1 つのモーダルに対して 1 チャンネルあたり起動チップが 3 つ並ぶ。代償は、その 2 面へは
CONSOLE から直接行けない (インスペクタより 1 押し多い) こと。

**どちらも右を指し、言っていることも同じだが、描き方は意図的に違う** — それぞれが乗っている面の
一族に属させている。インスペクタ側は 2 行上のセクション見出しの開閉矢印と同じ作り (グリフではなく
隣接 2 辺のボーダー) で、その矢印と並べて測ると 180 画素に対して 174 画素 = 同じ重さの同じ記号に
読める。CONSOLE 側がグリフなのは、隣がグリフだから。**両者を互いに合わせると、合わせた先の面が
壊れる。**

**3 セクションとも ON トグル + 起動ボタンだけに縮めた。**インスペクタにスライダーの写しを残すのは
単なる重複ではない — `dynFieldSlider` は render 時の params スナップショットを読み、値変更で
再レンダしないので、画面側で値を動かした後にそのスライダーをドラッグすると古い値が書き戻る。

CONSOLE 側を既存チップのジェスチャーにせず独立チップにしたのは、`wireActivate` が click と
Space/Enter を `detail` ガード無しで束ねているため、ダブルクリックが処理を 2 回トグルして 2 回
書き込むから。加えてダブルクリックはこのビューのフェーダー / ノブで工場出荷値リセットに使われている。
各ペアが 2 列グリッドの 1 行を埋める — ヘッド高さが一律なのは SENDS ラック / フェーダー / メーターを
揃えるためで、その整列は保たれる。

EQ の起動チップは mono CH で処理チップを 4 行目に入れるため、ヘッドがその分を負担する必要がある:
旧 252px で実測したヘッド内寸は 254px (height が content-box なので padding 対と下ボーダーが加算される)、
チップ 1 行は 24px で、Hi-Z チップを持つ CH3 / CH4 の余白は 0.9px しか無かった。**手計測に頼るのは
やめた** — どのストリップのヘッドも自分の内容を溢れさせないことを E2E が assert する
(`e2e/console.spec.ts`)。`--head-h` は 276px とし、チップを持たないストリップも含めて全ストリップの
フェーダー領域が 24px 縮む。起動チップは、レートで EQ が強制 OFF のとき (隣のトグルも読み取り専用) には
出さない。

**SSMCS モードのストリップは同じ高さ。**モーフィングストリップ自身のマスターと 1 つの起動チップが、
COMP と EQ の 2 つの起動チップが立っていた場所にちょうど入るので、チップ数はバンクで動かない。
COMP/EQ タイプはそれでもヘッド高キャッシュのキーに残す — サンプルレートと同じ理由で、ヘッドが**何を
載せるか**を変えるからで、ここで釣り合っているのは規則ではなく数の一致にすぎない。この項は過去に
両方向へヘッドを動かしている (このバンクに画面が無かった頃は起動チップが 0、画面が付いた直後は
1 モーダルに対して 3 つ) ので、切れたヘッドを画面に出さずに済んだのはこのキーによる。

## MIDI 割り当て

この画面の全パラメータは外部 MIDI コントローラーから操作できる。カタログもラーンのジェスチャも CONSOLE
ストリップと同一である (`ui/midi-learn.ts`。カタログは `core/midi/controls.ts`、周辺設計は architecture.md)。

- **対象は行のコントロールセル。** ラーン中は破線リング、アーム中は実線のパルス、割当済みは琥珀のドット —
  コンソールと同じ 3 状態なので、ストリップのコントロールと画面のコントロールが同じに読める。押下は
  **capture フェーズ**で取るため、アームするクリックでスライダーがドラッグを始めない。ホイールも同じ理由で
  ゲートする。
- **ロックされている行は提供しない。** 理由は行が既に印字しているものと同じ — レートによりステレオ CH の EQ
  が無効、1-knob が値を実機に渡している、フィルタタイプがその値を読まない。列挙セレクタ (COMP の knee、EQ の
  フィルタタイプと 1-knob タイプ) も対象外で、カタログは連続値とトグルのみを持つ。
- **バンドはそのバンドに束縛される。** id のスコープは `@eq.low` … `@eq.high` であり、「バーが選んでいるバンド」
  ではない。マッピングはこの画面を閉じていても効かねばならず、バーは開くたび LOW に戻るからである。値キーに
  対する id を答えるのは `DynProcessor.controlId` — ホストはどのプロセッサを表示しているか知らないままで、
  コントロールを持たないキーには `null` が返る。
- **SSMCS のスコープはプラン側の入れ子をそのまま写す** — Comp Drive / Morphing / Out Gain が `@ssmcs`、
  以下 `@ssmcs.comp` / `@ssmcs.sc` / `@ssmcs.eq.low` … `@ssmcs.eq.high` — ので、id が編集対象への経路として
  読め、サイドチェインの Q とバンドの Q はトークンではなくスコープで分かれる。マスター ON は他のセクション
  マスターと同じくノード直下のスコープを取る。シェルフ 2 帯の Q 行と Sweet Spot Data は提供しない — シェルフに
  Q パラメータは存在せず、プリセットは列挙セレクタだから。
- **グリッドはフィールド表のもの。** MIDI 値もドラッグしたスライダーも先に「位置」を解決する
  (`control/translate.ts` の `dynToPos` / `dynFromPos`) ので、同じグリッドの別の値に落ちることはない。
- **ラーン中でも画面は開く。** `▸` オープナー自身は割当対象ではないため、アームのガードを素通りする。

## デバイスが無いとき

どのビルドでも、どの状態でも開く。パラメーターはプランの値なのでデバイス無し (ブラウザビルド含む) でも
完全に編集でき、メーターは床、読み値は `—`。ロックも非表示も行わない — ここには**編集**にデスクトップ
シェルを要するものが無く、**観測**にだけ要るため。

## 実装メモ

`DynScreen` が「どの処理を開いているかに依存しないもの」をすべて持つ — モーダル・レーンラック・
メーターフィードとピーク・スロットの貸借・キャンバス のライフサイクル・バー選択の永続化。残りは
`DynProcessor` が渡す: そのノードが何を持つか (`bind`)・プラン内の自分の持ち分 (`read` / `patch`)・
バー・行とその状態・プロット。DUCKER や insert FX を足すのは descriptor 1 枚を書くことで、画面を
もう 1 つ作ることではない。

置き場所はその分担から決まる:

| モジュール | 持つもの |
| --- | --- |
| `src/ui/dyn-screen.ts` | ホスト: モーダル・レーン・メーターフィード・キャンバス・`DynField[]` からの行 |
| `src/ui/dyn-chan.ts` | GATE / COMP が「MONO IN のチャンネルストリップ処理」として共有するもの — 束縛・サブオブジェクトのプラン I/O・表示バー |
| `src/ui/dyn-plot.ts` | その 2 つが描く dB×dB 伝達プロット: `transferPlot()` が軸 3 定数とヒントから 5 つのフックを返す |
| `src/ui/dyn-freq-plot.ts` | 2 つの EQ が共有する周波数×ゲインのプロット: 座標系・グリッド・バンドマーカー。マーカーは両者で同じ面の同じピルで、違うのはバンドの集合とフィルターモデルだけ |
| `src/ui/dyn-{gate,comp,eq,ducker,ssmcs}.ts` | descriptor — 差分だけ |
| `src/core/control/translate.ts` | 全フィールドテーブル (EQ の `eqBandFields` と SSMCS ストリップのものを含む)。実測の fine グリッドやレンジが UI ファイルではなく他と並ぶ |
| `src/core/eq-response.ts` | 2 つの実測フィルターモデル。デバイスのスイープに対してテスト済み |

EQ の予約領域の 1 行は、ホストのフックではなく descriptor が自分の `rows.tail` に入れる DOM。
絶対配置 (高さ 0 コスト) + `pointer-events: none` — 背後の Close ボタンへの押下を飲み込むラベルは、
ラベルが無いより悪い。

画面は独自の部品ではなく共有レシピで組む。行と見出しは `settingsRow` / `settingsSection`、モードタブは
`.udk-banks`、-∞ の読み値は `setLevelText`、スライダーは `wheelStep`、実機の fine グリッドを持つ唯一の
値には `fineTag` / `optInFine`、メーターの shade / peak は CONSOLE の登録済み `--lvl` / `--pk` ルール。
GR レーンが足すのは反転 (上から下がり、覆いではなくバーそのもの) とハッチだけ。`formatDyn`・range の
-∞ ノッチ (`dynValueText`)・どのフィールドが fine グリッドを持つかは、いずれもそれらを定義する
フィールドテーブルの隣 = `translate.ts` に置く。画面とインスペクタで値の表記や刻みが食い違わない
ようにするため。

バーの選択は**処理ごとに**保存する (`urx-dyn-display2`・処理をキーにしたレコード。現在は SSMCS バンク
のみ)。この選択は「処理の読み方」であって機種ごとの写像ではないので、メーターポイントと違い機種
スコープにはしない。**保存するのはセグメントの序数**なので、バーのセグメントを振り直すときはキーを
変える — 旧い序数と新しい序数は区別できず、前のキーは 3 セグメント時代の番号 (1 が伝達曲線であって
サイドチェインではない) を保持していた。

曲線は**静的レイヤーのキャッシュ + ライブの点**に分けて描く。点以外はパラメーター / サイズ /
テーマにしか依存しないため。キャンバス のサイズは open と refresh で、テーマトークンは render で読む —
どちらも強制読み取りで、そのフレーム自身の DOM 書込直後のフレームループに置くと同期レイアウトを誘発する。
**他の行の持ち分を変える行 (1-knob / Auto Makeup) はコントロール列を組み直す**が、スライダーは組み直さない
— ドラッグ中に組み直すとポインタキャプチャが外れる。

## 不採用案 (新しい根拠なしに蒸し返さない)

| 不採用 | 理由 |
| --- | --- |
| 曲線の出力軸に入力軸の -72 dB 床を共有 | 工場 threshold では range 定義域の 70% で棚が目盛外。range を -30 → -56 dB に動かしても描画は 0% しか動かない |
| 出力軸を対数圧縮 | dB は既に対数単位で、さらに圧縮すると range が居る深い側がちょうど潰れる。同じ -30 → -56 の移動で実測 8.5% (軸を伸ばすだけの案は 20%) |
| 縦軸を出力でなくゲイン (出力 − 入力) に | 実測 4 案で最も読みやすく (35.6%)、軸がメーター 107 の報告値と一致する。ただし伝達曲線ではなくゲイン曲線になり、1:1 の領域が 0 dB の水平線に潰れてプラグインの慣用句から外れる |
| 出力軸を棚に合わせて自動伸縮 | 棚は常に見えるが、range をドラッグすると線ではなく目盛の数字が動くので、何が変わったのか読めない |
| GR を `monoTaps` の 8 番目として追加 | `tapsFor` は CONSOLE のメーターポイントセレクタの契約。GR が信号用 3 色帯の dBFS ラダーで選択可能になる。固定テストも 2 本壊れる |
| GR を 0〜-30 dB 固定フルスケールに | 工場値 range (-56 dB) で振り切れる。ゲートが仕事をしている間だけ情報を失う |
| GR を range 追従フルスケールに | 振り切れは直るが、共有の目盛列の下で GR だけ別スケールになる。隣の目盛で読めそうに見えて読めない |
| GR に `readingTap` / `decodeMeterDb` を流用 | `readingTap` は OVER センチネルで `over` を立てる。GR では「ON かつ開」を意味するので、素通し中のゲートがクリップ点灯する |
| OUT を IN + GR で導出 | 3 タップは実機が独立に計測する。1 フレーム内で最大の入力と最深のリダクションは同時刻ではなく、足すと出力が数十 dB 低く出た |
| インスペクタにも 5 スライダーを残す | `dynFieldSlider` は render 時の params スナップショットを読み、値変更で再レンダしない。画面側で threshold を動かした後、古い位置のスライダーをドラッグすると古い値が書き戻る |
| 履歴スクロール / レベル分布の表示 | 試作して不採用。ゲートの性質上どちらも読み取りづらい。両案が扱えていた問い (フレーズ間でゲートが落ちるか、ノイズフロアとソースの分離量) が対象外であることを記録として残す |
| 画面内の CH セレクタ | 切替のたびにアドレス集合を再登録することになる。そもそも CH 単位のコントロールから CH 単位で開く |
| CONSOLE の GATE チップへのジェスチャー (ダブルクリック / 右クリック) | ダブルクリックはこのビューの工場出荷値リセットで、`wireActivate` に `detail` ガードが無い。右クリックはアプリ全体で未使用だが macOS の Ctrl+click でネイティブメニューと衝突する |
| レベルレーンにアプリ側 release を足す | 実機のメーターが既に約 30 dB/s で減衰する。二重掛けになる |
| COMP GR を正味ゲイン (リダクション + makeup) と読む | makeup +18 dB の CH でアイドル OVER が出たことからこちらが有力に見えたが、そう読むと makeup を少し上げただけでレーンが役に立たなくなる。実測で否定 — makeup は下流タップを動かし GR は動かさない |
| COMP の GR レーンをレベルと同じ dB/px に | GATE のリダクションは目盛いっぱいに動くが、COMP は数 dB。動かないレーンに見える |
| COMP の曲線からニーを省く | セレクタが画面上で何も変えなくなる (GATE の出力軸で 1 度払った失敗と同型)。幅を測るほうが、フィードバックの無いコントロールを出荷するより安かった |
| COMP 用に画面インスタンスをもう 1 つ持つ | 同じモーダルホストと、セッションが持つ同じ 1 つのメーター購読を奪い合う。処理は open のたびに選ぶ方式にした |
| 実機同様に COMP 曲線上へ T / R / G のグリップを置く | 作ってから外した。グリップを外した押下が下の threshold ドラッグに落ちるため **gain のグリップを押すと threshold が動く**。加えて描画は枠内にクランプ、当たり判定はクランプ前の座標で、軸の端では両者が約 13px ずれていた。2 つの欠陥の下にあるのは「1 枚のプロットの 3 グリップでは押下がどの値を指したか決められない」こと |
| SSMCS の全 18 行を 1 画面に出す | 行だけで約 18 × 42px ≒ 756px。`.consent-box` の `max-height: calc(100vh - 48px)` は既定窓 800px で 752px、`tauri.conf.json` が許す下限 640px では 592px なので、見出し 4 本・題・アクション行を足す前に超え、出荷済み画面が避けている内部スクロールに入る |
| Side Chain を COMP 面の行に畳む | かつては 8 行 1 パネルで、Side Chain トグルが区切りを兼ねていた。バーを分けたことでフィルターは自分のセグメントを持ち、行はプロットに従う — 描かれていない曲線のスライダーは操作者に見える変化を起こさない。各 4 行で、これがこの面を兄弟と同じ高さに保っている量でもある |
| 面の切替を**題の行**に置く | セグメント行が 2 本あると、探しているものがどちらにあるかを操作者が知っている必要があり、題の行の方が見つけにくかった。今は表示列の 1 本にフェイスごとのセグメントを置き (COMP 面は 2 つのプロットが別の問いに答えるので 2 分割)、EQ 面のバンド選択はバーから消えた (マーカーがコントロール) |
| SSMCS MAIN 面にレーンラックを置く | 2 面 + ラックを 1 列に入れると各プロットの描画域が約 152px、高さは 320px 固定なので、EQ 面と同じ +6 dB のベルが 3 倍の勾配に見える。ラックを出さなくてもレーンは購読され読み値も動く — ホストがレーン要素を作るのは descriptor が要求したときだけ |
| 読み値タイルの列数を減らして表示側の幅を作る | 実測: MAIN 面のコントロール列は読み値 2 列でも 3 列でも 350px。`1fr` を並べたグリッドは親いっぱいに広がるだけで、幅を要求しているのは固定幅スライダーを持つパラメータ行。「列に遊びがある」という着眼は正しく、動かす対象が違った — レバーは列の分け方 |
| SSMCS の GR を OUT スロットに重ねる (DUCKER の `sameSlot`) | 列の分け方を変える前は 2 面の横にラックを入れる唯一の手だった。分け方を変えたことで不要になり、しかもここでは有害 — MAIN と COMP は同じアドレス集合を見るので、面ごとにラックが組み替わると「移動のはず」の切替で版面が動く |
| SSMCS EQ 面に Type 行をロックで常設 (4-band 画面と同じ形) | 4-band があの行を残すのは 4 バンド中 2 つが型を持ち、落とすとバンドで高さが変わるから。こちらは 3 バンドとも固定なので、どのバンドでも同じ 1 値のロック行が常設になるだけで、高さ不変にも寄与しない |
| 実機のステータスバーに倣い Out Gain を 3 面すべてに置く | 実機が常時出すのはエンコーダ割当の都合。こちらで複製すると、同じ値が 2 つの面で食い違って見える機会だけが増える |
| Morphing 中は SSMCS の COMP / EQ 行をロックする | Morphing は再計算であって継続する駆動ではない。書いた瞬間に所有は操作者へ戻り、実機の LCD も直後の編集を受ける。ロックは実機が許す編集をアプリが禁じることになる |
| 4-band EQ の実測モデルで SSMCS のプロットを描く | 別 DSP への外挿。4-band のモデルは実測して初めて出た補正を 3 つ必要としており、それがそのまま「測らずに描くな」の論拠になっている |
| DUCKER のリダクションを専用列にする | 列と専用目盛りのぶんの幅を食う。プロットに回せば、窓 1440px でレーン 333 → 235px、Envelope 312 → 410px |
| DUCKER のリダクションを KEY / PRE DUCKER に重ねる | 実測で否定。リダクションは 0 から下、レベルは床から上なので衝突条件は `レベル + \|リダクション\| > 0 dBFS`。入力側のレーンではこれが常態で、工場出荷のレンジではブロックが定規の 93% を覆いバーの頂点が読めない |
| Envelope にライブ表示を載せる | リダクションが数ピクセル右の POST バーにブロックとして出るようになった時点で、同じ量の 2 つ目の表示になった。時間軸はライブの読みに位置を与えないので、上下に動くだけだった |
| DUCKER に Ladder / Envelope のトグルを置く | EQ と同じく両方を同時に出すので選ぶものが無い。見出しが存在しない選択を名乗ることになる |
| 重ねたリダクションのために DUCKER の定規を -70 dB へ広げる | レンジの深い端を買う代わりに全レーンの分解能を薄める。しかも下 10 dB は KEY にとって死んだ領域 (しきい値がそこへ行けない) |
| 注記が切れるので文言を短くする | 器の側が欠陥だった。1 行確保のとき、出荷済みの COMP と EQ の注記は窓幅 約 1150px 以下 (日本語は約 1300px 以下) で既に折り返していた。短くしても次に切れる幅が動くだけ |

## 承知の上のトレードオフ / 注意点

- **ピーク保持時間 (1.2 秒) は純粋に UI 側の裁量**。実機に前例が無い — レベルメーターはハードウェアで
  保持し、GR は一切保持しない。
- **ピーク線の意味がレーンごとに違う** — GR では本質的、レベルレーンでは装飾。差異の明示より
  見た目の一貫性を採った。
- **100 ms 未満のゲート動作は GR に映らず**、どんな UI でも復元できない。この画面はそれを主張しない。
  定常状態のレベル関係を読み、それに対して threshold を置くための画面であって、attack / hold / decay を
  追い込むための画面ではない。
- **微調整モードは COMP Gain だけ。** 実機のパネルノブ押し込み微調整は GATE の全パラメーターで
  **無効**、COMP でも **Gain (makeup) のみ有効 (0.1 dB)** と検証済み。したがって FINE 表示が出るのは
  その 1 行だけで、これはクラス規則ではなく個別実測の結果。

## 編集 → デバイスのデータ経路

インスペクタと同一。`onUpdateNodeParams` がパッチを `plan.nodeParams[id]` の該当する持ち分にマージし
`markChanged()` を呼ぶ。これがプランの dirty フラグ・ライブ同期のスケジュール・MIDI フィードバックを
まとめて担う。BAL モードで STEREO リンクされたペアでは、他のノードパラメーターと同様にグループも
相方へミラーされる。値がどこにあるかは descriptor の担当: GATE / COMP は 1 つのサブオブジェクト、
EQ は `eqBands[i]` と `eqOneKnob` に分かれ、パッチをキーで振り分ける。SSMCS の 3 面は入れ子の形
(`ssmcs` / `ssmcs.comp` / `ssmcs.sc` / `ssmcs.eq.<band>`) を 1 つのレコードへ平らにし、パッチをキーで
分け直す — サイドチェインの 3 値がそこで接頭辞付きなのに、コントロール id では接頭辞を持たない (そこは
スコープがその役を果たす) のはこのため。

**1-knob の書き込みは読み込みとして返ってくる。** `ParamSpec.sideEffect` は 2 つの修復を区別する。
デバイスが動かした値の**所有者が違う**ためだ:

| フラグ | デバイスが動かしたもの | 修復 |
| --- | --- | --- |
| `"converge"` | プランが**著作**する値 (COMP/EQ type 変更で CH ストリップのトグルがクリアされる) | 押し戻す = 書込スコープに対する converge ラウンド |
| `"refetch"` | プランが**鏡映し**ているだけの値 (EQ 1-knob が 4 バンドを再計算する) | 所有ノードを読み直し、スナップショットをそこから採り直す |

2 つの 1-knob — EQ の 3 param と COMP の 2 param — が refetch 側。converge すると操作者の古い手動カーブをデバイス自身の計算結果に
上書きしてしまい、しかも再計算は誰も通知しない: notify 登録はアドレス列挙で、1-knob ON 中は
バンドのアドレスがその集合から外れる (プランが emit をやめる) から。そこで `live.ts` は
device-follow の scoped 経路と同じ device→plan の逆変換を呼び、その後スナップショットを採り直す —
これが無いと、読み込んだ値がすべて次の diff で「未送信の編集」として書き戻される。実機側で同じノブを
回した場合は既にこの経路を通っていた。これは**自分の書き込みに対する同じ修復**である。また refetch は
1 ノード 1 回の読みで converge ラウンドではないので、フラッシュ窓が収束の完了まで塞がれることはない —
1-knob レベルのドラッグがポインタ停止まで待たされていた原因がこれだった。

**refetch は converge を生き延びない。どちらかが譲る必要がある。** 2 つの修復は同じフラッシュに
同居しうる (PAN/BAL と Morphing が同じ 120 ms 窓に入れば足りる) 上に、converge が先に走る。
converge は書込スコープ全体をプランに一致させるので、プランがまだ emit していて実機が今しがた
再計算したアドレスは書込前の値へ戻され、後続の refetch はその converge が残した値を読む。画面には
何も出ず、実機には別のモーフ位置に属する strip を持った Morphing 値が残る。

どちらが譲るかは**その値を誰が著作しているか**で決まる:

| プランはその値を | 何で閉じるか | 該当 head |
| --- | --- | --- |
| **鏡映し**ているだけ | head が入っている間はプランがそのアドレスを emit しない = 誰も押し戻せない | EQ 1-knob (4 バンド)・COMP 1-knob (`COMP_ONE_KNOB_DRIVEN`。COMP 画面がロックしてタグを付ける集合でもあるので、行の所有者について画面と書込側が食い違うことはない) |
| 実際に**著作**している | head が実機へ渡した値を宣言し (`ParamSpec.drives`)、converge にそれだけを触らないよう伝える (そのフラッシュ・そのノードに限定) | SSMCS Morphing・SSMCS Sweet Spot Data |

**この head の 1 つは文字列である。** Sweet Spot Data のプリセットを選ぶと、モーフと同じ 17 本が
再計算される。プリセットは 4 桁文字列なので数値経路ではなく名前書込経路を通る。この経路は
どちらの集合も参照していなかったため、カタログ側で宣言するだけでは効かなかった — `NameWrite` が
カタログ名と所有ノードを持つようになり、フラッシュの名前ループがそこからフラグを読む。
プリセットが**しないこと**はモーフ位置を動かすことで、`93` は中身に関わらずバーストと一緒に
announce されるだけである (Morphing を 62 に置いてから書くと 62 が announce され読み戻しも 62)。
そのため `drives` は 17 本を名指し、`93` は含めない — 含めると操作者が置いたモーフを converge が
復元できなくなる。

使えるなら前者が上である — プランが送らないアドレスは誰にも押し戻せず、正しく保つべき一覧も残らない。
Morphing では使えない: インスペクタが strip の各値を直接編集するので、プランは実際にそれらを著作して
おり、伝えられた converge だけが両者を区別できる。その一覧は推定ではなく実測 — strip の連続値すべてと、
モーフが操作者に残す 5 つの ON スイッチは含まない — で、`live.test.ts` がアドレスで固定している。除外は
converge の読みと**ラウンド送信の両方**に掛かる。掛けないとグループ展開が、一度も比較されていない除外
アドレスを兄弟の差分に便乗させて送ってしまう。

ただし**無料ではなく**、その費用は測れる。実機は書込を ACK した時点ではまだその値に答えず
(`docs/ja/architecture.md`「書込は ACK された時点ではまだ読めない」)、refetch はまさにその同じ ms に発行
される。そのため読み出しはフラッシュの内側で書込を待ち合わせ、1-knob レベルのドラッグの 1 サイクルは
「書込 + 待ち + 読み」になる (通常のパラメーターは「書込」のみ)。レースハーネスで同一ジェスチャを比較すると
**フラッシュ窓 1 回あたり 423/428/432 ms、待ちが無かった時点では 322/334 ms** だった (`t2c-shape-change`。
このケースのドラッグを 10 ステップから 16 ステップへ伸ばしたのはこのためで、短いドラッグには窓が複数
入らなくなった)。同ケースの対照アーム — `sideEffect` を持たない LOW band gain のドラッグ — は 205/200 ms で
変化がない。**実機に再計算させるドラッグだけが払う。**

**そこからの推定ではなく、実機で測った** (2026-08-02・URX44V System V1.3.1.0・修正に診断計装を載せた使い捨て
ビルド)。1-knob LEVEL のドラッグは 10 回のフラッシュサイクルを生み、settle は **10/10 とも実機自身の notify で
終わった** — 書込発行から 42〜203 ms、書込から読み完了まで 58〜298 ms、上限 300 ms には一度も達していない。
つまり費用は実機が告知するまでの窓そのものであり、調整で消せるものではない。上限を下げてもドラッグには効かず、
代替案 (指を離すまで読みを遅らせる) はジェスチャ中ずっと band gain を古いままにするので、プロットは実機が出して
いないカーブを描き続ける。1 ジェスチャの中に複数のフラッシュが実機へ届くという性質は保たれている。
