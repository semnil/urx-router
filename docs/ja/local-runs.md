# ローカルでの走らせ方

> English version: [../en/local-runs.md](../en/local-runs.md)

開発のマシンで、テスト・ビルド・1 回だけの評価を走らせるときの手順。コマンドそのもの、ポートの決まり、
プロセスを止めるときの決まり、dev アプリの起動の確かめ方は `AGENTS.md`「Development」にある。この文書は、
その周りの手順を持つ。

## E2E の spec からライブ同期のセッションを始める

`e2e/tauri-stub.ts` は `LIVE_COMMANDS` を export している。セッションが、読み取りに加えて行う登録の一式で、
ライブ同期を ON にする spec は、これを `commands` に渡す。渡さないと、セッションが成立する前に、開始の処理が
中断する。

開始のボタンについて、2 つ。

- `#btn-live` は `#device-menu` の項目なので、spec は先に `#btn-device` をクリックする。
- 項目を選ぶとメニューは閉じ、項目は隠れたままになる。見えることを待つ形は、通らない。要素が付いているだけの
  状態で、属性を待つ:
  `page.waitForSelector('#btn-live[aria-checked="true"]', { state: "attached" })`。

## E2E のポートに残ったサーバーを見つける

E2E は、ポート 4173 で配る本番のビルド (`race` / `race-webkit` のプロジェクトは、
4174 で配るトレースのビルド) に対して走り、手元では `reuseExistingServer` が有効である: 走ったまま残った
`pnpm preview` (例えば `build:demo` のバンドル) は、`pnpm test:e2e` がそのまま使い、
黙って違うバンドルを確かめることになる。先に止める — そして、
同じ罠が**2 つ目のチェックアウト**も捕まえることに気を付ける: 2 つの実行がポートを共有すると、
後の方は先の方のバンドルを渡され、確かめるはずのコードではないコードに対して通ってしまう。

残っているか、どのバンドルを配っているかは、そのポートが配っているチャンクの名前を読み、
ディスクのビルドの出力と比べる。

```sh
curl -s localhost:<port>/ | grep -o 'assets/main-[A-Za-z0-9_-]*\.js'
ls dist/assets/main-*.js
```

- `index.html` の入口は `/src/main.ts` なので、Vite が出すチャンクは `main-<hash>.js` になる。
- 結果が空でも、サーバーが無い証拠にはならない。別の接頭辞を探すパターンは、生きているサーバーに対しても
  何も返さない。
- ディスクのハッシュと違えば、そのポートは、このツリーが最後にビルドしたバンドルを配っていない。ポート 4174 の
  ビルドの出力は `dist-trace/`。

止める前に、誰のプロセスかを、見つけたのと同じコマンドの中で読む。listener は 2 つのコマンドの間に終わることが
あり、そうなると、誰のものだったかを言う手掛かりが残らない。

```sh
for p in $(lsof -tnP -iTCP:<port> -sTCP:LISTEN); do ps -o pid,ppid,lstart,command -p $p; lsof -a -p $p -d cwd -Fn | grep '^n'; done
```

4173 と 4174 の対は、E2E のサーバー (`pnpm e2e:serve`) のもの。`pnpm tauri dev` が待ち受けるのは 5173 だけ。
コマンドラインと作業ディレクトリから、自分の走行だと分かったときだけ、その PID を止める。

## ほかのチェックアウトと並べてスイートを走らせる

2 つのポートは環境から来る — `E2E_PORT` / `E2E_TRACE_PORT` で、
既定は 4173 / 4174 — `playwright.config.ts` と、web サーバーが引き継ぐ `scripts/e2e-serve.mjs`
の中で読むので、確かめに行く URL と、待ち受けるポートは、1 つの場所から一度だけ決まる。
ポートの対だけでは隔離にならない: 1 つのチェックアウトの 2 つの実行は、
同じ `dist/` と `dist-trace/` にビルドするので、2 つ目のビルドが、
1 つ目が配っているバンドルを上書きする。**`pnpm e2e:worktree` が、
隔離した道である** — ポートの対を**プロセス ID** から導き (空いている対を探すのではなく、
わざとそうしている: 探すことと待ち受けることの間には `vite build` が挟まり、その間に探した 2 つの実行が、
同じ対を選んでしまう)、実行を使い捨ての `git worktree` に置き、
作業中の状態をそこへ運ぶ (追跡している変更はパッチとして、
追跡していないが無視もされていないファイルは写しとして、追跡していないシンボリックリンクは、
同じ先を指すシンボリックリンクとして)。そうしないと、worktree は HEAD をチェックアウトし、
作業ツリーについて報告しながら、最後のコミットを確かめることになるからである。`--keep` はツリーを残す。
`--` の後ろのものは Playwright へ渡す。

## worktree とほかのチェックアウトのカバレッジを比べる

`*.local.test.ts` のファイル (`src/core/control/urxf.local.test.ts`・
`src/core/control/dyn-time-stops.local.test.ts`) は、このリポジトリに含まれないサンプルのファイルを読み、
ファイルが無い場所では、そのケースを skip する。新しい worktree にはそのファイルが無いので、同じコミットでも、
そのケースが通るモジュールの行カバレッジは、ファイルがあるチェックアウトより低く出る。同じコミットの 2 回の
走行で数字が違うのは、入力のファイルの有無で、走行ごとに変わるスイートではない。

前後を比べるときは、両方を同じ条件で測る。両方にサンプルのファイルを置くか、両方とも置かない。

## `work/` の下の作業用のファイル

`.gitignore` は `work/` を無視しない。その直下に置いたファイルは、`git status` に `?? work/` と出る。

- その作業の後まで残さなくてよいファイル (例: プルリクエストの本文の下書き) は、リポジトリの外に置く。
- 残すファイルは、サブディレクトリ `work/<name>/` に置き、そのサブディレクトリの 1 行を、
  `git rev-parse --path-format=absolute --git-path info/exclude` が出す除外のファイルに足す。追加した worktree は
  git のディレクトリを別の場所に持つので、`.git/info/exclude` というパスは無い。このコマンドが出すファイルは主チェックアウトのもので、
  そのリポジトリの worktree が共通で読む。

## `src/` のモジュールを、テストなしで 1 回だけ評価する

`node_modules/.bin` には `esbuild` があり、`tsx` と `vite-node` は無い。関数を 1 回だけ評価するとき (例: 計算した値を
期待の値と比べる) は、小さい入口のファイルをバンドルして走らせる。

```sh
node_modules/.bin/esbuild <entry>.ts --bundle --platform=node --format=esm --outfile=<out>.mjs
node <out>.mjs
```

- リポジトリの外に置いた入口のファイルは、import を自分の場所から解く。`./src/...` は `Could not resolve` で
  落ちる。リポジトリの絶対パスで import する。
- 呼ぶ前に、export のシグネチャを読む。例えば `src/core/eq-response.ts` の `bandResponse` は、周波数を受ける
  関数を返す。周波数の配列は受けない。

## 新しい worktree の最初のビルド

`vendor/urx-lcd-sim` は git の submodule である: クローンと新しい worktree では空のまま始まり、
`pnpm install` はそれを、そのままつなぐ。だから `git submodule update --init` を `pnpm install`
の前に走らせる。

`src-tauri/tauri.conf.json` は、`src-tauri/THIRD_PARTY_LICENSES.html` をリソースとして同梱する。このファイルは git が無視する。
新しい worktree にはこのファイルが無く、最初のビルドは、ビルドスクリプトの `resource path ... doesn't exist` で
落ちる。`pnpm tauri dev` でも、`cargo check` と `cargo test` だけでも、同じように落ちる。

- 配布物を作らないなら、ファイルの中身は読まれない。ほかのチェックアウトのファイルを写すか、CI のジョブと同じ形で
  空のファイルを書く: `echo "" > src-tauri/THIRD_PARTY_LICENSES.html`。
- 本物を作るときは、`src-tauri/` で `cargo about generate` を、`.github/workflows/licenses.yml` が渡している引数で流す。
- worktree の `pnpm tauri dev` のコマンドを人に渡す前に、このファイルがあることを確かめる。

## コミットごとに、単独で緑かを確かめる

変更を複数のコミットに分けたときは、コミットごとに、使い捨ての detached の worktree で確かめる。

```sh
git worktree add --detach <dir> <sha>
```

- `node scripts/check-md-tables.mjs` と `node scripts/check-assets-index.mjs` は依存を持たないので、
  `pnpm install` なしで、そこで走る。
- 終わったら `git worktree remove --force <dir>` で消し、`git worktree list` で消えたことを確かめる。
- git のチェックアウトではないディレクトリへ、コミットを展開しない (`git archive`・`git checkout-index`)。
  `scripts/check-assets-index.mjs` は、無視されるパスを `git check-ignore` に尋ねる。リポジトリの外では、その
  問いに答えが無く、検査は実際には無い指摘を出す。
- コミットは SHA で名指す。`HEAD~2` のような相対の指定は、コマンドを走らせたチェックアウトの HEAD から解かれる。
  シェルが別の worktree にいると、別のコミットになる。

## 確かめるためにデスクトップアプリを起動する

コマンドは、README の dev の行 (`pnpm tauri dev`。experimental の機能を出すときは、後ろに
`-- -- --experimental` を付ける)。

- **ログインのプロファイルを読んでいないサブシェルの `PATH` には、Node も Cargo も無い。** Node の版を
  切り替える道具の shims、Cargo のバイナリ、パッケージマネージャーのディレクトリを、前に足す。
- **SIM ビューが、シミュレーターのフォントを名指す `Failed to resolve import` で読めないとき**は、シミュレーターが
  `node_modules` につながっていない。AGENTS.md「Development」の準備のコマンド (submodule、その後に
  インストール) を走らせる。追跡しているファイルは変わらない。
- **アプリが上がったかどうか**は、ログではなく、プロセスで答える。AGENTS.md「Development」の
  「The dev app being up is a process, not a log line」。
- **アプリは、submodule が指すコミットのシミュレーターを動かす。** シミュレーターのリポジトリでまだ
  マージされていない変更は、アプリに入っていない。見たことを報告するときに、そう書く。
- **`pnpm tauri dev` が古い版や UI を出し続けるとき**は、`pnpm clean` でビルドのキャッシュを捨てて、
  起動し直す (版はビルドのときに `tauri.conf.json`→`../package.json` で埋め込まれるので、
  Vite のキャッシュに残りやすい)。webview が持ち続けるデータ (`localStorage` の同意ゲートなど)
  はアプリの外にあり、`pnpm clean` の対象ではない。
  macOS では `~/Library/WebKit/<productName or identifier>/` を手で消す。
- **ウィンドウを閉じると、コマンドは終了コード 0 で終わる。**
- **止めるときは、自分が起動した `pnpm`・`vite`・アプリのプロセスだけを止める。** コマンドの文字列を読んでから
  止める。同じマシンで、別のセッションの `vite` が動いていることがある。
  ここでパターンが捕まえるもの: `pkill -f "playwright test"` はほかのチェックアウトの実行に当たり、
  広い `pkill -f vite` は操作者自身の `pnpm tauri dev` に当たり、`until ! pgrep -f …` は、
  ほかの人の実行が終わるのを待ってしまう — 相手が、残ったプレビューのサーバーでも、
  止まった Playwright の実行でも、dev アプリでも同じである。

## dev アプリが保存した状態を消す

dev アプリの localStorage (テーマ・機種・メーターポイント・同意ゲート・最近のファイル・インスペクターの開閉・
ユーザーの設定) **と、覚えているウィンドウの配置** (`localStorage` ではなくファイルにある状態 —
`.window-state.json` と、その横の `.window-scale.json`。どちらも消去で消える。
仕組みは [architecture.md](architecture.md)「ウィンドウの配置」にある) を消す方法: ブラウザでは
`http://localhost:5173/?reset` (か `#reset`) を開く (`pnpm reset:storage` がこれを開く。
起動のときに同期して消し、その後で URL から印を外す)。
デスクトップでは `pnpm tauri dev -- -- --reset-storage` で起動する (Rust が `--reset-storage` を読み、
フロントエンドが消して読み込み直す。`reset_storage_requested` のコマンド)。どちらの入口も、
`src/main.ts` の消去の処理に流れ込む。

## 実機に向けた起動フラグ: 端末に届くもの

フラグそのもの — `--experimental --self-test`・`--prepare-modified`・`--reset-storage` — と、
実行が本体に書いている間の編集の決まりは、`AGENTS.md`「Development」にある。

- **`--self-test` と `--prepare-modified` は、最初の起動の同意ゲートを待つ**:
  ゲートを受け入れていないプロファイル (新しく入れたもの、`--reset-storage` の後のもの) はゲートを出し、
  `[self-test] waiting for first-run consent` をログに書き、
  受け入れられるまで何も書かない ([architecture.md](architecture.md)「利用上の同意 (ライセンス表示と免責)」)。
- stdout に届くのは、Rust の `eprintln!` だけである。
  フロントエンドの `console.*` とステータスバーは webview の中にあり、dev サーバーがつながっているときは、
  Vite のクライアントが `console.warn` を `[vite] (client) [console.warn]` として転送する。
- **実行が本体に書いている間の HMR の読み込み直し**は、ページの読み込みであり、ページを読み込むたびに、
  走っているものの上に、もう 1 つの破壊的な掃引が始まる。`take_launch_action` のラッチは、
  1 回だけのフラグがもう一度発火するのを止めるが、実行そのものは始め直す。そして、
  元に戻す所まで届く前に殺された掃引は、本体をかき乱したままにし、取り込んだ元の状態は、
  死んだページのメモリの中にしか無い: 中断されただけではなく、取り戻せない。編集の前にアプリを止める。

## マージの後: `pnpm sync:merged`

決まりは `AGENTS.md`「Conventions」にある。この節は、その決まりが何に立っているかと、
報告されたことにどう動くかを書く。

**プルリクエストがマージされたら、グローバルの規則の後始末が当てはまる** (ローカルのブランチと、
それを運んだ worktree。その規則の 2 つの例外も含む)。ここでは、
worktree の方が高く付く半分である — `reuseExistingServer` と E2E のポートがあるので、忘れたチェックアウトは、
自分がビルドしたバンドルを、後の実行に渡しうる。そうなると、実行は、
確かめるはずのコードではないコードに対して通る。消すときは `git worktree remove <path>` の後に
`git branch -d <branch>` を打つ — git は、`vendor/urx-lcd-sim` をチェックアウトしている worktree
ではこれを断り、`pnpm sync:merged` は、submodule のリポジトリを一緒に消すのではなく、
そういう worktree を残す — `git worktree remove --force <path>` はそれを消し、そのリポジトリも消す。
代わりにディレクトリを消すと、誰かが `git worktree prune` を思い出すまで、
worktree は登録されたまま残る。**Windows では、先につないだ `node_modules` を外す** (`pnpm e2e:worktree` は、
それを主チェックアウトのインストールへのジャンクションにする): Git for Windows
はジャンクションの**向こう側まで**消すので、消す操作が成功してもしなくても、
指している先のインストールを空にしてしまう。`git branch --merged origin/main` は、
祖先を指しているだけで自分のコミットを持たないブランチも挙げる — それは始めていないブランチで、
終わったブランチではない。

**ローカルのデフォルトブランチを早送りするのは、同じ時点の 3 つ目の手順**で、
飛ばされがちな手順である: リモートより遅れたまま残ったチェックアウトは、
自分が持つリビジョンについて答え続ける。だから、デザインシステムのアーティファクトを `src/style.css`
と比べるスクリプトは、マージが足したセレクターを、違うものではなく、無いものとして見る — そして、無いものは、
その出力が見本だけのクラスと呼ぶ入れ物である。`pnpm sync:merged` が 3 つの手順を
1 つのコマンドにまとめているのは、そのためである。

このコマンドは、デフォルトブランチを origin まで早送りし (`vendor/urx-lcd-sim` を、
記録したコミットへ持っていく。手で動かしたときを除く)、ブランチを運んだ worktree を消し、ブランチを消す。
断るときは、何をなぜ断ったかを必ず名指す。決まりは `AGENTS.md`「Conventions」に、
守りは `scripts/sync-merged.mjs` にある。

取得して報告し、`--apply` で動く。**早送りが先に走り、それを止めるものは apply 全体を止める**。早送りが、
消すことを正当にするからである — git には、ブランチが HEAD にマージされているかを尋ねるので、
デフォルトブランチが動くまでは、まさにこれらのブランチについて、答えは「いいえ」になる。
代わりに消す操作の後ろに置くと、計画を読んだ後で作業ツリーが変わったときに早送りが失敗し、
worktree は消えたまま、どのブランチも遅れたまま残る。消す操作は、コマンドを始めたツリーではなく、
デフォルトブランチを持つツリーで走らせる。そうしないと、git はそのほかのブランチについて答えるからである。

このコマンドは、両方の半分にまたがる、自分自身の断る理由を 1 つ足す — ツリーから走っているビルドかサーバーで、
そのファイルが下で入れ替わってしまうもの — プロセスは、そのディレクトリが属する一番内側の worktree で数える。
このリポジトリは worktree を主チェックアウトの中に置くので、単純な接頭辞で比べると、
どれも主チェックアウトとして読んでしまうからである。何が走っているかをマシンに尋ねられないときは、
両方の半分は、そう言いながら進む。そのときは、git 自身の断りが、コミットしていないものとの間に立つ守りになる。

**無視されていることは、作り直せることと同じではない**。そしてここでは、
それはよくある場合ですらない: このリポジトリは、保存したルーティングのプラン、署名の素材、
ほかのリポジトリに属する非公開のチェックアウト、マシンごとの設定を無視しており、消す操作は、
`dist/` に届くのとまったく同じように、そのすべてに届く — git が一度も持っていないので、どこにも写しは無い。
だから、ここでコマンドが書くパスは `scripts/sync-merged.mjs` に名前で書き、
無視されているほかのものがあれば worktree を残す。そして、
追跡している**どの** `.gitignore` に足したパターンも、
そのどちらかに分類されるまで赤になる — ファイルの一覧ではなく git に尋ねる。
ルートの `.gitignore` だけではないからである: `src-tauri/.gitignore` は自分のパターンを持ち、
`build.rs` が生成する権限もその中にある。どこにも分類されないパターンは、
ビルドの出力しか持たない worktree も残してしまう。

**そして、apply が立っている読み取りは、どれも書く時点でもう一度取る。** 消す規則は、新しく読んだ上で、
2 回目を丸ごと問う。だから、worktree に保存したファイル、その中で始めたビルド、ロック、切り替え、
ブランチへのコミットは、計画の前に来ても後に来ても、その worktree を残す — 一度読んだ規則で壊すのは、
どの読み取りでも同じ欠陥である。早送りが書くツリーは、マージの前と後の両方で読み直す。消す操作は、
その 2 回目の読み取りで断れるので、何も壊れない。マージはそうはいかない: `git merge`
もディレクトリに向けられ、走りながら HEAD からブランチを解く。そして、
その隙間にチェックアウトの切り替えが入るのを防ぐロックは無い — index のロックは切り替えを止めず、
worktree のロックが守るのは、消すことだけである — だから、そこへ切り替えが来ると、そのセッションのブランチが、
代わりに早送りされてしまう。**だから、sync はブランチへマージするのではなく、
ブランチを名指す**: ref の compare-and-swap で、ほかの ref は書けない。その後で、
そのツリーの index とファイルをそろえる。これは ref を何も書かない。
残りは順序が担う — その間に切り替えて離れたツリーは、そろえる必要が無い。ブランチはそのとき、
どこにもチェックアウトされていないからである。まだ断りうる半分 (sync が書くファイルへの、
コミットしていない編集、sync が足す場所にある追跡していないファイル) は 2 番目に走るので、
断るときはブランチを元に戻す。

**それでも早送りは、コマンドを始めたツリーでしか行わない**。これが、残りをこのチェックアウトの中に収める。
index の更新の最中に来た切り替えは ref を書かないが、
そのツリー自身の HEAD がもう説明しない index を残す — sync の変更が、ほかの人のブランチに stage され、
その人の次のコミットが運んでしまう — だから、その後でツリーを読み返し、
sync が書いた各パスを、**その**ブランチが持つものへ戻す。それは、その index と作業ファイルの**両方**が、
sync が書いたものをまだ持っている場所だけで、**2 つは別々に問う**: 手で戻したファイルは、
HEAD と同じ作業ファイルの後ろに、sync の版を index の中で隠す。そこでは `git diff HEAD` は空で、
`git status` は `MM` と言い、そのブランチの次のコミットがそれを取ってしまう。
sync の内容がまだ残っているほかのものは、消さずに名指す。そのセッションが、その後で触っているからである。
すでにブランチと一致しているパスは、何も要らない — 書いた後に切り替えが来たときは、どのパスもそうなる。
git 自身のチェックアウトが、途中でブランチの内容を戻しているからである。
代わりにツリー全体をブランチの古い先端へ戻すと (単純に逆向きに読むとそうなる)、
そのブランチがそのパスに正当に持つものを消してしまう。

代償は日常の場合である — sync が残っている worktree から始めると、何も適用されない。早送りが、
消すことを正当にするからである — だから、デフォルトブランチを持つチェックアウトから走らせるか、
後でそこで走らせる。断りは、どのツリーで走らせるかを名指す。それが指示のすべてである。後始末を、
自分にはできないこととして報告するセッションは、その 1 歩手前で止まっている。

**指しているチェックアウトの外に作業ディレクトリがあるシェルから始める**:
シェルがまだそのチェックアウトの中にあると、apply は `SYNC BLOCKED — pid … runs out of …` で止まり、
名指されたプロセスは、それを起動したシェルである — 先にディレクトリを外へ移し、
それから `pnpm -C <the checkout that holds the default branch> sync:merged --apply` を打つ。

**報告が残した worktree は、コマンドが消す証拠を持たなかったもので、残すよう言われたものではない。だから、
持っているもので分ける**: 開いているプルリクエストか、最近のコミットがある — 残す。
違いも自分のコミットも無い — 消す。同じコミットから、また切れるからである。
違いがある — `cmp` と `git hash-object` で、ほかの場所に写しがあるかを探し、
その写しを使い捨ての worktree に当てて、消す前に、どのファイルも一致することを確かめる。
デフォルトブランチに無い文書の変更は、`git apply --check` がまだ当たると言うなら、
プルリクエストとして取り込み直す。実行が中に**いる** worktree は、それ自身の規則で残るので、最後の 1 つは、
次の実行で、デフォルトブランチを持つツリーから消える。早送りするものが無い実行は、どのツリーにも書かないので、
この影響を受けない。ほかの人の pull が早送りを済ませた後に残った後始末が、それである。

`pnpm test sync-merged` は、それぞれの守りを、それが断る配置に対して固定する。
