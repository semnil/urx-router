# 再利用できる資産

> English version: [../en/reusable-assets.md](../en/reusable-assets.md)

リポジトリが既に持っているもの — ハーネス・プローブ・生成器・フィクスチャ・ピンのテスト — のすべてと、
それぞれをいつ使うか。そのどれかを使う・拡げる変更が守る決まりは `AGENTS.md`「Reusable assets」にある。
`pnpm check:assets` は、下の資産の索引を、木と両方向に突き合わせ、読むのは英語の表である:
日本語の訳が照らされるのは、どの文書も照らされるファイルの参照の決まりだけなので、
一方で変えた行は、同じ変更でもう一方でも変える。検査が何を確かめるかは
[repository-checks.md](repository-checks.md)「`pnpm check:assets`」にある。

## 資産の索引

**下にあるものは、どれも作り直す必要が無い。** 日々使うコマンドは AGENTS.md「Development」の pnpm のスクリプトである。
ここにあるのは、それ以外にリポジトリが既に持っているもの — 見落としやすく、二重に作ると高くつく、
ハーネス・プローブ・生成器・ピン — のすべてである。新しい道具を書く前に、`ls scripts/` と
`grep -rn "window.__urx" src/` に 3 分かける価値がある。

**フィクスチャの行は、プルリクエストがそのフィクスチャに公開の呼び出しを足した後、フィクスチャと手で突き合わせる。**
検査が、行にすべての輸出の名前を書くよう求めるのは、その行が目録として書かれているところだけである
(`scripts/check-assets-index.mjs` の規則 E3)。いつそのフィクスチャを使うかを文で書いた行は、
フィクスチャが前に持っていた呼び出しを書いたまま、通り続ける。

**外からアプリを動かす。** 5 つとも本番のバンドルからは静的に落とされ、
`ci.yml` が `dist` をそれぞれの名前で grep する。

| ハンドル | こんなときに使う | 置き場 |
| --- | --- | --- |
| `window.__urxConsole` | CONSOLE の描画やメーターの費用を測るとき、または外からストリップの作り直しを再現するとき | dev ビルドだけ (`pnpm dev`)。その面は `pnpm test meter-bench` が固定する |

| `window.__urxMidiProbe` | 問いが**間隔**であるとき — アプリが送ってからどれだけ後にコントローラーが答えるか、そしてその答えが、入ってくる MIDI を断るのをやめる前に届くか後に届くか。エンジン自身の時計での、時刻つきの rx / tx / エンジンの判断 / ライブ同期の印と、「何も起きなかった」と読める沈黙 (早く戻ったフィードバックの 1 回)。報告は、印ごとに、どれだけ出て行き、最初の返事がいつ届いたかを出す。**トレースのファイルも書く**。置き場はリンク台帳の横で、ページの再読み込みをまたぐ問いに要るのはこれである — ページの中の環状バッファも、それが刻む時計も、再読み込みでやり直すので、調べたいその時点ではバッファだけでは空になる。症状がときどきしか出ず、求めに応じて再現するのではなく捕まえる必要があるときに、このファイルを使う。ハンドルの flush が、読む前にファイルを今に合わせる。ファイルの名前・まとめ方・ローテーションと、インストールしたアプリからこれを外す 2 つのコンパイル時の門は、[docs/ja/architecture.md](architecture.md) の「外部 MIDI コントロール」にある | dev ビルドだけ (`pnpm tauri dev`)。`pnpm test midi-probe` が固定する。このテストは、スタブにしたシェルに対して、そのハンドルを通してシンクを動かす — 開始・記録・flush |

**本物のハードウェアと話す。** デスクトップだけ。Tauri の CLI は 2 つ目の組を渡すので、フラグには `--` が 2 回要る。
1 回だけの動作は、最初に呼んだものが使い切る (HMR の再読み込みはページの読み込みである)。

| 道具 | こんなときに使う | 使い方 |
| --- | --- | --- |
| セルフテストの往復 | 本体に対して、書き込みが忠実であることを示すとき (丸め、無視されるパラメータ、完全な復元) | `pnpm tauri dev -- -- --experimental --self-test` — **フラグは両方**。自動の実行は experimental の門の内側にある |
| 監査の準備の書き手 | シーンの SAVE/RECALL の差分に見せるものがあるよう、書けるスカラーをすべて見分けのつく値に散らすとき | `pnpm tauri dev -- -- --experimental --prepare-modified` (書く。わざと復元しない) |
| 本体と比べる | 何も書かずに、`.urxf` の取り込みを本体と突き合わせるとき | Device メニュー → Compare (experimental)。パラメータごとの全ログ、比べた数、かかった時間 (`src/core/control/client.ts`) |
| `.urxf` の取り込み | 本体の microSD の設定ファイルをプランに読み込むとき | File メニュー (experimental)、またはウィンドウへのドロップ。ライブ同期の間は、取り込みはセッションが本体に書く編集になり、ファイルが本体の時計を変えるところでは、先に尋ねる (`src/core/control/urxf.ts`) |
| 保存した状態を消す | 同意ゲート / モデル / ビューの状態を消すとき | `pnpm reset:storage` (ブラウザ) または `pnpm tauri dev -- -- --reset-storage` |

| --- | --- | --- |

| vitest のワーカーが死んだテストファイルを名指す | 単体の実行が、ワーカーが思いがけず終わったと報告し、1 つのファイルの結果が、何にも名指されずに欠けているとき | `URX_VITEST_WORKER_LOG` にファイルのパスを入れて `pnpm test` を走らせる。すると `vitest.config.ts` が `scripts/vitest-worker-log-setup.mjs` をセットアップのファイルとして足し、各ワーカーは、ファイルを読み込む前に自分の pid とテストファイルを書いた開始の行を足し、ファイルが済んだ後に vitest が終わらせるやり方でそのワーカーが終わったとき (自分で終わるか、vitest が SIGTERM を送る) に、終わりの行を足す。開始の行があって終わりの行が無いファイルがそれで、その pid は、そのワーカーについての OS のクラッシュレポートが持つ pid である。コマンドラインで渡したレポーターは、これを止めない。macOS と Linux だけ: Windows では `vitest.config.ts` がこの変数を断る。そこでは SIGTERM が、終わりの行を書くハンドラーを走らせずにワーカーを終わらせるからである。`pnpm test vitest-worker-log` が固定する。このテストは、フィクスチャのワーカーを殺してログを読み戻す。Windows では、設定の 2 ケース (その中に断るケースがある) と、変数を設定しない実行を走らせ、SIGTERM のハンドラーが要る 4 ケースは名前を挙げて飛ばす |
| 本物の webview を外から読む | 問いが、出荷するエンジンが何をするかで、Chromium のエミュレーションには答えられないとき — OS が動かすメディアの状態 (Windows のハイコントラストが実際に扱った例)、計算されたスタイル、動いているウィンドウを切り取ったキャプチャ | **Windows だけ**: WebView2 の追加のブラウザ引数の環境変数にリモートデバッグのポートを入れて起動し、そのポートが知らせるソケットの上で DevTools のプロトコルを動かす — ページの中で式を評価するか、1 つの要素をその矩形で取る。デバッグのビルドは devtools が有効で、グローバルの Tauri のブリッジに手が届くので、メニューのコマンドを、クリックが呼ぶのとまったく同じに呼べる。**そのソケットは自分で動かす — Playwright をつながない。** `connectOverCDP` は、つないだすべてのページに Playwright 自身のエミュレーションの既定を当て、その 1 つが `forced-colors` を切る。システムの色はハイコントラストのパレットを報告し続けるので、ページは、コントラストのテーマを知っていて、メディアクエリが壊れたエンジンとして読め、計算された背景はすべてアプリのふつうの色で返ってくる。それは、エンジンがすることのちょうど逆である。依存は、Node のグローバルの `WebSocket` と `Runtime.evaluate` / `Input.dispatchMouseEvent` / `Page.captureScreenshot` だけである。ハイコントラストを**入れる**には、アプリの再起動も要る — 動いている WebView2 は、再読み込みをまたいでも、それを拾わない — 一方、既に入っている状態でコントラストのテーマを切り替えるのはその場で効き、**切る**のもその場で効く。だから、どちらの向きも、もう一方を予測しない。**誤りとしてではなく、何も写っていない画像として返ってくるもの 2 つ**: ウィンドウが非アクティブの間は、`<select>` のドロップダウンはまったく開かない (送ったクリック、`userGesture` の評価の下での `showPicker()`、Alt+ArrowDown のどれも、閉じたままにする — そしてクリック自身のフォーカスの輪が、少なくともその入力はページに届いたことを示すので、閉じたポップアップは、入力が失われたのではなく、ウィンドウの状態である。操作者のクリックがウィンドウをアクティブにした後は、クリックと `showPicker()` で開き、Alt+ArrowDown はそこではまだ試していない)。そして、ポップアップはページのコンポジターの外にあるネイティブのウィジェットなので、開いていても `Page.captureScreenshot` には見えない。代わりに Win32 の画面キャプチャで撮る — そして、**プロセスをまたいでアクティブにすることはプローブにはできない** (前面のロックが `SetForegroundWindow` を黙って何もしないものにする) ので、そのキャプチャは、操作者にクリックを頼む**前に** `GetForegroundWindow` の見張りに仕掛け、後には仕掛けない: 操作者の返事が、前面を端末へ戻すからである。macOS に同じものは無い: WKWebView の Web Inspector が手で使う道で、`scripts/meter-bench.mjs` が、そこへ貼り付けられるように書かれているのはそのためである |

**E2E のフィクスチャ — 分けて写すのではなく、これらを拡げる。**

| フィクスチャ | こんなときに使う |
| --- | --- |
| `e2e/tauri-stub.ts` | spec にデスクトップのシェルが要るとき: ファイルの IO、ダイアログ、機器のコマンド、またはライブ同期のセッションまるごと — 本体自身のパネルで行った変更も含む。その変更は、`setDeviceValue` (アドレス 1 つ。読みに種を入れるオプションは、パラメータの id のすべてのインスタンスを一度に埋めるので、1 追従の層は、異なるものがいくつかを超えると機器全体を読み直す — に使うのは `notifyBurst` である。1 回の呼び出しでまとめて届けるからである: 1 つずつ送ると、落ち着くのを待つ処理が途中で発火して狭い道を取ることがあり、それでも結果についてのどの確かめも通ってしまう。`deviceValueOf` は、スタブが 1 (シェルが断る notify の登録など)。`meterAddrsOf` は、アプリが最後に登録したメーターのアドレスを読む — 登録は前の登録を置き換えるので、それがアプリの読む集合のすべてである — そして `pushMeters` は、生のメーターの読みを 1 回分、その登録のチャンネルを通して届ける。シェルが本体の流れを転送するのと同じ形である: 主題が、セッション中にストリップがレベルの何を**示す**かであるときに使う。スタブは、そうでなければ登録に答えるだけで、何も流さないからである。`setHeldWrites` は、名指したパラメータの書き込みに答えずに持っておき、`releaseHeldWrite` が最も古いものを着地させ、`heldWritesOf` がいくつ待っているかを言う — 持っておく読みの、書く側の双子で、次の一歩が書き込みの着地を待つ流れのためのものである。`savedFilesOf` は、保存が書いたもの — プランの文書そのもの — を読み戻す。spec が保存のダイアログと、決まったコマンドの中のファイルの書き込みに答えた後に使える: 問いが、ボードが見せるものではなく、プランが**持つ**ものであるとき (ボードがもう描かないノードのために書かれた場所など) に使う。strings のオプションは、文字列の読みに、パラメータの id とインスタンスごとに答える — ユーザー定義のノブの Function と Parameter 1 — ほかの文字列の読みはすべて、1 つの決まった値で答える。2 つのスタブはどちらも、シェルと同じく、すべてのコマンドに後のタスクで、尋ねられた順に答える — コマンドが記録するものは、送ったときに取られるが、1 つの答えを待ってから次を送る流れは、クリックが戻ったときには、まだ次を送っていない。だから、ケースは `writesOf` や `dialogsOf` を読む前に、流れの終わりの状態 (その状態行、そのダイアログ) を待つ。`e2e/tauri-stub.spec.ts` がその時機を固定する。自分のスタブを持つ spec は、同じ待ち行列を通して落ち着く — 同じページかコンテキストの上の `installAnswerQueue` で、答えはすべて、それが答えるコマンドとともに `window.__urxAnswerLater` に渡す — そして `answerTimingOf` でそれを固定する。これは、送ったタスクの中で落ち着いた答えがあったかと、落ち着いた順を報告する。`untilAnswered` | `pnpm test webkit-tier` | アプリのティアの WebKit のプロジェクトが、静かに縮むこと。`app-webkit` は**タグ**で選ぶので、ケースは、読み手が削除と呼ぶ行を 1 つも消さない編集でそこから外れる — テストの名前を変え、末尾の ` @webkit` を落とすと、`chromium` が持っていたケースをすべて持ち続ける間に、このプロジェクトは 1 ケース少なく走る。その一端は既にうるさい: **何も**集めないプロジェクトは、Playwright 自身の「No tests found」で、`--list` でも実行のときでも exit 1 になる。それに見えないのは、組が**縮む**ことで、それは名前の変更が残す形である。だから、下限は**ファイル**ごとで、`e2e/race/skip-ledger.json` がハーネスのものを持つのと同じやり方である — ちょうどの数ではなく最小で、下限を上回るファイルはどれも表自身の形で出るので、上げるのは貼り付けで済む。そして、下限をまったく持たない、タグの付いたファイルは断る。そうしたファイルは、落ちずに自分のケースをすべて失いうるからである。spec を読むのではなく、**ランナー**に尋ねる: spec を集めるとそれを実行するので、死んだコードの中や文字列の中のケースは決して登録されない。一方「題名を grep する」のどの版も、コメントの中の題名で満たされる。最後の規則が、比べることを比べることのままにする — WebKit のプロジェクトが集めるすべてのケースは、`chromium` も同じ名前で集めるものでなければならない。そうでないと、2 つのティアは違うケースを走らせており、2 つ目のエンジンの判定は、1 つ目が一度も測らなかったものについてのものになる |
| `pnpm check:skips` | **理由**が切れた、恒久に飛ばすレースのケース — どれも `e2e/race/skip-ledger.json` に、それを真に保つテストを名指して登録してあるので、そのテストを消すか名前を変えるとここで落ち、何も保たないものは、何がそれを決着させるかとともに、毎回の実行で出す。「述語が無い」を、沈黙ではなく数のままにしておくのはこれである。spec を読むのではなく、ランナーに尋ねる — `e2e/race` が何を集めるかは Playwright に、そして vitest の**実行**を、ファイルの中の名指したガードに絞って。自分の本体の中から飛ばすガードは、確かめるガードとまったく同じに一覧に出るからである。ファイルと題名の絞り込みは、兄弟のテストを単体の全体の実行に任せ、構造化した結果の名前は、今もあいまいなガードを見つける。この部分の実行は Vitest の結果のキャッシュを切るので、全体のスイートの予定の時間と判定をそのままにする。`scripts/check-race-skips.test.mjs` は、飛ばした・落ちた・無い・あいまいなガードを含む本物のランナーの報告で、検査器を動かす。だから、これはインストールのある `ci.yml` から走る。ハーネスからではない。ハーネスのきっかけは、版を動かさない文書だけのプルリクエストを飛ばすので、文書のマージのたびに、何かが見る前に理由が切れるのを許してしまうからである。**ガードは単体のテストでなければならない**: E2E のケースは、ティアを走らせて — バンドルを作って配って — しか確かめられず、代わりにその宣言を読むことは答えにならない。`test.fixme` は "skip" でない注記とともに集められ、本体の中の `test.skip()` は `--list` に見えないからである。E2E のガードは、2 つの出口を名指して断る。**各プロジェクトが集めるものに下限も保つ** (その台帳の中のファイルごとの最小で、Playwright のプロジェクトごとに 1 つの表): ここのほかのすべては、Playwright が集めたケースについて尋ねるので、集められなくなったケースはそれに見えない — 集めることがまるごと落ちるのでない限り、ケースやファイルまるごとを消しても、どの確かめも満たされたままで、検査は緑になる。WebKit のプロジェクトは、Chromium のものの分け前ではなく、自分の表が要る。ケースはタグを失うことでそこから外れるからである — 読み手が削除と呼ぶ行は 1 つも無く、ファイルのもう一方の数は動いていない。ちょうどの数ではなく最小で、下限を上回るファイルはどれも台帳自身の形で出るので、上げるのは貼り付けで済む。**分け方が要るただ 1 つの読みも取る** — `collect.shardWeights` の下で Playwright が各シャードにいくつのケースを渡すか。それは `.github/workflows/race.yml` が `PWTEST_SHARD_WEIGHTS` として渡す配列で、ティアを、Playwright 自身のシャードの分け方が使うケースの数ではなく、時間で切るためのものである。その読みが何を決め、何が見えないかの 2 つは、`pnpm test shard-weights` の行にある |

## ドキュメントのスクリーンショットと CONSOLE の描画ベンチ

上の索引の「ドキュメントのスクリーンショット」と「CONSOLE の描画ベンチ」の行の裏にある 2 つのスクリプトと、それぞれの実行が何を覆うか。

- `scripts/capture-screenshots.mjs` — ドキュメントのスクリーンショットの取得 (graph + console × EN/JA、dark のテーマ、URX44V) を `docs/assets/` へ。console のショットは、`.con-strips` が収まるようにビューポートを広げる。開発の記事が使う、ダッカーのバイパスの警告 (`screenshot-ducker-warning-*`) も撮る: 既定のプランの USB MAIN OUT B の配線を消し、CH 5/6 をその Rec Point の取り出しからそこへつなぎ直し、そのチャンネルの Ducker を入れる — 記事の画像は、そうでなければ `docs/assets/` の下に原本の無い唯一のもので、UI が変わったときに、ほかにそれを作り直すものは無い
- `scripts/meter-bench.mjs` + `scripts/meter-bench-run.mjs` — CONSOLE の描画ベンチ。1 つ目はページの中のベンチで、合成したメーターの入力からビュー自身の描画のループを動かし (`churn` を付けると、機器の追従のストリップの作り直し / 全体の描き直しも)、描いたフレーム、フレームごとと作り直しごとの JS の時間、DOM の変化、フレームの隙間、イベントループの遅れを報告する。2 つ目は木を配り、それを Playwright の **WebKit** で走らせ、標本をブラウザのプロセスの CPU の時間で囲む。どの実行も `scrollCheck` を持ち、それは**そのエンジンで**、描き直しをまたいでストリップのラックのスクロールのずれを固定する — E2E のスイートの 2 つの WebKit のプロジェクトは、ほかの種類のケースを持つ (`app-webkit` はレイアウトが収まることの不変条件、`race-webkit` は判定がエンジンのものであるハーネスのケース) ので、そこではどれも、この描画の振る舞いで落ちることができない。どちらも `window.__urxConsole` を通してビューに届き、その面は `src/ui/meter-bench.contract.test.ts` が固定する。代わりに本物の機器の入力を測るには、`meter-bench.mjs` を `pnpm tauri dev` のウィンドウの Web Inspector のコンソールに貼る (`__urxBench.run({ feed: "none", live: false })`)
