# リポジトリの検査

> English version: [../en/repository-checks.md](../en/repository-checks.md)

リポジトリの検査とテストのティアが、それぞれ何を確かめ、なぜその形なのか。コマンドと、
変更が守る決まりは `AGENTS.md`「Development」と「Conventions」にある。この文書は、その裏にある説明を持つ。
検査を変える前、そのピンやフックを変える前に、その検査の節を読む。

## `pnpm test` とカバレッジ

`pnpm test` は、次のものに対して vitest を走らせる。

- core: routing/constraints/plan/levels/meters/midi
- control: vd/translate/readback/live/follow/fx/insert-fx/firmware など
- models
- ui: console/graph/inspector/dyn-*/midi/prefs/dom/fine/history/keys/licenses など
- アプリの入口: ブラウザの中の main.boot と main.flows、
  スタブにした Tauri のシェルに対する main.device (main.ts の半分は isTauri() が門になっているので、
  そのシェルが無いと、そこはテストされていないのではなく、届かない)
- [reusable-assets.md](reusable-assets.md)「資産の索引」が挙げる、契約のテストとピン

`include` は、`scripts/` の下の `*.test.mjs` も含む。これはツールそのもののピンで、
カバレッジの対象には入れない。

`pnpm test:coverage` は、同じ単体のスイートを、フロントエンドの TypeScript のソースに対する
V8 のカバレッジ付きで走らせる。2 つのメッセージカタログは外す (理由は `vitest.config.ts` にあり、
同じ除外が `.github/codecov.yml` と `e2e/coverage-options.ts` にもある)。
Codecov のために `coverage/lcov.info` を書く。

## E2E のティア

- `pnpm typecheck:e2e` (`tsc -p tsconfig.e2e.json`) は、`e2e/` と、
  ルートにある設定の `.ts` (playwright/vite/vitest) の型を確かめる。
  src のビルドの tsconfig は `"src"` しか含まないからである。
- `pnpm test:e2e:app` (`--project=chromium`) は、`e2e/*.spec.ts` だけを走らせる
  (routing/hide/notes/insertfx/midi など)。プルリクエストのティアで、`ci.yml` にある。
- `pnpm test:e2e:app:webkit` (`--project=app-webkit`) は、@webkit の印が付いたアプリのケースを、
  WebKit (macOS のビルドが描画に使うエンジン) で走らせる。`ci.yml` の中に自分のジョブを持つ。
  この組が持つのは 1 つの種類 — 狭めたウィンドウでもレイアウトが保たれること — だけである。
  2 つのエンジンが同じように実装していないのは、そこだからである。
  何がこの組に入るかは `playwright.config.ts` が書き、`scripts/webkit-tier.test.mjs` が下限を固定する。
  ケースは、印を失うとこのプロジェクトから外れるからである。
- `pnpm test:e2e:race:webkit` (`--project=race-webkit`) は、@webkit の印が付いたレースのケースを、
  WebKit (macOS のビルドが描画に使うエンジン) で走らせる。

`race` のプロジェクトをどうシャードに分けるか、`--shard` の前になぜ `--` を置かないか、
素の `--shard=k/3` がなぜ CI のシャード k ではないかは、
[live-race-harness.md](live-race-harness.md)「実装と実行」にある。

## `pnpm format`

`pnpm format` は、`check:comments` が読むものから**導いた**ファイルの一覧に対して、
Prettier を `--write` で走らせる。だから、整形の範囲が検査の範囲より狭くなることはない (`scripts/format.mjs`。
設定は `package.json` の "prettier"、`printWidth` は 120)。

**`pnpm format` は、自分のファイルの一覧を持たない。** `scripts/format.mjs` は、
`check:comments` の読む範囲から一覧を取り、そのうち Prettier が解析できるもの — `.ts` / `.mjs` / `.cjs` /
`.js` / `.css` / `.html` — を残す。

重いのは JavaScript の半分である: 出どころの検査が誤って指摘する唯一の形は、整形した文には現れない。
この理屈は整形が届く範囲でしか通らないので、2 つの一覧は 1 つの一覧になる。整形するのは**目録**であって、
読む範囲ではない — この検査は、自分の 2 つのファイルを読む範囲から外しているが、その除外が、
Prettier の見るものを決める理由は無い。YAML は、Prettier が解析できるのに、
わざと外してある — 誤った指摘は JavaScript の形であり、ワークフローとアクションの YAML を整形し直すと、
グローバルの規則が禁じる、整形だけの差分になる (`AGENTS.md`「Conventions」)。

**適合していると書く前に測る**: このツリーの外では、Prettier の `printWidth` の既定は 80 で、
`src/style.css` と `index.html` を適合しないと判定する。リポジトリ自身の設定の外で走らせた検査は、
別の問いに答えている。

**追跡していない**ファイルは、無視の規則が覆っていない限り、書いた時点で、
導いた一覧に入る — 一覧は git が報告するもの (index に加えて `--others --exclude-standard`) なので、
新しいファイルは、追加する前から整形され、検査される。

## `pnpm check:assets`

`pnpm check:assets` (`scripts/check-assets-index.mjs`) は、[reusable-assets.md](reusable-assets.md)
「資産の索引」と `docs/{en,ja}` を、リポジトリと突き合わせる: すべての行と、文書が名指すすべてのファイル —
コードスパンの中でも文の中でも — が本物のものを指し、本物のもので表から欠けているものが無いこと。

行ごとに突き合わせる表は、英語のものである。日本語の文書はその訳で、`docs/{en,ja}` の下のほかのどの文書とも
同じ、ファイルの参照の決まりに照らされる。逆向きの規則のうち 3 つは、索引ではなく `AGENTS.md` を読む:
`package.json` のどのスクリプトもそこで名指されていること (規則 A)、`scripts/` の下のファイルが、そこか
索引から届くこと (規則 B)、そして、どのソースファイルも、それか [architecture.md](architecture.md)
の両方の訳に名指されていること (規則 H)。

## `pnpm check:comments`

`pnpm check:comments` は、ソースのコメントが、コードのすることではなく、
事実がどこから**来たか**を書いていないことを確かめる — `(measured)` という挿入句、方法を名指す文、
取得した日付。

語そのものは対象ではない (`the level meters are measured` は、データを説明している)。対象は形であり、
その組はわざと狭くしてある。言い回しを全部捕まえるほど広い規則は、言い換えを教えるだけだからである。
この検査は、行を grep するのではなく、コメントを字句として読む。だから `Object.entries(measured)` は識別子で、
指摘ではない。テンプレートの埋め込みの中のコメントも、コメントである。JavaScript のファイルは、
字句のゴールによって**一度だけ**読み、割り算や正規表現を強いた読み方で読み直すことはしない。
強いた読み方には文法が無いので、ゴールと違う所で出てくるものは、回復か作り事のどちらかで、
2 つを見分ける手掛かりが無い。しかも、正しく、Prettier で変わらないファイル
(`[/\//, "…"]`・`[/[//]/, "…"]`・`[a / "x///y", "…"]`) を断ってしまう。ゴールは、
`export default` と `break` の後に正規表現を置くことを許し、後置の `!` の後ろに値を残し、修飾子の並びを、
キーワードそのものから辿る。この取引は、この読み方に起こりうる見逃しの種類と、
この読み方では起こりえない誤検出の種類との交換であり、ここでの欠陥は、
正しい答えが 1 つしかない文法のバグになる。

**`pnpm format` は、JavaScript のファイルの一覧を、この読む範囲から取る** (`scripts/format.mjs`)。だから、
どちらか一方だけを狭めることはできない。

この検査は **YAML・TOML・シェル・Python・HTML** も読む。それぞれに専用の読み手があり、
`#` を共通に探すのではない: YAML のブロックスカラーの本文と、行をまたぐ引用符のスカラーは文である。
TOML の `"""…"""` は行をまたぎ、その `#` は前に空白が要らないが、YAML の `#` は要る。
ヒアドキュメントの本文は文だが、その**宣言**の行の残りはコードである。二重引用符の中の `$( … )` は、
またコードになる。

ひとつのスカラーはデータではない: ワークフローの **`run:`** はシェルを持つ — ブロック、**引用符付き**、
または、そのどちらかへのエイリアスである。GitHub は書き方ではなく値を走らせるし、**フロー**のマッピングは
1 行にいくつもの項目を置くからである — その本文は、位置を引き継いだまま、シェルの読み手へ渡す。
値をそのスカラーにするのは、キーの**名前**ではなく、
そこへの**パス**である: GitHub が走らせるのは `jobs.<id>.steps[].run` と、
composite アクションの `runs.steps[].run` だけなので、読み手は、
各行の上で開いているブロックのキーを持ち運ぶ — それぞれが始まる列も一緒に持つ。キーは、その列か、
それより左に書かれたもので閉じるからである。フローのコレクションを開いたときのキーも持ち運ぶ。
`steps: [{ run: "…" }]` は、自分の `steps` と同じ行にステップを置くからである。名前だけで決めると、
`env:` の変数、`with:` の入力、そのどちらかの下にあるものすべてが、
書かれていない文法で字句として読まれてしまう。

**値**: ブロックなら、インデントを外し、ヘッダーが `|` でなく `>` なら**折り畳む** —
2 つの違いはそれだけだからである。インデントを外すのは、ヒアドキュメントの `EOF` が、
インデントした区切りの行とは決して等しくならないからでもある。引用符付きなら、エスケープを解き、
YAML が引用符付きのスカラーを折り畳むのと同じように改行を折り畳む — 1 つの改行は空白になり、
n 個の改行は n-1 個の改行になり、最初の改行の前の `\` はそれをエスケープする。だから、
エスケープした改行はコメントをその先へ運び、空行はそこでコメントを終わらせる — `\n`・`\r\n`・`\r`
はどれも改行として扱う。そうしないと、CRLF のファイルのエスケープした改行は、エスケープした復帰と、
その後の折り畳みとして読まれる。そして、これは `.github/workflows` か `.github/actions` の下でだけ行う。
このツリーで、ほかに run を走らせるものは無いからである。

**どのシェルで字句として読むかは、ステップが選んだシェルで決まる** — `bash`/`sh`・`pwsh`・`cmd`・`python`
のどれかで、`powershell` (Windows PowerShell。GitHub は Windows でだけ走らせる) は、読まずに名前で**断る**。
シェルは、ステップ自身の `shell:`、次にそのジョブの `defaults.run.shell`、次にワークフローのもの、
最後にランナー自身のもの (Windows 以外ではどこでも bash) の順に決める — ステップの `shell:` はその `run:`
の後に書けるし、ジョブの `runs-on` はステップの後に書けるので、値は待ち行列に入れておき、
文書を読み終えてから字句として読む。

PowerShell のブロックコメントは入れ子に**ならない** — 最初の `#>` で終わり、
その後はコードである — その `#` は、**トークン**が始まりうる所でだけコメントを始め、
その文字列はシェルのものと違う: `'…'` は引用符を二重にし、`"…"` は**バッククォート**でエスケープし、
ヒアストリングは `"@` で始まる行まで続き、展開する形は、中身の見えないものではない。どちらの中の `$( … )` も、
文の並びだからである。cmd は、行の始まりの `rem` (前に `@` があってもなくても) と、`::` のラベルを持ち、
`#` はまったく持たない。この組に無いシェルは独自のコマンドラインであり、
宣言を持たない **composite** アクションの run のステップには、頼れる既定が無い。
式で名指したランナーは Windows 以外の既定を取る。2 つの既定は `#` について一致し、
どちらも cmd ではないからである — どの場合も、書かれていない文法で字句として読むのではなく、読まずに残す。

シェル自身の 3 つ: バッククォートの置換は、二重引用符の中でもコードである。
case の**パターン**の `)` には開きが無く、何も閉じない。そして `case` がキーワードになるのは、
コマンドが始まりうる所だけである — この位置は**空白**では終わらずに続き、複合リストを開く予約語、`!`、
そして `time` 自身のオプション (`time -p case …`) も、
同じ行の上でこの位置を続ける — 続けるのは `time` のオプションだけである。どこでも素通しの `-word` にすると、
次の語がキーワードになり、置換を閉じた `)` が、パターンのものとして読まれてしまうからである。
それも次の区切りまでで、`time` が測るのはコマンド 1 つだからである。コマンドの位置、そのオプションの状態、
開いている `case` は、どれも、それを読んだ置換の**枠**に属する。そうしないと、
内側の `;` が外側の位置を開いたままにし、置換を閉じる `)` が、パターンのものとして読まれる。

キーに付けて書いた `[` や `{` も、単独で立つものと同じく、フローのコレクションを開く。そうしないと、
その項目はフローの深さ 0 で読まれ、その値は行の終わりまで続く — それも、ノードが**始まり**うる所でだけである。
ブロックの文脈では、素のスカラーがどちらの文字も持てる (`echo a[0`) ので、それを開きとして取ると、
後に続くすべての行で、コレクションが開いたままになる。フローのコレクションは、
何行にわたって書かれていても**1 つ**のノードなので、それが開く範囲と、その中でまだ待っているキーは、
改行をまたいで持ち運ばれる。その中の行は、ブロックのキーを開かず、閉じもしない。そこでキーをその値へ運ぶのは、
インデントではなく**順序**である。どの行もフローの外で始まるものとして読むと、
アクションの `with:` の入力がステップの `run` のパスで読まれ、値が次の行にある `run:` は、
どのパスにも無いことになる。

引用符付きのマッピングのキーも、エスケープを解けば同じキーである: `"run": |` は GitHub
が走らせるブロックである。キーと値の間には、引用符付きでもブロックでも、アンカーかタグが入りうる — そして、
キーの行がその後で終わるときは、値は、さらに深くインデントした次のノードで、3 つの書き方のどれでもよく、
キーの前のアンカーはその値に属する。そのときヘッダーのインデントの指示子が数え始めるのは、
上の行の**キー**の列であり、ブロックが終わるのもその列である。単独の行に書いたヘッダーは、
本文自身のインデントの位置にあってもよいからである。

**素の**スカラーも、その値である — `run: echo ok` は、ほかの書き方と同じく、GitHub が走らせるシェルである。
YAML は素のスカラーを ` #` で終わらせるので、値に残るのは `;` の後ろの `#` で、
そこはシェルのコメントが始まる所である。スカラーは、ブロックの文脈では行の終わりまで、
フローのコレクションの中では項目を閉じる `,`・`]`・`}` まで続き、**どちら**でも、
続きの行へ続く — 1 つの改行は空白に、空行は改行に折り畳まれる。
フローの続きの行がそれより深くインデントしなければならない相手は、その中に書いたキーの列ではなく、
フローを開いたブロックのノードである。行の**始まり**に何があっても、
すでに始まったスカラーは終わらない: `- b`・`-b`・`?b` は見たままの語で、`x:y` も同じである。
マッピングのキーのコロンの後には空白か行の終わりが要り、そうでないコロンはキーの一部だからである。

**エイリアス**も、その値である — `run: *script` は、そのアンカーが持つシェルである。名前は、
フローのマッピングが終わらせる所では、行ではなく `,`・`]`・`}` で終わる。指摘は文がある行を指し、
いくつのエイリアスがそれを読んでも **1 回**だけ数える。**明示**の項目は、キーを単独の行に書き (`? run`)、
値を運ぶ `: |` を次の行に置く — その間の、ノードではない空行やコメントだけの行をまたぎ、
キー自身の列に置く (普通の書き方は、もっと深い列を取る)。だから、**兄弟**のシーケンスの項目を、
キーが持ったことの無い値と取り違えない。シーケンスの項目は、ダッシュの後に何も書かずに置ける。
そしてダッシュ自身の列で閉じると、**インデントの無い**シーケンス — ダッシュが、
それを持つキーの列にあるもの — は、そのキーを閉じ、その項目を上のマッピングのパスに置いてしまう。

TOML は、複数行の文字列を、引用符の並びの最初ではなく**最後**の 3 つで閉じる。
Python の f-string の置換フィールドは、PEP 701 からコードであり、コメントも含む。一方、
その書式指定はまた文である — そこの `#` は詰め物の文字であり、`!s` の変換は、書式指定を開くのではなく、
式を終わらせる。PEP 750 のテンプレート文字列も同じフィールドを持つので、`t` の接頭辞は `f` と同じように読む。

`/` が正規表現を開くのか割り算なのかは、字句の**ゴール**として持ち運ぶ — 最後のトークンと、
括弧の種類ごとのスタックである — 前の文字では決められないからである (同じ状態が TypeScript
の型の位置にも答える。そこでは、ジェネリックの制約が、
シグネチャ自身の深さに波括弧を置く — 型の文法ではなくキーワードの一覧なので、一覧に無い型の中の波括弧は、
ブロックとして読まれることが今もある。分かっている場合を決めるのは、
`=>` の直後の波括弧は決して宣言の本体ではない、ということである)。型の**引数**の並びは、
値で閉じる — 値を終えるものすべての後で、添字と呼び出しも含む — だから `f<string> / 2` は割り算で、
`a < b > /re/` は比べてから照合する。1 つの文法ではこの 2 つを分けられず、整形した文で分けるのは、
trivia (コメントと空白) の**前**の空白である。Prettier は、比較をすべて空白付きで書き (`a /* c */ < b`)、
型の引数の並びをすべて名前に詰めて書く (`f/* c */ <string>`) からである。

**宣言**の型の仮引数は、代わりにその**本体**で閉じる。そうしないと、
`class C<T> {}` はオブジェクトリテラルを後に残し、次の行の正規表現は、
それへの割り算として読まれる — その前に修飾子の並びを越える。`abstract` と `declare` はその一部だからである。
前にある**デコレーター**も越える。デコレーターの並びは 2 つの段階を持つ — 自分の式を読む段階と、
その対象を待つ段階である — `@sealed` は名前で、`@a.b` はドットの付いた名前で、`@dec(…)` は `)` で終わり、
宣言を決めるのは、並びが開いたときに記録したトークンだからである。その**引数**は、そこから外れる。
型の引数も数える括弧の深さで外す — その中の `{` はオブジェクトリテラルで、その中の `class` は式であり、
`@dec<string>()` は名前と呼び出しの間に並びを置く。メンバー自身のデコレーターは、
その初期化子が持つクラス式の所ではなく、メンバーの所で終わる。型の中には、`<` が比較になる余地が無い。だから、
入れ子のジェネリックのシグネチャは、前に何があってもそれを開き、閉じていない並びを終わらせる `;` は、
型リテラルのプロパティを区切るものではなく、並び自身の括弧の深さにあるものである: `)` は、
呼び出しの後では値を終え、`if (…)` の後では式を始める。`}` は、オブジェクトリテラルの後では値を終え、
ブロックの後では式を始める。`+` は、`a + /re/` では演算子で、`x++ / 2` では後置の `++` の半分である。

この検査は **Rust も**読む。そこではブロックコメントが入れ子に**なり**、raw 文字列は `#` をいくつでも持てる。
先頭の `'` は、文字のリテラルよりも、ライフタイムであることがずっと多い (引用符として消費すると、
次のアポストロフィまで続き、その間のコメントをすべて飲み込む)。

**読む範囲は git が報告するものである** (`ls-files --cached --others --exclude-standard`)。
ディレクトリの一覧ではない: **読む範囲が開かないソースは、検査しないソースである**。
どれだけ上手に字句として読めてもそうであり、根の一覧が答えるのは、どのディレクトリを思い付いたかであって、
リポジトリが何を持っているかではない。書いたがまだ追加していないファイルは範囲に入り、
無視の規則が覆うものは決して入らない。git に尋ねると、答えられないときに、
届く所だけを辿るのではなく、**はっきりと**失敗する。

この検査が読まない 2 つのファイルは、**パス**で除外する: **名前**で合わせると、
ほかのどのディレクトリの下にある同じ名前のファイルも、
ほかのソースと同じように対象になるはずの検査から外れてしまう。**目録と読む範囲は別物である**: `pnpm format`
は前者を、この検査は後者を取る。自分を外すことを目録に混ぜると、整形が、この検査とそのピンを飛ばしてしまう。
`.tsx` は、わざと範囲の外にしてある: JSX の文はコードでもコメントでもなく、
その中の URL は `//` で行コメントを開いてしまう。そしてこのツリーには、その状態機械を書いて当てる JSX が無い。
module を import しても、コマンドラインの部分は何も走らない — どのピンもそれを import し、
import がそれを走らせたら、vitest の argv でツリーを読んでしまうからである。

**`scripts/comment-provenance-baseline.json` はファイルごとの天井である**。
0 を目指す値ではない: ツリーはすでにこの言い回しを持っており、一度の掃除で消すと、ツリーの広い部分にまたがる、
コメントだけの差分になる。ファイルは、持っていた分までを持ってよく、それより多くは持てない。
だから**新しい**ものは赤になり、残りは数えられるまま残る。きれいにしたファイルは、
台帳と同じ形で少ない数を出すので、天井を下げるのは貼り付けで済む。**`--update` は下げることしかしない** —
見つかった数をそのまま取ると、コメントを足し、断られ、update して、違反を中に抱えたまま緑に戻れてしまう。
規則を変えて正当に対象が増えるときは `--reseed` で、これは別の判断として、差分の上でもそれと分かる。

**編集のときのフックも、同じ天井を問う** — どんな指摘でも断ると、台帳が名指すファイルの、
どの編集も断ってしまう — 鍵は、編集したファイルが属するチェックアウトから取る。だから、
このチェックアウトの中に入れ子になった worktree のファイルは、
その worktree 自身の台帳に照らされる — この検査とそのピンは、このチェックアウトの中と同じく、
その worktree の中でもパスで除外する — そして、この中にチェックアウトした別のリポジトリのファイルは、
どの台帳にも照らされない。パスを明示して走らせたときは、そのパスだけを比べる。開いていない行は、
空になった行ではないからである。部分的な `--update` は、読んだ部分からファイルを書き直すのではなく、併合する。

## `pnpm check:pr-assumptions`

`pnpm check:pr-assumptions` は、プルリクエストの本文の前提の欄を、その欄の目的に照らして確かめる: 各項目は、
その観察に要る外のもの (`[hardware]` / `[operator]` / `[other-checkout]`) を名指さなければならない。
3 つのどれも要らない観察は、宣言するものではなく、
プルリクエストを開く前に取るものだからである — 本文はリポジトリの外にあり、マージした瞬間に見えなくなるので、
そこに書いた先送りには、何も続かない。

印の付いた項目には、その下に、どう決着したかを書いた項目も要る — `Result` の項目か、
項目を開いたままプルリクエストを開くという指示を引用した `Left open by the operator` の項目である。
印は先送りを説明するだけで、終わらせはしないからである。この検査は `PR_BODY` (か、
手で走らせるときの形である `--file <path>`) を読み、どちらも渡されない実行は**断る**。
本文を何も読まずに判定を出すコマンドは、書き手が、
これから書く本文についての答えだと受け取ってしまうからである — 空の本文は別の状態で、何も主張しない。

この検査が問うのは、誰かが**書いた**もの — 欄の下の項目と、コロンでラベルから分けた答え — であって、
その横のチェックではない。チェックは、そのどちらとも関係が無い: チェックを問いとして読むと、
誰もチェックを付けなかった箱の下の項目が、すべて隠れてしまう。答えを書いて箱を忘れた人が残すのは、
まさにその本文である。"none" はテンプレートが用意している答えで、
手を付けていないテンプレートは何も挙げておらず、その欄をまったく持たない本文は、この検査の役目の外である。
印が**正しい**かどうかは、メッセージカタログの dev/fixed/tr の印と同じく判断の問題で、この検査は、
判断がなされたことを問う。

`docs.yml` の中で、プルリクエストのときだけ走る。push には読む本文が無いからである — そして、
そのワークフローは、このために edited のイベントを購読する。本文は、後ろにコミットの無いまま変わるからである。

**プルリクエストの本文は `.github/PULL_REQUEST_TEMPLATE.md` に従う。** テンプレートは、
自分の規則を HTML のコメントに書いている。テンプレートが自分について言えず、
`AGENTS.md`「Conventions」が代わりに言うことは、次のとおり: `gh pr create --body` と `--body-file` は、
テンプレートを下書きとして入れるのではなく、**置き換える**。だから、その形でプルリクエストを開くときは、
節を自分で書き直す。チェックは実際に走ったものにだけ付け、付けないものは、横に短い理由を添えて残す。そして、
実機の検証の行には、機種と System のファームウェアを書く。

**前提の欄は答えるもので、先送りには使わない**: 各項目は、
その観察に要る外のもの (`[hardware]` / `[operator]` / `[other-checkout]`) で書き始める。
3 つのどれも要らない観察は、プルリクエストを開く前に取るものである — 書く印が無いので、そこに残すのは、
黙っていることではなく、偽りを書くことになる。印の付いた項目も、
操作者が項目を開いたまま開くよう明示して指示したのでない限り、プルリクエストを開く前に操作者と決着させ、
その結果を項目の下に `Result` の項目として書く。`pnpm check:pr-assumptions` はこれを求める。
`pnpm check:pr-assumptions` は印の無い項目を断り、`docs.yml` は、どのプルリクエストでも、
開いたときの本文ではなく今の本文に対して、それを走らせる — そして、欄を読ませるのは、
箱のチェックではない: その下に書いたものである。

## `pnpm check:gates`

`pnpm check:gates` は、次のことを確かめる: `.github/required-checks.json`
が名指すすべてのコンテキストが、**すべての**プルリクエストで今も報告できること。
GitHub の外のホストから取得するワークフローのステップが、どれも自分の `timeout-minutes` を持つこと。
Codecov へのアップロードが、すべてのレポートが揃った後に 1 つのジョブから、レポートごとに 1 回ずつ行われ、
`.github/codecov.yml` の `codecov.notify.after_n_builds` がその回数に等しいこと。そして、
Codecov が報告する必須のコンテキストには、すべてのプルリクエストでそのアップロードがあり、
`.github/codecov.yml` がそのステータスを有効にしていること。`--ruleset` は、さらにその一覧を、
実際のブランチの ruleset と比べる (admin の `gh` が要る。CI のトークンでは読めない)。

## `pnpm check:skips`

`pnpm check:skips` は、次のことを確かめる: 恒久に飛ばすレースのケース (Playwright が報告するもの) が、
どれも `e2e/race/skip-ledger.json` に登録され、この検査が走らせて通るのを見る単体のテストか、
何がそれを決着させるかのどちらかを名指していること。そして、どの spec のファイルも、同じ台帳が名指す下限を
今も少なくとも集めること — Chromium のプロジェクトと WebKit のプロジェクトで別々に。ケースは、
そのファイルが持っていたケースをすべて持ち続けたまま、タグを失うことで後者から外れるからである — だから、
集められなくなったケースは、小さくなった緑の実行ではなく、赤になる。その台帳のシャードの重みの下で、
集めることも取り直すので、決まった分け方の下で大きさを変えたコーパスや、それを読まなくなった Playwright は、
遅くなるのではなく、赤になる。

各ガードをどう走らせるか、なぜガードは単体のテストでなければならないか、下限とシャードの読みが何を足すかは、
[reusable-assets.md](reusable-assets.md)「資産の索引」の `pnpm check:skips` の行にある。決定は
[decisions/race-harness.md](decisions/race-harness.md)「The permanent-skip ledger」である。

## 編集のときのフック

Markdown の表の行の間に貼った注記は、そこで表を終わらせる。
表を続けるには、**ヘッダーと区切りの行を書き直す**。

`scripts/check-md-tables.mjs` がそれを捕まえる (`pnpm check:md`、`docs.yml`、
そして `PostToolUse` のフック — `.claude/settings.json` は追跡しているので、フックはどのクローンにも届く。
`scripts/md-hook.sh` は、同じきっかけで `check-assets-index.mjs --hook` を走らせるので、
索引 ([reusable-assets.md](reusable-assets.md)) の編集で壊れた資産の行も — `docs/{en,ja}` の編集で壊れた
ファイルの参照も — CI ではなく、編集の時点で報告される。非公開のノートのチェックアウトの中のファイルを
編集したときは、同じフックが、
そのチェックアウト自身の台帳のアンカーの検査も走らせる — 検査は git を通して主チェックアウトの中から探すので、
そのチェックアウトを自分では持たない worktree からも届く — このチェックアウトから行った台帳の編集が、
台帳の取り決めに照らされるのは、こうしてである)。

`PreToolUse` のフック (`scripts/check-startup-wait.mjs`。`.claude/settings.json` の中に、Markdown の検査の横に、
`scripts/startup-wait-hook.sh` を通して登録してある。どちらのフックの包みも、`scripts/hook-node.sh` を通して
node を見つける) は、ログで待つ Bash のコマンドや、バイナリに `pgrep -f` を使う Bash のコマンドを、
コマンドをシェルとして読んで断る — 引用符で囲んだ検索のパターンはコマンドではなく、ヒアドキュメントの本体は文で、
バックスラッシュがエスケープした置換も文であり、ループの `done` の後の grep はその中にない — そして、その
`PostToolUse` の半分は、バックグラウンドの `tauri dev` の起動に、その確かめで答える。バックグラウンドの
コマンドは、終わったときにしか報告せず、アプリはウィンドウを閉じたときに終わるからである。
`pnpm test check-startup-wait` は、断る各形を、それが変異させたもとの、許される形の横に置き、
登録したコマンドを走らせて、つながっていることを示す。確かめが何に答えるかと、なぜログも `pgrep -f` も
答えられないかは、[local-runs.md](local-runs.md)「dev アプリが上がったかどうか」にある。

## 表示項目の目録

**どのダイアログ・ウィンドウ・メニュー・ポップオーバーも、そのメッセージが表示すると言っているものを、
すべて表示し、それは 100% のまま保つ。** `e2e/inventory.spec.ts` は、期待する組をメッセージカタログから導き、
各面をその状態ごとに動かす。だから、**メッセージを足すと、
どこかの面がそれを表示しなければならない** — 足して、何にも確かめられないままにする道は無い。

逃げ道は 4 つあり、どれもそのファイルに*書いておく*必要がある: 別の面がそれを表示する (`elsewhere`。
その面を名指す)。アプリはここでそれを表示せず、実行が、それが無いままであることを確かめる (`neverShown`)。
アプリはそれを、ツールチップか、ほかのラベルの属性でだけ、
わざと表示する (`viaAttribute` — マウスを重ねて出る説明は、表示では**ない**。既定が文だけなのは、
そのためである)。もしくは、もっと大きな並びの中に組み込まれる (`composed`)。**`OUT_OF_SCOPE` は、
緑の実行が証明しないものを、数えられる形で書いたもの**で、グローバルの規則の、
除外の一覧の決まりのもとで増える (`AGENTS.md`「Conventions」)。

この守りが答えるのは**有無であって、配置ではない**: 畳まれた要素や切り取られた要素も、
文が描画されていれば通る。その問いは `ui-capture` の役目である。

## どの検査も見ていないもの: スキルの手書きの半分

スキルは `.claude/skills/urx-routing-planner/` にある。下の `SKILL.md`・`references/`・`scripts/` は、
その中のものである。スキルをアプリとそろえておく規則は `AGENTS.md`「Conventions」にある。

**スキルの手書きの半分は、黙って古くなる。そして 4 つのファイルのうち
1 つは守られている。** `SKILL.md`・`references/plan-schema.md`・`references/device-apply.md` には、
テストもリントも無く、`pnpm format` の外にある。Markdown は `pnpm check:md` が表を確かめ、
`plan_tool.py` のコメントは `pnpm check:comments` が読む — どちらも、
それらが説明する取り決めについては何も知らない — だから、アプリが変わっても、それらは古い取り決めで、
自信を持って答え続ける。

`.claude/skills/urx-routing-planner/scripts/plan_tool.py` は例外である: `pnpm test plan-tool` は、
それとアプリ自身の読み込みを同じ文書に対して走らせ、
文書が読み込みを生き残るかどうかで 2 つが食い違うと失敗する。それが、このツールの主張のすべてである。それで、
同梱のデータが答えられることは覆える。散文のファイルは、データが答えられないことを、今もすべて持っている。

次の **6 つ**のどれかと同じ変更の中で、それらを直す:

- (1) **プランの文書の形** — `serialize` / `deserializeDocument` に足したフィールド。例えば、
  シーンの範囲の `scope:"scene"` は、`sampleRate` とシーンの外の状態を落とすので、
  貼ったプランは「モニターの音源が無い」と読まれ — version
  5 以前の文書では「出力のパッチが無い」とも読まれる。
- (2) **新しい `NodeParams` のキー**。例えば、出力のバスのマスターの `pan`。
- (3) **パラメータの安定についての主張** — insert-FX / FX のセレクターへの書き込みは、**元に戻せない**。
  エンジンの配列を、その種類の既定の値で埋め直す (`control/insert-fx-effect.ts` の頭書きが正である)。
- (4) **`plan_tool.py` が写している、読み込みの門** — `deserializeDocument` の形式と version の確かめ、
  アプリの機種の確かめ、そして**黙って落とす**規則 (知らない kind、正しくない params、有限でない葉、
  配列の 1 つの悪い要素がコレクション全体を落とすこと)。落ちた配線は、深刻な問題ではなく、
  ルーティングの確かめの範囲の外になる。
- (5) **書き込みの UX** — Device メニューの確認 (ファームウェアの食い違い、レートの 3 択) と、
  Preferences の device の範囲。*Scene only* はモニターの音源も microSD の録音の割り当ても書かないので、
  それを中心にしたプランは、本体に届かないままになる。
- (6) **「将来のリリースで使える」という言い回し**。次の出荷で嘘になる。

**ルートの表に決して現れない、意味の上の制約 (信号の流れの順 = プリ/ポストフェーダー、ダッカー) は、
そもそも生成できない**。だから、手書きの実現可能性の注記だけが、
それを運ぶ — 例: チャンネル → USB/SD のダイレクトアウトは、
Rec Point で取り出す = プリフェーダー/プリダッカー。

**スキルはマーケットプレイスのプラグインとしても公開しており、その 2 つの manifest は、
どちらも手で版を付ける。** `.claude-plugin/marketplace.json` と
`.claude/skills/urx-routing-planner/.claude-plugin/plugin.json` は、
それぞれ `version` を固定している。**どちらのファイルも、
読むものが無い** — `skill-export.test.ts` は生成した半分を比べ、`pnpm check:assets` は文書と資産の表を読み、
どのワークフローもそれらを grep しない — だから、入れてある写しには、更新があることが伝わらない。

`SKILL.md`、`references/`、`scripts/` を変える同じ変更の中で、両方を上げる。
