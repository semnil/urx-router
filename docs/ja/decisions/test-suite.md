# Decisions: the test suite

> English version: [../../en/decisions/test-suite.md](../../en/decisions/test-suite.md)

テストの作り方と走らせ方について、閉じた判断を置く。何を決めたか、理由、却下した案、決めるもとになった
出来事を書く。変更が守る決まりは `AGENTS.md`「Development」と「Conventions」にあり、レースのハーネスには
専用の文書 [live-race-harness.md](../live-race-harness.md) がある。この文書は、そこに無い理由だけを持つ。

## The displayed-item inventory

**決定 (2026-08-06)。** `e2e/inventory.spec.ts` は、ダイアログ・ウィンドウ・メニュー・ポップオーバーが
それぞれ何を表示しなければならないかを、メッセージのカタログから導き、それぞれの面を状態ごとに動かす。
決まりそのものと、メッセージが取れる 4 つの逃げ道は、`AGENTS.md`「Conventions」にある。

**実害の記録。** MIDI コントロールを、オーバーレイのパネルから独立のウィンドウへ移したとき、Behavior の列の
凡例のカードが、パネルと一緒に落ちた。そこに出ていた 2 つのメッセージ (`modeDesc` と `buttonModeDesc`) は、
メッセージのカタログに残ったまま、どこからも読まれない状態で、その後のいくつかの版を過ごした。その間、
テストは緑だった。

**理由。** 作業を始める前に、通常の E2E の層で測った値: ダイアログが表示する 202 個の文字列のうち、どれかの
ケースが assert していたのは 76 個 (37.6%)。同意のゲートを見る spec は無かった (spec は `localStorage` で
ゲートを飛ばす)。File と View のメニューは、開閉するだけで、項目は読まれていなかった。前からある 173 個の
`toBeVisible` は、挙動 (ロック・値・開くこと) を見ていて、項目が並んでいることを見るものは無かった。

**却下した案。**

- **面ごとの期待する項目の一覧を、spec に書く。** 面から項目を落とす変更は、同じ編集で一覧からも消すので、
  この種類の欠陥を捕まえられない。
- **面が宣言しているものから、調べる集合を作る。** どの面も名指していない namespace は、「未請求」ではなく、
  見えないものになる。この作り方では、カタログの 681 個の葉のうち 272 個 (40%) しか見ていなかった。集合は
  カタログの全体にして、検査の外に置くものは、理由と一緒に `OUT_OF_SCOPE` に書き出す。カタログに足した
  namespace は、足したその日に走行を落とす。
- **面の文字の全体に対する部分一致で、メッセージを照らす。** 面のどれかで、同じ面の別のメッセージで満たせる
  項目が 25 個あった (`"MIDI CONTROL"` の中の `"ON"`、"Copy the report below" の中の `"Copy"`、`"EQ"` の中の
  `"Q"`)。文字は、要素ごとに、その要素の直下の文字を 1 つの run として集め、ふつうのメッセージは run と
  等しくなければならない。補間や合成のあるメッセージは、最初は run に含まれていればよいとしていた。
  これは 2026-10-10 ([#554](https://github.com/semnil/urx-router/pull/554)) にやめ、合成した文字が区切る位置での
  一致か、run の全体への錨付きの一致にした (`e2e/inventory.ts` の `shows`)。
- **`title` 属性を表示に数える。** この修正の要点は、hover で出る説明は表示ではない、ということだった。
  `title` を数えると、凡例をツールチップに置き換えても通る。既定は文字だけにして、ツールチップが正しい表示で
  ある項目は、`viaAttribute` で 1 つずつ名指す。
- **宣言を unit のスイートへ移す。** 宣言のデータと、それを動かす側を分けるほうが整うが、`elsewhere` の項目は
  「どの spec がどの面を動かすか」を述べる文なので、同じ場所に置く。

**下に置いたもの。** `src/i18n/refs.contract.test.ts` (`pnpm test refs.contract`) は、メッセージのキーが `src/` から
参照されているかを、静的に調べる。上の実害の欠陥は、これがミリ秒で捕まえる (修正の 1 つ前のコミットでは、
`modeDesc` を未参照として報告する)。インベントリが受け持つのは、もう半分の「参照はあるが、描画されない」側。

**範囲の決め方。** 面は、`.hidden = false` を置いている場所を 1 つずつ見て数えた。その時点で 14 個 (モーダル 8、
MIDI のウィンドウ、メニュー 3、ポップオーバー 2 と、最初の数え方が落としていたドロップゾーンのオーバーレイ)。
インスペクタ・CONSOLE・ステータス行・警告のカードは、常設の面で、`OUT_OF_SCOPE` の側にある。ガードが落ちる
ことは確かめた。凡例の 2 行を消すと、6 個のケースが落ちる。

## Unit suite speed and CI workers

**決定 (2026-10-19)。** CI は、vitest が既定で選ぶ数のワーカーで unit のスイートを走らせる。設定には、
ワーカーの数を書かない。

**理由。** CI では、スイートの時間は「ファイルごとの時間の合計 ÷ ワーカーの数」に従い、一番長いファイルは
走行の全体の内側に十分収まる。ファイルをさらに分けても、縮まらない。既定の値を明示の設定として書いても、
何も変わらない。既定より多い数は、CI で走らせていないので、そこでの効果は分かっていない。

**経緯。** デスクトップの device のケースは [#675](https://github.com/semnil/urx-router/pull/675) で機能ごとの
ファイルに分け、後始末の drain は [#677](https://github.com/semnil/urx-router/pull/677) で 18 回の読みに縮めた。
その数の理由は、#677 の説明にある。

## A teardown that does not finish fails the next case

**決定 (2026-10-11)。** デスクトップの unit のケースの後始末が、次のケースが始まるときにまだ走っていたら、
次のケースは、アプリを起こす前に失敗し、後始末が終わらなかったケースの名前を挙げる。変更は
[#589](https://github.com/semnil/urx-router/pull/589)。

**理由。** 前のケースが残したアプリは、テストの側から止められない。`src/core/platform.ts` の `resolveInvoke` は、
呼び出しのたびに `window.__TAURI_INTERNALS__` を読むので、そのコマンドは次のケースのスタブに届く。

**却下した案。**

- **後始末の待ち時間を延ばす。**
- **`src/main.ts` に停止の処理を足す。** テストが前のアプリを止められるようにする案。テストのために製品の
  コードを変えることになる。

**実害の記録。** あるケースが device の読みを保持し、その解放を、各 `afterEach` の後に走る場所に登録していた。
読みを保持したままだと、ファイルの後始末は device のリンクを待ち続け、フックの時間切れになり、時間切れの後も
走り続けて、その間に始まった次のケースのページを drain して復元した。2 件目の失敗 (前提が成り立たない) は、
この巻き添えで、アプリの欠陥ではなかった。

## E2E serves the production build

**決定。** E2E の Web サーバーは `pnpm e2e:serve` で、本番のビルドを `vite preview` で配る。E2E は dev サーバーに
対しては走らせない。

**理由。** dev サーバーに対して走らせていたとき、`fullyParallel` で始まるケースが、空の `#model-picker` を
見つけることがあった。原因は、dev サーバーがモジュールを要求のたびに変換することと、依存を最適化した後に
ページを再読み込みすることだった。

## The startup check

**決定 (2026-10-10)。** dev アプリが上がったかどうかは、`node scripts/check-startup-wait.mjs --pid <tree>` が答える。
ログで待つコマンドは、フックが断る。仕組みは `AGENTS.md`「Development」にあり、変更は
[#564](https://github.com/semnil/urx-router/pull/564)。その中の 2 つの決定:

- **検査が見るのは、今のユーザーのプロセスだけ** (`pgrep -x -u <uid>`)。ほかのユーザーのプロセスの作業
  ディレクトリは `lsof` で読めないので、それを含めると、答えが「判定できない」になる。
- **フックは、コマンドをシェルとして狭く読み、シェルの構文の全体へは広げない。** わざと断らないもの:
  引用の中の語、ヒアドキュメントの本文、バックスラッシュでエスケープした置換、ループの `done` の後の grep。

**実害の記録。** この検査ができる前、起動の判定を、毎回違う形で、何度も外した: ラッパーの終了がビルドを
止める形の起動、プロセスが持っていない絶対パスへの `pgrep -f`、シェルの引用で壊れたパターン、色の付いた
`Running` の行には含まれない固定の文字列、「上がった」を判定する式を持たない背景での起動、手で閉じた窓を
クラッシュと読んだこと。

## Values that change with module evaluation order

**決定 (2026-09-23)。** モジュールの評価の順の欠陥は、コンプレッサーの Ratio の段
([#506](https://github.com/semnil/urx-router/pull/506)) とは別のプルリクエスト
[#509](https://github.com/semnil/urx-router/pull/509) で直した。#506 は、自分の表を葉のモジュール
`src/core/control/comp-ratio.ts` に置いて、同じ問題を先に避けてあった。

**何が悪かったかと、直し。** 仕組みは #509 の説明にある: 互いを import して循環するモジュール、まだ初期化
されていない束縛からモジュールのスコープで組まれる表、そして、それが表に出る順で循環に入るのは unit の
テストだけであること。`src/core/control/vd.ts` を葉にして、`pnpm test module-order.contract` が守る。

**測った値。** 直す前は、`vd.ts` から入る順でだけ、表の 21 個の項目が食い違った。直した後は、7 通りの入口の順
(循環に残る 6 つのモジュールと `vd.ts`) で、食い違いは無い。直しを戻すと、ガードは 22 個の項目で落ちる。
