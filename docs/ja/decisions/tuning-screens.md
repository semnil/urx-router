# Decisions: the channel tuning screens

> English version: [../../en/decisions/tuning-screens.md](../../en/decisions/tuning-screens.md)

調整画面 (GATE・COMP・EQ・DUCKER・SSMCS・INS FX・FX EFFECT) について、閉じた判断と、その周りで起きたことを置く。
画面の仕組みと、却下した設計は [channel-tuning.md](../channel-tuning.md) にある。先に読む表は
「不採用案 (新しい根拠なしに蒸し返さない)」。この文書は、その仕様に無い経緯を持つ。CONSOLE 自身の判断は
[console.md](console.md) にある。下の「操作者」は、このプロジェクトの作業を指示し、決める人のこと。

## Meter subscription

**決定 (2026-08-15)。** アプリが持つメーターの購読は、同時に 1 つ。これは、このアプリの持ち方で、実機の制限では
ない。ワイヤに、購読という単位は無い。登録はアドレスごとに行う。1 つなのは、シェルが、登録済みのアドレスを消して
から、次の集合を登録するため。複数を持つこと (使う側ごとの集合と、参照カウント) は、技術的にはできる。それは
**検討しない** (操作者の判断)。もう提案しない。仕組みは、channel-tuning.md の「メーター購読の所有権」にある。

**実害の記録: 2 つの持ち主の継ぎ目を、5 回踏んだ。** 購読を解除するハンドルは、その購読のものに見えて、実は
グローバルだった。古いハンドルが、今の持ち主を、黙って取り消せた。世代のスタンプと、貸し借りの
`Console.metersLent` で塞いだ。踏んだ 5 回:

1. 画面が購読を取る側だけを実装していた。
2. CONSOLE が `render()` の末尾で取り返していた。画面を CONSOLE から開いたときだけ起きた。
3. 飛んでいる途中の登録が解決して、もう一方の持ち主の登録を消した。
4. 面の切り替えで、登録が 2 本同時に飛んだ。遅い方が後に着いて、残った。
5. その失敗が `onMeterError` に届いて、生きているセッションを落とした。

後ろの 2 つは、登録を直列にし、世代で守る形で直した ([#390](https://github.com/semnil/urx-router/pull/390))。
**次のダイナミクスの画面を足す前に、世代のスタンプが置いている前提を確かめる。**

## SSMCS

- **`persistSel` を持つのは、COMP の面だけ。** 最初の版は、3 つの面のどれにも持たせなかった。根拠は「MAIN と COMP
  にはバーが無い」だった。伝達曲線を COMP の面に戻したとき、その根拠は無くなっていた。
- **確かさの違いを、線の種類で表さない。** 読み値に基づく 2 本の曲線の片方だけを破線にすると、絵が「こちらは
  確かでない」と言う。曲線が置いている前提は、文章の側に書く。
- **角のモデルは [src/ui/dyn-ssmcs.ts](../../../src/ui/dyn-ssmcs.ts) に置く。
  [src/core/control/vd.ts](../../../src/core/control/vd.ts) へは移さない** (2026-08-16 のレビューで検討し、却下した)。
  `vd.ts` の `ssmcs*` の関数は、1 つのパラメータの raw 値を、表示の単位に直す。角は、2 つのパラメータから出る値で、
  実機は表示しない。移すと、角の床・膝の届く範囲・メイクアップの分数が、元の側に残る。1 つの伝達モデルが、
  2 つの層に割れる。サイドチェインと EQ の応答は、core にある
  ([src/core/eq-response.ts](../../../src/core/eq-response.ts))。この非対称は前からあり、コンプの側だけを動かす
  理由にはならない。
- **MID バンドの Q の法則は、出荷していた描画ごと切り替えた** (2026-08-16、
  [#404](https://github.com/semnil/urx-router/pull/404))。操作者に上げた問いは「出荷している絵が変わる変更を
  入れるか」で、答えは「入れる」。「読み値は揃っていて、絵が変わる」案件を、コメントに書いて先送りにしない。

## EQ screen

今の画面は、channel-tuning.md の「EQ」「パネルの高さは変わらない」「1-knob とデバイスの持ち分」にある。インサート
エフェクトの分は、同じ文書の「1-knob は操作者のコントロール」にある。そこへ至るまでの経緯を置く。操作者が
途中で取り下げた決定を含む。

- **Ladder のタブを消し、その位置にバンドのセレクタを置いた。** mono CH の HPF は、EQ のプロットに重ねない。
  COMP を通る経路で、特性が変わるため。
- **位置を示す印は「マーカー」と呼ぶ。** 「ハンドル」と「グリップ」は、ドラッグできることを含む。この印は、
  つかませない設計になっている。
- **取り下げた決定: 「バンドの行は、ロックして見せる」。** 1-knob が ON の間は、行を隠す。高さは変えない。行は
  `visibility: hidden` で残し、タグと見出しのピルも、見えないまま残す。
- **フィルタの型でも、行は消えない。** Parameters は常に 5 行。パネルの高さは、E2E で固定してある。
- **取り下げた決定 (2026-08-29): 「壊す副作用を持つコントロールは、読み取り専用にする」。** M.B.Comp の 1-Knob と、
  Pitch Fix の MIDI Control は、「ON にすると値が失われる」ことを理由に、書けなくしていた。操作者は、2 つの理由で
  却下した。COMP と EQ の 1-knob は同じ性質のまま書けるので、この 2 つだけが例外になっていた。値が失われるのは
  操作者が頼んだとおりのことで、止める理由にならない。**決まった形は、拒否ではなく、駆動集合。** 書く側は、実機が
  計算し直すスロットだけを送らず、画面はそのスロットをロックする (`mbcDeviceDriven` と `pitchDeviceDriven`。
  `COMP_ONE_KNOB_DRIVEN` と同じ形)。M.B.Comp の駆動集合は 15 スロットで、Out Gain だけが操作者のもの。「Attack・
  Release・クロスオーバーは、1-Knob を ON にしたときに 1 度上書きされるだけで、その後は自由」という前の読みは、
  誤りだった。
- **`DynScreen` の一般化は、1 度で行った。** ducker とインサートエフェクトまで見込んだ。ホストは、どの処理を
  出しているかを知らない。
- **`--head-h` を 252 px から 276 px にした。** Hi-Z を持つジャックを読むストリップは、余白が 0.9 px しか無く、
  19 px はみ出していた。
- **level を回しても、カーブが動かなかった。** `sideEffect` を `"converge"` と `"refetch"` に分けて直した。

## Tags on a card

**決定 (2026-09-05、[#465](https://github.com/semnil/urx-router/pull/465))。** カードの上のタグは、1 つの作り方に
する。`.gt-knobtag` と、グリッドの中の `.prefs-lock` が、フォント・枠・余白・インクを共有する。グリッドの外の行は、
前からの設定のピルのまま。

**絵で却下した案。** 調整の行にも同じ面を配る案を、実際に描いた。アクティブでない EQ の行が、画面でいちばん濃い
要素になった。

**除外は、規則ごとに書き分ける。** 12 音の鍵盤の行 (`:not(:has(.gt-notes))`) が外れるのは、積み方だけで、面は
外さない。列をまたぐ行には、タグを積む高さが無い。タグの出入りで、モーダルが伸び縮みする。

**結果。** ピルは 117.3 px で、114.9 px のカードから、左右に 1.2 px ずつはみ出していた。今は 98.7 px で、余裕は
8.1 px。APCA の Lc は、ライトで 76.2 → 67.0、ダークで 72.8 → 74.2 (床は 60)。

## Wiring to follow

- **画面の `refresh()` は、追従の反映に配線してある。** 無いと、実機で動かした値が、画面のスライダーに出ない。
  同じ種類の面を足すときも、同じ配線が要る。
- **`refresh(changed?)` の範囲のガードを置ける位置。** 変わったノードが、画面の描くノードに 1 つも無いときに
  作り直しを飛ばすガードは、`syncBank`・`rebind`・`resubscribeIfMoved` の**下**に置く。この 3 つは、反映のたびに
  走る必要がある ([src/ui/dyn-screen.ts](../../../src/ui/dyn-screen.ts))。ガードが見るノードの集合は、3 つを含む:
  束縛したノード、`attachTo` のホスト、KEY の配線が始まるノード (ducker の KEY のレーンは、別のノードの Rec Point
  を読む)。**full の分岐の `refresh()` には、ガードを付けない。** 2 つの reconcile のフックは、変わったノードの集合に
  何も足さないので、そこでは、空のリストがふつうになる。
