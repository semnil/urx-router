# Decisions: the CONSOLE

> English version: [../../en/decisions/console.md](../../en/decisions/console.md)

CONSOLE ビューについて、閉じた判断と、その周りで起きたことを置く。ビューの仕組みは
[console-sends.md](../console-sends.md) と [architecture.md](../architecture.md)「CONSOLE ビュー (ミキサー型レベル一覧)」にある。
この文書は、そこに無い経緯を持つ。下の「操作者」は、このプロジェクトの作業を指示し、決める人のこと。

## Controls a rate ceiling stops were still live on the CONSOLE

**起きたこと (2026-08-29)。** インスペクタの上にある 3 本の警告は、サンプルレートが実機に掛ける上限を名指して
いた。一方で、ストリップの側では、その上限に掛かるコントロールを操作できた。操作者が指摘し、ビューを端から
見直して、4 か所が見つかった。

- INS FX の面には、ツールチップだけが付いていた。
- その横の開示 (`▸` / `+`) は、そのまま操作できた。
- `F2` の Send の列の 3 つのコントロールは、実機が動かしていないバスへ書けた。
- `.con-sl.readonly` の CSS の規則が無かった。クラスと `aria-disabled` は付いていたので、スクリーンリーダーには
  無効で、目には有効に見えた。

**決定。** 扱いは、console-sends.md の「レート上限がコントロールに何をするか」と「レートがバスごと落とした列」の
とおり。面は残して読み取り専用にし、理由を添える。上限で開く先が無くなった開示は、描かない。述語は
`nodeRateDisabled` の 1 つにして、グラフの `disabledNodes` と CONSOLE が同じものを使う。前は別々だったので、
グラフがノードを減光しているのに、CONSOLE がその Send を操作できる状態になっていた。

**幅のテストの仕方。** 開示を描かなくしたときに、横の面の幅が変わったことがある。描いた結果の寸法を見る
テストでは、これを捕まえられない。行に隠しのプレースホルダがあると、伸びる面も、幅を宣言した面も、同じ幅に
なる。そのため、テストは宣言の側、つまり面の `flex-grow` と `flex-basis` を読む (`e2e/ratewarning.spec.ts`)。

## Closed decisions on the CONSOLE

下の項目は、意図して決めたもの。そろえるべき不一致ではない。新しい根拠が無ければ、もう一度は提案しない。

- **(a) 3 つの MUTE は 1 つの仕組み。** 入力 CH の MUTE、MIX の MUTE、STEREO への Send の ON / OFF (TO ST) は、
  実機の V1.3 のファームウェアから同じもの。「ストリップの種類ごとに別の機能」は読み違い。
- **(b) 電源 LED と OSC は、ON を正の向きにする。** MUTE の向きにそろえると、ボタンの名前が「OFF」になる。
- **(c) ストリップの頭の高さは、いちばん高い MAIN にそろえる。** フェーダーとメーターを、ラックを通して同じ高さに
  置くため。
- **(d) 数値は、実機の LCD が出す精度で出す。** 正規化しない。
- **(e) ラベルは `C.INT`。** `CUE` だけでは、実機の単発の CUE ボタンと読める。`CUE Int` は 2 行に折り返す。
- **(f) オーディオの send は、2 つの言語で「Send」と書く。** **(g) `SEND PAN` は英語として正しい** (名詞を
  修飾する単数形)。語の決定は [localization-and-documents.md](localization-and-documents.md) の
  「The audio send is written send」にある。
- **(h) Send を -∞ まで下げても、接続は残す。** 決まりは console-sends.md の「スロット」にある。
- **(i) MIX のマスターの ON は、CONSOLE から変えられる** (電源 LED)。インスペクタだけの項目には戻さない。
- **(j) Pan Link の下でも、表記は BALANCE。** 実機の LCD がそう出すため。最初の仕様は PAN だったが、実機で決めた。
- **(k) メーターの床 (-96 dBFS) と、フェーダーの目盛りの -∞ は、意図してそろえていない。** メーターに -∞ は無い。
- **(l) GRAPH と CONSOLE が違う値を出すことは無い。** 同じプランを描き、編集は 1 つのファネルを通る。非対称に
  見える所は、挙げ終えて、意図したものと確かめてある。
- **(m) インスペクタにだけ置いている詳細の項目は、そのまま置く。** ストリップに合わない。出す候補で、開いたままの
  ものは無い。
- **(n) フェーダーと Send に、Shift の微調整は付けない。** 実機に、それらの fine が無い。実機で確かめてある。
- **(n2) Clip Safe の切り替えは、CONSOLE に足さない。** 誤って押すのを避けるため。Clip Safe が効いている**状態**は、
  CONSOLE とインスペクタに出す ([#659](https://github.com/semnil/urx-router/pull/659))。形は、描いた画像で比べてから
  決めた。
- **(o) Send のポップオーバーに、メーターは置かない。** 実機は、Send ごとのメーターを持たない。
- **(p) 再描画は、何も壊さないのが契約。** メーターの弾道とフォーカスを引き継ぎ、同じタスクの中で描き直す。
  スクロールの位置は、意図して引き継がない。保存と復元は、レイアウトを強制する (architecture.md の
  「CONSOLE ビュー (ミキサー型レベル一覧)」)。ライブ同期中のちらつきの報告は、まず、この契約が保たれているかを見る。
- **(q) 直接の追従でも、ストリップを丸ごと作り直す。** 項目ごとの更新の対応表を CONSOLE の側に持つと、読み戻しと
  変換の表と二重になる。表から漏れた項目は、黙って古い表示のまま残る。
- **(r) 行を押さえている間は、再描画を待たせる** (2026-08-14)。値は、プランと実機にすぐ届く。待つのは描画だけで、
  押下が終わるまで。その間、画面が古い値を出すという代償は、操作者が受け入れた。「押さえている間も、その場で
  更新する」は、もう提案しない。待たせる目的は、押したままのポインタに、生きたコントロールを渡さないこと。値の
  更新も、行の差し替えを起こしうる。仕組みは、architecture.md の「インスペクタ再描画と IME 合成」と、
  channel-tuning.md の「ジェスチャの途中でウィンドウを奪われたとき」にある。

## Meters

**決定。** ストリップのメーターのタップは、そのストリップのポップオーバーで選ぶ。既定は、いちばん下流のタップ
(POST)。右上に、ストリップをまとめて切り替えるバーは置かない (操作者の判断)。選んだタップは、機種ごとに保つ。

**実害の記録。** ステレオ入力のメーターは、ステレオペアの位置で指す。mono CH の本数が、ペアの始まる位置をずらす。
最初の実装は、URX44V で較正した 1 つの表を、機種を問わず使っていた。URX22 では、ステレオのメーターが 1 ペア分
ずれた。これを隠していた原因は、`getTapsMap(undefined)` が URX44 の表に落ちること。E2E のメーターのケースは
URX44V で走るので、機種の id の配線が欠けていても、通っていた。配線は、ユニットテスト
[src/ui/console.test.ts](../../../src/ui/console.test.ts) で固定してある。表の衝突の監査は、機種ごとに走らせ、空の
表を通さないガードを付けた。

## Render cost during Live sync

**決定 (2026-08-31。フレームのゲートは 2026-10-10)。** メーターのコストは、描いたフレームの数で決まる。要素の数や、
画面に見えているかどうかでは決まらない。そこで、次のように決めた。

- **一部だけ止めること、画面の外のメーターを間引くことは、しない。** ラックのうち 1 本だけを描いても、メーターが
  画面に 1 つも無くても、コストはほとんど変わらない。変わるのは、描画を止めたとき。
- **遮蔽と最小化を見つける、アプリ独自のゲートは作らない。** そこでは、OS とエンジンが、既に負荷を下げている。
  アプリ自身の状態で判定するガード (モーダルが開いている・ビューが隠れている) は、ウィンドウが隠れている間も
  成り立つので、その場合を含む。
- **`.live` に付けた `will-change` は、そのまま。** 外すと、コストが上がる。
- **30 fps のゲートは、今のまま。** 60 Hz の画面では、毎秒 30 フレームより少なく描く。緩めると、CPU と引き換えに
  滑らかになる。操作者は CPU を取った。ゲートの説明は、architecture.md の「CONSOLE ビュー (ミキサー型レベル一覧)」
  にある。

**却下した案。**

- フレームの中で `offsetLeft` を読んで間引く: 読みがレイアウトを強制し、省ける分より高く付く。
- `contain: layout paint`: 合計は変わらない。
- `content-visibility: auto`: 狭い幅ではコストが下がる。ただし、paint containment が常に掛かる。`.con-strip` の
  `min-height: min-content` が作る溢れが、ラックのスクロールの領域へ渡らなくなる。アプリが出荷するエンジンでは、
  アプリ自身の最小のウィンドウの大きさで、ストリップの下端へスクロールで届かなくなった。もう提案しない。

最後の件を受けて、レイアウトの不変条件は、出荷するエンジンでも走らせている
([#442](https://github.com/semnil/urx-router/pull/442))。コマンドは `CLAUDE.md` にある。

## Following the unit

**決定 (2026-10-10)。** デバイス追従での作り直しは、常に掛かるコストではない。作り直しを頼む呼び出しは、notify か、
書き込みが落ち着いたときから始まる。`isEcho` が受けた値を落とすのは、送った値と等しいときだけ。そのため、実機が
丸めた自分の書き込みのエコーと、converge や読み直しの後に実機が計算し直した値は、実機の側の変更として数えられ、
作り直しを起こす。これは受け入れて、閉じた。この決定の元にした実機の記録では、書いた値は丸められずに返った。
計算し直した値での作り直しは、追従が役目を果たしている姿。

## Level grid

**決定。** レベルの刻みから外れた値は、読み戻しとファイルの読み込みでは、そのまま受ける。次にそのコントロールを
動かしたときに、刻みに合わせる。入口を 1 か所に集めて、そこで刻みに合わせる案は、検討して見送った。実機の細かい
刻みと、UI が出す刻みの関係は、整理ではなく、正しさの問いになるため。

## Fixed sends

**決定。** CONSOLE はレベルを調整する画面で、ルーティングはしない。`setSend` は、今ある配線のレベルを変えるだけ。
Send を -∞ まで下げても、配線は残す。

**却下した案。** -∞ の Send を隠す: フェーダーを下まで下げた瞬間に、そのコントロールが消える。

## Linked pairs

**決定。** ペアの 2 つの CH の間でミラーするかどうかを決めるのは、Signal Type のリンクで、PAN / BAL のモードではない。
モードが決めるのは、Send のパンの扱いだけ。BAL では、ペアが 1 つのバランスの値を共有するので、2 つの CH に書く
(外すと、食い違う)。PAN では、CH ごとに持つので、コピーから外す。

**ミラーを、編集のファネルごとに当てている理由。** ファネルの下に、プランの変更が必ず通る 1 つの層が無い。今の
作りでは、ファネルが正しい高さになる。相方の描き直しは、編集の細かさに合わせる。チップはすぐ、ノブは確定のとき、
フェーダーはその場で。

## Fader travel

**決定。** MAIN のフェーダーの溝は、6 px の inset のままにする。ミニフェーダーの溝は、高さいっぱいに直した。MAIN
では、キャップが端を覆っているので、直して得るものが無い。この問いの残りの 2 つは、別の所で決着している。MAIN
のフェーダーは、キャップの上で押すと、掴むだけで書かない (architecture.md の「メインフェーダーの押下」、
[#340](https://github.com/semnil/urx-router/pull/340))。列のフェーダーの相対ドラッグは、MAIN と同じ可動域を使う
([#571](https://github.com/semnil/urx-router/pull/571)。最初は据え置きとし、2026-10-10 にそろえると決めた)。

## Power LED and focus ring

**決定。** 電源 LED は、暗くへこんだ座金の中に置く。実機の CH SETTING の色の上では、LED の色そのもののコントラストが
1.0〜1.6 しか無い。そこで、コントラストの目標を当てる組を「点灯と座金」にした (ダークで 11.7、ライトで 7.7)。
フォーカスの輪は、白に暗いハローを重ねた二重にする。アンバーの輪は、アンバーのストリップの上で消えるため。
どのストリップが MUTE のチップ・電源 LED・その両方を持つかは、console-sends.md の「背景」にある。

## Contrast

下の値は、描いた DOM から実効の色を読み、コントラスト比を計算して出した。

- **MUTE の点灯: 3.27 → 4.98。** `--mute-on` を `--tally` から分けた。
- **空のメーターと周り: 1.63 → 2.82。** `--meter-frame` を足した。これより明るくすると、メーターが 20 本並んだときに
  うるさい。ここで止めている。
- **`inkOn` は、コントラスト比で黒か白を選ぶ。** 前の決まり (輝度のしきい値 0.6) は、誤った側を選んでいた (赤の
  STEREO のストリップで 3.96 → 4.93)。
- **工場の CH の色 `#4a78c0` は、黒でも白でも 4.43 が上限。** 色そのものが限界を決めている。実機のデータなので、
  色は変えない。読みやすさは、ハローで補う。意図した引き換え。
- **`--groove` は、ライトテーマでも暗い色に固定する。** メーターのスロットを、黒地の LED として読ませるため。
- **`inkOn` は、共有のモジュールへ移さない。** 使う側が 1 つしか無い。

却下した設計は、console-sends.md の「不採用案 (新しい根拠なしに再検討しない)」にある。その表に添える注記が 2 つある。

## Incidents

**ducker の反映が、どこにも届かなかった。** ducker は、CONSOLE に自分のストリップを持たない。
`refreshStrip(duckerId)` は何も見つけず、MIDI やデバイス追従で動いた ducker が、画面では古いまま残った。今は、
ビュー自身の refresh の中で、`attachTo` をたどって、親のストリップへ向け直す。共有の反映の層ではなく、ここに置く。
コントロールのノードを描く場所が、ビューごとに違うため。
