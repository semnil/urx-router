# Decisions: Live sync

> English version: [../../en/decisions/live-sync.md](../../en/decisions/live-sync.md)

ライブ同期 (`src/core/control/live.ts`) とデバイス追従 (`src/core/control/follow.ts`) について、閉じた判断を置く。
何を決めたか、何を却下したか、何をもう提案しないかが対象になる。2 つの仕組みは
[architecture.md](../architecture.md) の「実機制御の接続」と「リンク台帳」に、今できないことは
[known-issues.md](../known-issues.md) にある。下の層の判断は [device-control.md](device-control.md) に、ここに
書く多くの挙動を固定しているレースのハーネスの判断は [race-harness.md](race-harness.md) にある。下の
「操作者」は、このプロジェクトの作業を指示し、決める人のこと。編集の送り方、実機の側の変更の取り込み方、
その知らせ方を変える前に、ここを読む。

## Adding a reader to the worker

**決定 (2026-10-15、[#634](https://github.com/semnil/urx-router/pull/634))。** セッション自身のコマンドの横に足す
読み手 (パラメータ監視の読みや、同じ種類の読み) は、2 つの決まりを守る。

- **受け取った失敗は、先へ回す。** `linkFailureIn` へ渡し、そこから `stopLiveOnError` へ届ける。実機を失った
  知らせは、そのとき読んでいたコマンドが消費する。シェルは、リンクのイベントを出さずにラッチする。エラーを
  記録して続ける読み手は、切れたリンクの上でライブ同期を ON のまま残す。
- **読んだものは、アドレスごとに反映する。読んでいる間にそのアドレスの notify が届いたら、読んだ値を捨てる。**
  いくつかのアドレスを順に読んでからまとめて反映すると、途中で届いた notify を古い読みで上書きし、起きて
  いない往復を記録した。

この 2 つは、その PR のレビューで再現し、直した。

## Reading the silent families ahead of the write (the park)

仕組みは、architecture.md (「実機制御の接続」の下の 2 つの park) と、
[channel-tuning.md](../channel-tuning.md) の「FX EFFECT」にある。変更は
[#472](https://github.com/semnil/urx-router/pull/472)・
[#476](https://github.com/semnil/urx-router/pull/476)・
[#477](https://github.com/semnil/urx-router/pull/477) (2026-09-08 から 2026-09-10)。閉じたこと:

- **手当ては、書込の手前の読みだけ。** 本体のパネルで動かしても実機が何も告知しない系統 (FX のパラメーターの
  配列、Insert FX のエンジンの配列と 3 つのセレクタ、D.Gain) は、購読では覆えない。収束は、書込の範囲の中で
  違うものを送り直す。放っておくと、実機の側で設定した値を、プランの古い写しで上書きする。
- **読みの置き場は `LiveSync.flush()` の境界。UI のセレクタではない。** 2 つのセレクタに付けた版は、アンドゥ、
  MIDI の割り当て、プランの読み込み、Insert FX のセレクタを取りこぼした。境界に置くと、1 つの読みが、書く側を
  残らず覆い、UI にフックは残らない。セレクタへ戻す案は、もう提案しない。
- **ヘッドの park は、実機が乗っているヘッドでアドレスを並べる。** 並びを決めるヘッド (FX の EFFECT TYPE、
  Insert FX のセレクタ) がプランと実機で違うと、同じアドレスが、2 つの違うパラメーターを指す。プランのヘッドで
  並べた読みは、違うパラメーターの値をプランへ入れる。
- **ヘッドは、続けて 2 回、同じ読みが取れたときだけ採る。** 「読みの前と後で同じ」では、読みの間に離れて
  戻ったヘッドを通してしまう。
- **読んだものは、置き換えずにマージする。** 使っている系統だけからパラメーターを組み直した版は、その
  チャンネルが使っていない系統の設定を消した。
- **「このセッションが最後に送った値を実機がまだ持っているなら、プランの値で答える」というガードは、ヘッドが
  並べるアドレスには当てない。** ヘッドが並べないもの (FX の ON と LEVEL、Insert FX のバイパス) だけが、
  このガードをいつも持つ。
- **1 回の flush が取る park は、0 回・1 回・2 回のどれか。2 つの条件は独立している**: 送るものがあるか、
  副作用を送るか。収束のヘッドには、リセットを宣言しないものがある。そのため、park が 1 回の flush (収束の側
  だけ) が実際にある: COMP/EQ Type、BUS Type、Signal Type、PAN/BAL。「いつも 2 回」と書くと、失敗のときの
  保証も間違える。「読みが失敗したらタイプを書かない」は、手前に park があるヘッドの保証になる。park が 1 回の
  flush では、先頭の書込は既に出ている。

**移したことで起きたこと。** 読みを境界に移すと、読みの結果が `requestReflect` のタイマーを通って届き、
インスペクタの作り直しのゲートが、利用者が開いている `<select>` に掛かった。次の 1 回の押下が、ゲートを外す
ことに使われた。今は、結果をすぐに流し (`reflectFollow()`)、インスペクタをすぐに作り直す
(`rebuildInspectorNow()`)。これは、ページに計装を入れて、フォーカスのある要素が `<select>` だと分かって
見つかった。コードを読むだけでは見つからなかった。

**回数を固定するテスト。** `live.test.ts` は、park が 0 回の flush と 2 回の flush を持ち、1 回の flush を持って
いなかった。隣の COMP/EQ のケースは、覆っているように見えたが、早い return で自分を絞っていて、park を 2 回
取る実装でも通る。1 回の flush のために足したケースは、「送るものがあるか」の条件を常に真にすると落ちる。

## The lifetime of the protection record handed to a park

**決定 (2026-10-14、[#611](https://github.com/semnil/urx-router/pull/611))。** インスペクタで EFFECT TYPE を選ぶと、
新しいタイプの工場の値がプランに入る。ライブ同期の間は、タイプの書込の手前の park がそのキーを上書きしない
ように、記録 (`fxReseeds`。読む側の名前は `keepFx`) を渡す。この記録を使うのは、そのチャンネルのタイプの
書込のすぐ手前の park だけ。タイプの書込が待っていない記録 (プランがそのタイプを離れた、または、実機へ
最後に送ったタイプが既にそのタイプである (`holdsSent`)) は、次に走る park が消す (`takeFxReseeds`)。

**起きたこと。** 最初の版は、記録をどの park にも渡し、タイプの書込が起きないとき (Hall、Room、もう一度 Hall と
選び、送る前に元へ戻ったとき) に消さなかった。その後、別のチャンネルの COMP/EQ Type の変更が、古い既定値を
守ったまま収束の park を走らせ、その値を送った。外部のレビューが、スタブで再現した。

**帰結。** 守る記録や保留の記録の寿命は、それが待っている書込に結ぶ。ジェスチャごとに作り、決まった 1 つの
消費者だけが消す記録は、その消費者が来ない経路で残り、後の関係のない操作に効く。

## Send throttling

**決定。** 編集は、`DEBOUNCE_MS` の末尾スロットルで送る。編集が来ても、窓を張り直さない。前の debounce は、
編集のたびにタイマーを張り直していたので、続けてドラッグしている間は 1 度も送らず、止まったときに初めて
送った。連続して動かすコントロールが残らず当たり (CONSOLE のフェーダー、ノブ、Send を含む)、実機には、
動きの終わりしか届いていなかった。1 回の flush は、プランの全体を変換して差分を取る。これは、窓ごとに 1 回
行える軽さになっている。

**例外。** 副作用のあるパラメーターを送る flush は、収束を走らせる。収束は窓よりずっと長く掛かる。この印を
持つスライダー (EQ 1-knob の level) は、間隔を保証すると収束が連なる。「前の flush が収束したか」だけでは、
判定に足りない。収束の後の最初のジェスチャ (関係のないフェーダー) が、また無音に戻る。そのラッチが立って
いる間だけ、送る前の差分に副作用のあるパラメーターがあるかを問う (`convergePending`)。

## Matching the announcement (echo) of the app's own write

**決定 ([#339](https://github.com/semnil/urx-router/pull/339)、2026-08-11。順序は
[#569](https://github.com/semnil/urx-router/pull/569)、2026-10-11 で決着)。**

- **エコーは、スナップショットに加えて、「ACK が済み、まだ告知されていない書込」(アドレスごとに持つ) とも
  照合する。** スナップショットの 1 つの値とだけ照合すると、同じアドレスへの 2 つの書込のうち、2 本目が
  スナップショットを進めた時点で、1 本目の告知が実機の側の変更に見えた。これは、ドラッグで届く。その結果、
  古い値がプランへ書き戻され、全体の照合が走り、アンドゥの履歴が何の知らせも無く消えた。
- **この書込は、壁時計で持つ。** settle の notify の連番を借りると、静かなリンクでは期限が来ない。告知の
  来ないパラメーターの記録がたまる。
- **順序は、飛行中 (まだ ACK されていない) の書込の値、保留のキュー、スナップショットの順。** 飛行中の値に
  一致したら、そのアドレスの保留のキューを捨てる。キューの中で一致したら、一致する最も新しい記録と、それより
  前の記録を消す。前の順序 (キューが先で、最も古い一致) では、実機が続きの最後の書込だけを告知したとき、
  古い値がキューに残った。保持の窓の中で、利用者が実機をその値へ戻した操作は、エコーとして飲まれ、盤面にも
  プランにも出なかった。
- **受け入れた代償。** それぞれの書込が、遅れて、順に告知されるなら、途中の値が一瞬出て、全体の照合が 1 回
  走る (最後は一致する)。コードは、後の書込に追い越された書込を、実機が告知しないことを前提にしている。
  そのため、実機を相手にすると、これは起きない。

**テストの罠。** `DeviceFollow` を載せた単体テストで、アイドルの照合より後まで待ってから assert すると、その
照合が誤りを直し、変異が生き残る。値を直に追従したかどうかは、notify のすぐ後に assert する
(`live.test.ts` の「ends on the unit's last announcement…」)。

## Another client's notify that arrives before the app's own announcement

**決定 (2026-09-24、[#507](https://github.com/semnil/urx-router/pull/507))。** このセッションの書込が出ていて、
まだ告知されていないアドレス (`LiveSync.hasUnannouncedWrite`。追従の `isSuperseded` のフックで聞く) への notify
は、プランへ入れない。そのノードを、範囲つきの読みに回す。常設のケースは `e2e/race/t1b-overtake.spec.ts`。

**却下した案。** 最初の修正は、アイドルの網を張るときだけ早く return していて、refetch の経路を壊した。直に
届いた値を捨てる判定は、「反映しない」だけを意味する。notify は、必ず読み直しへ落とす。

## Follow re-reads wait while a flush is scheduled or running

**決定 (2026-09-24、操作者。同じ PR)。** flush が予約されているか走っている間、追従の照合は待つ
(`live.isWriting`)。前に決めていた「収束のときだけ待ち、ふつうの flush とは並んで走る」は、これで置き換わった。

**理由。** 上の節の読み直しは、(a) 書込の ACK と告知の間に始まると、settle がほかのクライアントの値を告知として
受け取った。(b) 同じノードへの、まだ送られていない編集を、マージで取り消した。これは、その PR より前から
あった欠陥で、ふつうの実機の側の変更でも起きる。(c) 名前には、この判定そのものが無かった。

**却下した案。**

- **置き換えの窓の間だけ待つ。** (b) の一般の形が残る。
- **常に開いているプランの書込の監視で、送っていないキーを保つ。** その監視は、実機から来た書込も、アプリの
  編集に数える。
- **送った値の重ね合わせを、追従の読みに掛ける。** 送っていない値がデバイスの見え方に入り、スナップショットが
  それを「送った」と記録する。

**その後の変更。** `t8-stress` は、打鍵の前に読みを通信に載せて、重なりを作る形にした。`tzb-tail` の、
ドラッグの間のまとめての変更は、「flush のすき間で読む」と「離した後に読む」の両方を受け入れる。refetch が
開いたまま告知を消費する単体のケースは、届かなくなったので、操作者の決定で消した。refetch の側の同じ系統は
[#513](https://github.com/semnil/urx-router/pull/513): flush が最初に取る値の中に refetch のヘッドがあれば、最初の
書込の前に編集の監視を開いて読みに渡す。送り始めた後に現れたヘッドは、次の flush まで待つ。

## A value held for the next flush is guarded on every path that rewrites the snapshot

決まりは、architecture.md「内部状態の取り直し: スナップショットと履歴ベースライン」の段落と、その後の表に
ある ([#513](https://github.com/semnil/urx-router/pull/513)・
[#514](https://github.com/semnil/urx-router/pull/514))。

**起きたこと。** 先送りを入れた後、レビューの 6 巡が、1 巡に 1 つずつ、送っていない値を「送った」と記録する
経路を見つけた: 収束の送信、収束の後の取り直し、flush の間に初めて現れたアドレス、別のノードの refetch の
読み戻し、refetch が読まないチャンネルの名前。表の行は、段落を 1 巡ずつ直す間に取り残され、マージの後に
PR の #514 が直した。

**帰結。** 同じ種類の変更は、スナップショットの書き手 (`capture` を呼ぶ所と `noteDirect`) と、それぞれの
読みが実際に読んだものを並べる所から始める。経路ごとに、「送っていない値が次の flush で出る」テストを 1 本
当てる。段落を直したら、同じ節の表も読む。

## Display-update throttling

**決定。** `requestReflect` は、タイマーの上のゲート (`REFLECT_MIN_MS`) で、直の経路、範囲つきの読み戻し、
全体の読み戻しが、これを通る。仕組みは architecture.md「表示更新」にある。

**却下した案。**

- **アニメーションフレームでまとめる。** 120 Hz のディスプレイでは、描くものが無いまま回る。
- **`graphDirty` を消す。** この印は、「追従のまとまりは作り直しが要る」と「CONSOLE の編集は塗り直しだけで
  足りる」を分ける。グラフが隠れていることからは、導けない。

## An incomplete follow read merges nothing

**決定 (2026-10-11、操作者。[#580](https://github.com/semnil/urx-router/pull/580))。** 全部か、無しか。不完全な
まま返った追従の読みは、読んだものを 1 つもプランへ入れない。前の姿の何が悪かったか、この決まりで受け入れた
代償は、PR にある。

**却下した案。** 部分のマージを残し、読めなかったノードに「?」を付け、履歴には触らない。

**2 つの守りは、別々。** `accept` を外すと、単体のケース (「merges nothing from a reconcile whose read comes
back incomplete」) だけが落ちる。`assertReadComplete` の位置を戻すと、レースの 2 つのケースだけが落ちる。
レースのティアは、描かれたものを読む。反映が走らなければ、プランが汚れていても緑のままになる。

**単体のケースの書き方。** 読みは、ノードの単位で失敗する。1 つのノードの中で拒んでも、どちらの実装でも
何もマージされず、見分けが付かない。2 つのノードを同時に notify し、片方の読みを拒む。

## The cap on holding sends while a converge is pending

**決定 (2026-10-11、[#592](https://github.com/semnil/urx-router/pull/592))。** 収束が待っている間の再アームは、
始まってから `CONVERGE_DEFER_MAX_MS` で止める。この値を決めた比較と、試したほかの値は、PR にある。

**上限が掘り出した 2 つの欠陥。** どちらも、上限とは独立している
([#591](https://github.com/semnil/urx-router/pull/591))。

1. 収束の書込が、エコーの照合に登録されていなかった。固定した写しから送ったフェーダーの告知を、追従が実機の
   操作と読み、プランを戻した。
2. 収束の後の取り直しが、収束の書込が上書きしたパネルの操作を、ジャーナルから戻した。今は、収束の書込が
   受理された時点で、そのアドレスのジャーナルを消す。**却下した案:** 収束が終わるときに、ジャーナルを
   まとめて消す。書込の後のパネルの操作を失う。

**閉じた件 (操作者)。** もっと長い上限で試した 1 回が、1 つの操作の後に、プランと実機が食い違ったまま
終わった。告知のログを入れる前の回で、仕組みは分かっていない。同じ回で、欠陥 1 が動いていた。ログを入れた
後は、起きていない。**却下した案:** #591 より前のコードで、再現するまで回す。**覆す条件:** 同じ
症状が出たとき。そのときは、先に告知の判定のログを取る。

## No announcement is required per write

**決定 ([#446](https://github.com/semnil/urx-router/pull/446))。もう提案しない。** `settle.ts` は、「1 本の
notify は 1 つの書込にだけ答える」を持たない。コードは、後の書込に追い越された書込を、実機が告知しないことを
前提にしている。書込ごとに告知を求めると、ドラッグの最後を除く操作が、どれも「どこにも届かなかった書込」と
して報告され、そのたびに全体の照合が張られた。今は、アドレスごとに、済んでいない義務を前へまとめる。

**これも、もう提案しない。** notify の位置の台帳。まとめた後は、「最後の notify か」の判定と同じ答えしか
出せない。「2 つの書込が同じ印を共有する」問題は、まとめることが先に解く。

**まとめが届く範囲。** まだ判定していない義務まで。判定が済んだ書込の次の書込は、自分の告知を求める。

## The link outlives the session

決定と理由は、architecture.md「セッションの終了処理」と
[#450](https://github.com/semnil/urx-router/pull/450) にある: セッションを終えても追従の読みを中断しない。
リンクは、残っている読みが終わってから閉じる。保持者は、切断の後に返す。ここには、1 つだけ書く。

**切断の失敗を知らせるのは、セッションがエラーで終わったのではないときだけ** (`reason !== "error"`)。条件
なしで知らせる版は、`stopLiveOnError` が同じ切断について既に出したダイアログの上に、2 枚目を重ねた。レースの
ハーネスの `t5-drop` の 2 つのケースが、これを拒んだ。変異では捕まっていなかった。

## The status line's vocabulary

**決定。** ステータスバーは、リンク台帳の一部を、パネル自身のラベルと数字で出す
([#253](https://github.com/semnil/urx-router/pull/253))。**バーに項目を足すのは、操作者の明示の指示があるとき
だけ。**

**`#statusbar` は、メッセージの要素のままにする。** 1 度、バーの全体の入れ物に変えた。E2E の spec は、この
id を「ステータス行の文言」の意味で使っている。そのため、行の側に新しい名前 (`.statusbar-row`) を付け、id は
メッセージへ戻した。

## A rate change's line is not replaced by the session's

**決定 (2026-11-13・操作者)。** 操作者に見せる行は、読まれる前に置き換えてはいけない。ライブ同期中は、
レート変更の自身の送信と、リクロックの後の読み出しがすぐに報告する。そのためレート変更の行 (レートと、それが

## Send pans under Pan Link

挙動は architecture.md「リセット連鎖と、収束ラウンドが送るもの」にある。変更は
[#534](https://github.com/semnil/urx-router/pull/534) と
[#535](https://github.com/semnil/urx-router/pull/535)。

**決定 (2026-09-29、操作者。もう一度は持ち出さない)。**

- **Pan Link を切った後の Send のパンは、その Send のソース (Send を出しているチャンネル) の値にする。** 実機が残す値と同じにする
  (`sendPansToSources`。パネルの編集と、追従の直の経路から呼ぶ)。リンクの前にプランが持っていた値を書き戻す
  案は、採らなかった。
- **FIXED のバスへの Send は、保存している PRE を、読み取り専用で出す。** Level と Pan について、この面が
  従っている決まりと同じ ([console-sends.md](../console-sends.md))。最初の実装は、実際に効く値 (消灯) を出して
  いて、差し戻された。信号の流れで答えるのは、GRAPH の PRE の印と、Ducker の注記だけ (`sendIsPreFader`)。
- **`PAN_LINK` に `sideEffect: "converge"` を付けない。** 宣言ありの Write と、宣言なしの Write は、同じ回数で
  終わり、残差が無かった。
- **Pan Link を Send より前に書いても、切る操作は先に着かない。** 同じ回の Send のパンがソースを動かし、次の
  回が戻す。一時的なずれは受け入れ、説明を直した。Send を次の回へ遅らせる案は、採らなかった。
- **Pan Link を入れた操作の取り消しは、Send のパンを、リンクの前の値に戻す。** 取り消しは、ジェスチャの前の
  プランへ戻る。上の最初の決定は、取り消しには当てない。
- **本体自身の画面でバスを FIXED にすると、実機は、告知せずに Pan Link を切る。** そのため、読み直しが
  `panLink` の入から切への変化を見たら、その回で読まなかった Send を、ソースの値にする (全体の読み直しは
  Send を読むので、何も解放しない)。これが受け持つのは、範囲つきの読み直しと、静止のときの全体の照合の間の
  窓だけ。全体の照合は、Send も読む。この処理は残す。守りは単体テストで、レースのハーネスには段を入れない
  (判定が時間に依るものになる)。
- **リンクの間、プランの Send のパンを、ソースの位置に保つ** (入と切の両方の端で `sendPansToSources`、
  リンクの間にソースが動いたら `alignLinkedSendPans`)。**読み込んだプランも、そろえる。** 読み込みでは
  そろえない版は、#535 の再レビューで差し戻された。CONSOLE の読み取り専用の SEND PAN ノブ、MIDI の返し、
  次の保存が、文書の値を出し続ける。面はプランが持つ値を出すので、表示だけを差し替える直し方は取れなかった。

**置き換わった決定 (2026-10-14、[#611](https://github.com/semnil/urx-router/pull/611)、操作者の指示)。** 「FIXED の
バスでも、プランの `panLink` を保って書く」は、もう成り立たない。インスペクタでバスを FIXED にすると、実機と
同じく、プランの `panLink` も切れる。VARI に戻しても、元には戻らない。読み込んだ文書や、実機の読みが
持ち込んだ「FIXED で Pan Link が入」は、そのまま書く。
