# Reusable assets

> 日本語版: [../ja/reusable-assets.md](../ja/reusable-assets.md)

Everything the repository already carries — harnesses, probes, generators, fixtures and pin tests —
and when to reach for each. The rules a change has to follow when it uses or extends one are in
`AGENTS.md` "Reusable assets". `pnpm check:assets` holds the asset index below to the tree in both
directions, and the English table is the one it reads: the Japanese translation is held only to the
file-reference rules every document is, so a row changed here is changed there in the same change.
What the check holds is in [repository-checks.md](repository-checks.md) "`pnpm check:assets`".

## The asset index

**Nothing below needs to be built again.** The pnpm scripts in AGENTS.md "Development" are the
everyday commands; this is everything else the repo already carries — harnesses, probes, generators
and pins that are easy to miss and expensive to duplicate. Before writing a new tool, `ls scripts/`
and `grep -rn "window.__urx" src/` cost three minutes.

**A fixture row is compared with the fixture by hand after a pull request adds a public call to it.**
The check holds a row to naming every export only where the row is written as an inventory
(rule E3 in `scripts/check-assets-index.mjs`); a row written as prose about when to reach for the
fixture goes on passing while it describes the calls the fixture had before.

**Driving the app from outside.** All five are statically dropped from a production bundle, and
`ci.yml` greps `dist` for each name.

| Handle | Reach for it when | Where it lives |
| --- | --- | --- |
| `window.__urxConsole` | measuring CONSOLE render/meter cost, or reproducing a strip rebuild from outside | dev build only (`pnpm dev`); its surface is pinned by `pnpm test meter-bench` |
| `window.__urxKeyProbe` | answering what only the real webview can — does a chord reach the page, does WebKit's field undo fire, what does a native menu click do | dev build only; F2–F10 bindings pinned by `pnpm test keyprobe` |
| `window.__urxMidiProbe` | the question is a **gap** — how long after the app transmits does a controller answer, and does that answer land before or after incoming MIDI stops being refused. Timestamped rx / tx / engine decisions / live-sync marks on the engine's own clock, plus the silence that reads as "nothing happened" (a feedback pass that returned early). Its report prints, per mark, how much went out and when the first reply landed. **It also writes a trace file**, beside the link ledger, which is what a question spanning a page RELOAD needs — the in-page ring and the clock it stamps with both restart there, so the ring alone is empty at the moment being investigated. Reach for the file when the symptom is intermittent and has to be caught rather than reproduced on demand; the handle's flush makes it current before it is read. Its name, batching, rotation and the two compile-time gates that keep it out of an installed app are in [docs/en/architecture.md](architecture.md), "External MIDI control" | dev build only (`pnpm tauri dev`); pinned by `pnpm test midi-probe`, which drives the sink through that handle — start, record, flush — against a stubbed shell |
| `window.__urxParamWatch` | the question is **when** a parameter the app never writes, and reads nowhere but in this watch, changed on the unit, and what else moved around it — an intermittent change that has to be caught over days rather than reproduced, with the operation mode, the current scene and the SCENE LIST cursor recorded as context; the SIM view reads those three as well. It registers those addresses as a subscription of its own beside the live-sync set, reads them once a second, and writes every change with the wall clock to a JSONL file beside the link ledger, plus a liveness line a minute so a quiet stream and a dead one read differently. Read-only; what it records and the two compile-time gates are in [docs/en/architecture.md](architecture.md), "The parameter watch (dev builds)" | dev build only (`pnpm tauri dev`), while Live sync is up; pinned by `pnpm test param-watch` against a stubbed shell, and its life with the session by a case in `pnpm test main.device` |
| `window.__urxTrace` | needing the plan-key write ledger (who wrote which key) or the live snapshot's contents | `VITE_TRACE=1` build only (`pnpm build:trace`, served by `pnpm e2e:serve:trace`); pinned by `pnpm test:e2e:race t9-probe` |

| Naming the test file a vitest worker died in | a unit run reports that a worker exited unexpectedly and one file's results are missing with nothing naming it | set `URX_VITEST_WORKER_LOG` to a file path and run `pnpm test`: `vitest.config.ts` then adds `scripts/vitest-worker-log-setup.mjs` as a setup file, and each worker appends a start line with its pid and test file before the file loads, and an end line when that worker ends the way vitest ends it once the file is done (it exits on its own, or vitest sends it SIGTERM). The file with a start line and no end line is the one, and its pid is the one an OS crash report for that worker carries. A reporter given on the command line does not turn it off. macOS and Linux only: on Windows `vitest.config.ts` refuses the variable, since a SIGTERM there ends a worker without running the handler that writes its end line. Pinned by `pnpm test vitest-worker-log`, which kills a fixture's worker and reads the log back; on Windows it runs the two config cases (the refusal among them) and the run with the variable unset, and skips by name the four cases that need the SIGTERM handler |
| Reading the REAL webview from outside | the question is what the shipping engine does and Chromium's emulation cannot answer it — an OS-driven media state (Windows high contrast is the worked case), a computed style, a clipped capture of the running window | **Windows only**: launch with WebView2's extra-browser-arguments environment variable set to a remote debugging port, then drive the DevTools protocol over the socket that port advertises — evaluate an expression inside the page, or capture one element by its rectangle. A debug build has devtools on and the global Tauri bridge in reach, so a menu command can be invoked exactly as a click invokes it. **Drive that socket yourself — do not attach Playwright to it.** `connectOverCDP` applies Playwright's own emulation defaults to every page it attaches to, and one of them turns `forced-colors` off; the system colours keep reporting the high-contrast palette, so the page reads as an engine that knows about the contrast theme and has a broken media query, and every computed background comes back as the app's ordinary colour. That is the exact inverse of what the engine does. Node's global `WebSocket` plus `Runtime.evaluate` / `Input.dispatchMouseEvent` / `Page.captureScreenshot` is the whole dependency. Turning high contrast **on** also needs the app restarted — a running WebView2 never picks it up, not even across a reload — while swapping between contrast themes with it already on lands live, and turning it **off** lands live too, so neither direction predicts the other. **Two things that come back as a picture of nothing rather than as an error**: a `<select>`'s dropdown will not open at all while the window is INACTIVE (a dispatched click, `showPicker()` under a `userGesture` evaluate, and Alt+ArrowDown all leave it shut — and the click's own focus ring shows that at least that input reached the page, so the shut popup is the window state rather than a lost event; once an operator's click has made the window active, the click and `showPicker()` open it, and Alt+ArrowDown has not been tried there), and a popup is a native widget outside the page's compositor, so `Page.captureScreenshot` cannot see one even when it is open. Photograph it with a Win32 screen capture instead — and since **cross-process activation is not available to a probe** (the foreground lock makes `SetForegroundWindow` a silent no-op), arm that capture on a poll of `GetForegroundWindow` BEFORE asking the operator to click, never after: their reply moves the foreground back to the terminal. macOS has no equivalent: WKWebView's Web Inspector is the manual path, which is why `scripts/meter-bench.mjs` is written to be pasted into it |

**E2E fixtures — extend these rather than forking them.**

| Fixture | Reach for it when |

| `e2e/tauri-stub.ts` | a spec needs the desktop shell: file IO, dialogs, device commands, or a whole live-sync session — including a change made on the unit's OWN panel, which `setDeviceValue` (one address, since the read-seeding option fills every instance of a param id at once and so cannot say that one channel differs from its neighbour) then `notifyParam` deliver through the notify stream the stub keeps. That stream is the only way a spec reaches the device-follow paths at all, and the two calls are ordered: an announced change the app cannot read back is one the reconcile undoes. `notifyBurst` is the one to reach for when the subject is a burst's WIDTH rather than one control — the follow layer re-reads the whole device past a few distinct ones — since it delivers a batch in a single call: sent one at a time, the settle can fire part-way through and take the narrow path, which every assertion about the outcome still passes. `deviceValueOf` reads what the stub holds at one ADDRESS, the read half of `setDeviceValue` — reach for it when the question is which instance of a param a value went to, such as a USB output's L half against its R half, since `writesOf` records neither x nor y. `setRefusedReads` refuses every read of the named params — one refused parameter on a link that otherwise answers — and `setHeldReads` holds those reads unanswered until a later call stops naming them, with `heldReadsOf` saying how many wait: reach for them when the subject is a flow caught PART-WAY through a read, such as a model-switching Fetch that has to refuse edits while its read is outstanding, since a stub that answers at once gives the spec no moment to act in. `setWriteEffect` makes a write at one address also move others with no notify — what the unit does when turning the last input CUE off puts back the output cues it held — since the stub otherwise keeps what is written and applies no rule of its own; **In a save → new → open round trip, a spec selects a node only after the open.** A node selection placed between the press of New and the press of Open timed the file chooser out when the specs ran in parallel; `e2e/rename.spec.ts` has the working order.

**An E2E gesture that must move no value is a mis-grab of a node, not a press on a fader cap.** Pressing the centre of a CONSOLE fader's cap moves the fader one detent, because the cap's grab point is offset from its centre. `e2e/undo.spec.ts` ("a mis-grab that moves no value records no entry") has the form.

**Unit fixtures — extend these rather than forking them.** The same rule as the E2E ones, and
harder to find: vitest collects only the test files themselves, so these carry a `*.test-util.ts`
suffix and a search for tests does not turn them up. Each is the host or stub some layer needs in
order to run at all under jsdom or node, and each says in its own header **why it answers the way
it does** — a fixture that answers too obligingly is how a case ends up green while the code runs
the branch nobody meant to test. **Reverse rule E2 in `scripts/check-assets-index.mjs` requires a
row here for every one of them**.

| Fixture | Reach for it when |

| `src/main.test-util.ts` | booting the app entry whole, against the real `index.html` markup — and optionally against a stubbed Tauri shell, which is the same seam `e2e/tauri-stub.ts` gives the E2E tier rather than a second invention. The two scripts behind the "Documentation screenshots" and "CONSOLE render bench" rows of the index

- `scripts/capture-screenshots.mjs` — documentation screenshot capture (graph + console × EN/JA,
  dark theme, URX44V) into `docs/assets/`; the console shot widens the viewport to fit
  `.con-strips`. It also shoots the ducker-bypass warning the development article uses
  (`screenshot-ducker-warning-*`): the default plan's USB MAIN OUT B wire is deleted, CH 5/6 is

  first is an in-page bench that drives the view's own paint loop from a synthetic meter feed (and,
  with `churn`, the device-follow strip rebuild / full re-render) and reports painted frames, JS
  time per frame and per rebuild, DOM mutations, frame gaps and event-loop lag; the second serves a
  tree, runs it in Playwright **WebKit** and brackets the sample with the browser processes' CPU
  time. Every run also carries `scrollCheck`, which pins the strip rack's scroll offset across a
  re-render **in that engine** — the E2E suite's two WebKit projects carry other classes of case
  (`app-webkit` the layout-fit invariants, `race-webkit` the harness cases whose verdict is the
  engine's), so nothing there can fail on this rendering behavior. Both reach the view through
  `window.__urxConsole`, whose surface is pinned by `src/ui/meter-bench.contract.test.ts`. Paste
  `meter-bench.mjs` into the Web Inspector console of a `pnpm tauri dev` window to measure a real
  device feed instead (`__urxBench.run({ feed: "none", live: false })`)
